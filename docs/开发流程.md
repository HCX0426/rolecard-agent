# 开发流程（活文档 · 设计先行）

> 存在的理由（用户 2026-09-18：「没有先设计后端、再设计界面功能、再实现、最后后端对照前端吗？
> 有时候界面不合理还得我说」）：把"设计先行 + 实现后对照回写"固化成可执行的四步，让界面在
> **写码前**就摆出来，而不是事后补救。

---

## 一个功能/能力的标准四步

顺序不可颠倒：**后端设计 → 界面设计 → 实现 → 对照回写**。

### ① 后端设计（先定契约，不写码）
产出落到 `架构总览.md`（模块地图加/改一行）：
- **数据契约**：新增表/列？→ 列名不改、加列走幂等 `_migrate`（铁律，见架构总览 §5）；
- **接口契约**：端点路径、入参/返回字段、错误码（堆栈只进日志不进返回值）；
- **不变式**：这个能力受哪几条硬约束（fail-closed / 路径边界 / 权限三重过滤 / 审计只记路径不记内容 / per-role 隔离 / 配置双源热切五处同步…）。
- 若要加配置项：一次点齐 `Settings` 字段 + `from_env` + `RUNTIME_FIELDS` + settings runtime 视图组 + `.env.example`（check_consistency 会卡前缀）。

**出口**：契约与不变式白纸黑字，能对着它评审，不用猜。

### ② 界面设计（写码前把界面摆出来 —— 治"界面不合理得你说"的那一步）
产出落到 `前端设计.md` 的 **能力↔界面覆盖矩阵**，为该能力**先加一行**并写清：
- **落在哪个页签/面板**（对话/数据/知识库/角色卡/插件/设置/审批/主动）；
- **用户能看到什么、能操作什么**（只读？可编辑？有哪些控件？）；
- **状态**：加载中 / 空态 / 错误 / 成功反馈（toast 三态等）；
- **是否刻意不做 UI**（如 MCP：配置驱动、不给运行时自扩权入口）——"不做"也要在矩阵里写明理由。

**出口**：这一行 + 一句线框级描述（哪块区域、放什么）经确认，再进实现。避免"后端做完了才想界面长啥样"。

### ③ 实现
- 后端：按 ① 的契约写，配 **单元测试（全离线，LLM 注入脚本替身）**；guard/权限/fail-closed 不图省事绕过。
- 前端：按 ② 的矩阵行写；数据只从 `api.ts` 出；复用 `components/ui/`；深色/响应式跟基线。
- **小步跑快反馈**：改哪个模块就先只跑对应测试文件（≈2s）；提交前再走门禁（见下）。

### ④ 对照回写（实现完必须做，否则文档又过期）
- 把 `前端设计.md` 矩阵那行从"设计中"改成最终状态（✅ / ⚙️ / ⬜）；有后端↔前端分歧就**当场修或记进 §6 小缺口**；
- 更新 `架构总览.md`：模块地图、里程碑状态表（A–D / M 线）、关键决策/不变式（若引入新的）、待办清单；
- 触及需求/验收 → 同步 `需求与验收标准.md` 的用户故事与追溯矩阵；
- 改了 `.env`/字段 → 跑 `check_consistency`；
- **扩任何一条尺子的受验面，两臂要在干净 worktree 里量一次**：`git worktree add ../rc-ci-wt HEAD --detach`
  后在那儿跑 `.venv\Scripts\python.exe scripts\check_consistency.py`。理由是 `R28-47` 那次实测：
  给 `doc links` 加 `build/` 前缀之后**本机全绿、CI 红 10 处** —— `build/` 在 `.gitignore` 里，
  那里的名字只在这台机器上存在。**一条检查在本机与 runner 上结论不同，就是判据里混了 gitignore 的东西**；
  现在的结构性防法是把"此处不存在"的引用先问一遍 `git check-ignore` 分区（被跳过的数量写进 OK 行）。
  同理别把整句 prose 套进反引号 —— 那是这条检查读路径的记号。
- **这份设计稿搬进 `docs/archive/`**：判据只有一条 —— 它的结论已经在某份活文档里有一份了
  （总览的里程碑行、前端设计的矩阵、或台账的收口行）。搬完把 `docs/README.md` 索引那一行
  从「活文档」挪到「归档」，并把**指向这份稿子的 markdown 链接与反引号路径一起改到归档位置**
  （写成带 `docs/` 前缀的仓库相对路径：只写 `archive/名字` 会以"既非仓库相对、也非裸文件名"
  被 `doc links` 跳过，于是得到一个看起来绿、其实没人验的引用）。写完就留在 `docs/` 根，
  等于让下一个找现状的人在做完的稿子里翻。
  **例外：审计台账不搬。** 它被代码按编号引用，搬进 `archive/` 会让那些引用集体变黄，
  所以它**原地封存**（`R26-19` 定下的同一件事）。

**出口**：设计文档描述与代码现状一致（文档可信是它不被跳过的前提），且 `docs/` 根目录里
每一份都还是活的。

## 怎么加一个领域插件（开发者向）

> 这一段原来长在**插件页的界面上**（`PluginsPage.tsx` 一整节"如何新增一个领域插件？"），
> 09-28 轮 A 类把它搬进文档：那三步是给改这个仓库的人看的，不是给使用者看的，
> 摆在用户界面里等于把仓库目录结构当产品文案（`src/rolecard_agent/domains/<id>/`、
> `build_registry` 接线…）。使用者需要的那一句仍然在界面上：**为什么没有"安装"按钮**。

1. 新建 `src/rolecard_agent/domains/<id>/` 包：`models.py` / `service.py` / `tools.py`，
   需要建表的再加 `schema.sql`；
2. 在 `domains/registry.py` 的 `DOMAINS` 追加这个 id，并在 `build_registry` 里接线它的工具工厂
   （漏接线启动即报错 —— 这是刻意的，别让"注册了一半"安静通过）；
3. 重启服务：建表、插件行、工具注册自动完成；**随包的 schema 清单是按目录现数的**
   （`packaging/rolecard-backend.spec` 的 `domains/*/schema.sql`），所以新域不必改 spec，
   但**要重打 sidecar** 才会进安装包；
4. 在角色卡页为需要的角色勾选新工具（白名单默认不含新工具）。

权限边界不变式：**不做界面动态安装**（让运行中的 Agent 自己扩权 = 把权限边界交给运行时注入）。
RAG 检索是例外那一侧：它是内核能力，按角色作用域授权，不属于任何插件。

## 门禁：别每次都跑全量（慢在真机冒烟 + 覆盖率二跑）

| 场景 | 命令 | 约时 | 覆盖 |
|---|---|---|---|
| 迭代中小改（默认） | `python scripts/gate.py --fast` | ≈1.5 分钟（实测 83.8s） | ruff + mypy + 单测(-x) + 一致性 |
| **CI 每次 push/PR** | `python scripts/gate.py --ci` | ≈5.5 分钟（本机实测 320.5s） | 快层全部 + `baseline --check`；**覆盖率档不进 CI**（2026-10-04 起整步跳过，只在本机全量档与夜间臂跑）；跳过需要 node/浏览器/真机的步骤（各有专属 job）|
| 相关改动即时反馈 | `pytest tests/unit/test_<模块>.py` | ≈2 秒 | 单模块 |
| 提交 / 发布前 | `python scripts/gate.py` | ≈4 分钟（离线冒烟实测 10s）；跑真机 UI 段再 +≈10 分钟 | + 覆盖率≥90% + 前端 test/build + 冒烟 14 项 |
| 真模型验收（不进门禁） | `pytest -m live` 或 `scripts/tools/run_eval.py` | 分钟级、随模型版本波动 | 真 8B 抽取 / 评测基线 |

> 计时口径（2026-09-19 实测校正，此前那组数字是 2026-09-18 的旧值）：单测占 fast 层 88%；
> **pytest-xdist 并行反而更慢**（各用例自起临时 chroma/sqlite，
> 建库开销吃掉并行收益）——别往并行优化，要快就只跑相关测试文件。
> 真模型/真机用例一律带 `live` 标记，`addopts` 里的 `-m 'not live'` 把它们整条挡在门禁外；
> 冒烟的浏览器那段用 `SMOKE_SKIP_UI=1` 显式跳过（提交前至少跑一次完整冒烟）。
> `live` 用例**要机器上有对应东西才有牙**：视觉闸门那条要任何一个纯文本 Ollama 模型
> （`ollama pull all-minilm`，45 MB；换名字用 `ROLECARD_TEST_TEXT_MODEL`）。没装时它**跳过而不是
> 失败**——这是有意的：探针"问不到"就是"不知道"，而那本来就是放行的正确答案，把环境问题报成
> 断言失败会让这条用例在别人的机器上变成噪音。
> 门禁每跑一趟会把**它自己量到的**几个数**分槽**写盘（2026-10-07 拍板"数字移出散文"的另一半）：
> **覆盖率家族**进 `docs/gate-readings.json`（入库 —— 只有全量档量它、src 没动时整步跳过，
> 入库不吵）；**后端/前端用例数与 head** 进 gitignore 的 `build/gate-readings-scratch.json`
> （快档每跑一趟都变，住在入库文件里就是每轮一笔纯数字提交 —— 实测一个会话 13+ 笔
> "读数收尾"，其中不少是把一个还对的数改成另一个还对的数）。**按键合并**，每个键自带
> 测量时刻，所以 `--ci` 那趟不会抹掉 `--only 前端` 补的数。
> README **不抄数，只给链接**：断言 `README headline numbers` 是**反向守卫** —— 首屏 35 行内
> 三个头条形状出现即红（谁把数抄回来就拦，包括未来的自己），链接丢失即红（数字的家不能
> 没有门牌）。那格数不是"要记得更新的文档字段"，是"上一趟量到了什么"（10-01，`R28-55` 的
> 第二次收口；那时它拿 README 与读数**对读**，2026-10-07 起改反向 —— 对读拦得住"漂"，
> 拦不住"吵"）。**「一致性有几条」这一格故意不在读数里**（`R28-69`）：那 45 条里含
> "比对 README 这一条"自己，于是 README 一漂就有一条红、读到的数就少 1，改成对的那个数
> 下一趟又回到原值 —— 自指的东西不能当读数，它只留在门禁输出那一行里。
> 入库槽**入库**的理由：判据读 gitignore 里的文件等于把"这格数真不真"换成"这台机器上
> 有没有这个文件"（第六条规矩，见 09-30 那笔）。只补读其中一个数：
> `python scripts/gate.py --only 前端`。
> **runner 的读数两槽都不碰库内那份**（`R28-74`）：`ci.yml` 给 gate 那几步设了
> `GATE_READINGS_SCRATCH=1`，两槽都落 gitignore 的 `build/`。原因是**覆盖率是按平台的数** ——
> 本机 win32 与 Linux runner 各量各的都对（win32/posix 两条分支互相执行不到对方的行），
> 而入库那份记的语义是"哪台机器量的"；谁都能覆盖它，就等于两份事实互相把对方判成漂移。
> 读数里因此还有一格 `coverage_platform` 说清是谁量的。
> 一个坑记在这儿：**pytest 的 quiet 是累加的**，`pyproject.toml` 的 `addopts` 已带一个 `-q`，
> 命令行再补一个就成了 verbosity −2，最后那行 `N passed in Xs` 连同失败时的 `FAILED tests/...`
> 一起被吞 —— 第一版的读数就这么永远读不到后端那个数，而缺一个键看起来完全像"这一档不量它"。

### 节奏：每项局部检查，每阶段一次全套（2026-09-19 定）

一轮整改里每项都跑一次全套，实测成本是 6×88s ≈ 9 分钟；而多数失败其实是秒级就能暴露的
（import 顺序、类型、某条测试的语义）。所以：

- **每个提交前**（局部，约 10s）：`ruff` + `mypy` + **只跑受影响的那几个测试文件**
  （`.venv\Scripts\python.exe -m pytest tests/unit/test_x.py tests/test_y_api.py`）。
  绿了才提交 —— 提交保持自洽可 bisect，见下一节。
- **每个大阶段结束时**（一次）：`gate.py --fast`。这一层负责抓到"局部检查看不见的跨项串扰"
  （改了配置契约影响别的模块、装配根挪了位置、检查器自身被改坏）。
- **补一次全量的判定条件**（满足任一）：删改公开 env 配置项 / API 形状、动前端渲染的数据面、
  改装配根或进程生命周期、发布/打 tag 前。否则阶段末的 `--fast` 就是终点。
- 阶段末失败时**按提交二分定位**，不要回头整片重改；也别把"每项一次全套"当成保险 ——
  重复的慢检查不等于更可靠，它只是让人不敢改。

## 桌宠壳（`shell/`，Electron）怎么跑（2026-09-20 起）

```
cd shell && npm install          # 首次要设 ELECTRON_MIRROR，否则二进制从 GitHub 拉常卡
npx electron/install.js          # 若上面只装了 wrapper 没下二进制（369 MB），补这一刀
npm run dev                      # = tsc + electron .；关桌宠窗用 ROLECARD_PET=0
```

壳侧的环境变量约定（与壳技术无关，都不是 Python 的 `Settings` 契约）：

| 变量 | 作用 | 缺省 |
|---|---|---|
| `ROLECARD_PYTHON` / `ROLECARD_API_SCRIPT` | 开发态用仓库 `.venv` + `scripts/run_api.py` 起后端 | 由仓库根推 |
| `ROLECARD_BACKEND_CMD` | 打包形态：整条后端启动命令（优先级最高） | 未设 |
| `ROLECARD_API_PORT` / `ROLECARD_BACKEND_URL` | 连哪个端口 / 控制台地址（壳必须把它**同时作为 `RUN_API_PORT` 传给子进程**，否则"后端起在 8000、壳在探 8011"这种谁都没错却连不上的事故会重演） | 127.0.0.1:8000 |
| `ROLECARD_PET` | `0` = 不开桌宠窗 | 开 |
| `ROLECARD_OLLAMA_BIN` | 壳起停本地推理服务时用哪个可执行文件（D③-b）。不设则按 `%LOCALAPPDATA%\Programs\Ollama` → `Program Files(x86)\Ollama` → PATH 依次找。**装在非默认位置又没进 PATH 的（本机就是 `D:\code\Ollama`）必须设这一项** | 自动发现 |
| `ROLECARD_OLLAMA_URL` | 壳判断"端口上有没有人在跑"的地址（只用来决定要不要再起一个；"在不在跑"由后端的 `/api/local-service` 说） | `http://127.0.0.1:11434` |
| `ROLECARD_PARENT_PID` | 后端看门狗：父进程没了就自杀（壳注入） | — |

**Electron 侧实测（两扇真窗 + 真进程）**：

- 透明成立：`transparent` + `backgroundColor:#00000000` + `hasShadow:false` 三者齐，截屏幕
  区域可证 IDE 内容从透明区透出。**按窗口截图永远看不出来**（不合成下层窗口）。
- 无边框拖拽**不再需要壳的能力**：`-webkit-app-region: drag` 由 Chromium 处理，后端托管的
  页面直接能用（Tauri 那边"远程源拿不到注入 → 拖不动"的坑在这里不存在）。
- 着陆页是 `file://` 页面，**自己跨源 fetch 后端只会拿到恒假信号** → 探活必须问主进程
  （`shell:backend-reachable`），端口与判据只有一处定义。
- 硬杀壳（`taskkill /F` 不带 `/T`）后，后端在 1 秒内消失，但**没打印看门狗日志** ——
  带走它的是 Chromium 侧的进程管理（作业对象），不是 `core/parent_watch.py`。看门狗作为
  第二道保险保留（换壳、或壳被整树 `taskkill /T /F` 时只剩它），其机制由
  `tests/unit/test_parent_watch.py` 用真父子进程闭环证明；**打包态是否还靠 Chromium 兜**这一条
  已于 2026-09-20 在真安装包上复验，结论见下面「进程归属：两层各自实测过谁在兜」。
- 验证进程一律用真实 Windows PID：git-bash 的 `$!` 是它自己的编号，杀不到东西。
- **关控制台 = 收起**（`close` 里 `preventDefault` + `hide`），唯一退出入口是托盘「退出」；
  单实例锁让"再跑一次 `npx electron .`"变成"把控制台带回前台"。这两条都可以不靠托盘验证：
  点 ✕ 后用 `list_windows` 看窗口消失而进程仍活，再起第二个实例看窗口回来。
- 窗口位置存在 `%APPDATA%\rolecard-shell\window-state.json`。**不用点桌面也能验全三段**：
  把这个文件手工写成越界坐标（如 `{"main":{"x":-5000,"y":-5000,…}}`）再启动 → 窗口被夹回
  当前工作区，且 `move` 事件会把夹完的位置写回文件 —— 还原、夹取、保存一次跑完。
- 桌宠那扇窗要 `page-title-updated` + `preventDefault`：不然着陆页/控制台的 `<title>` 会把它
  在窗口列表里也叫"控制台"，看窗口名字排查时会找错东西。
- **锁屏时合成输入进不去**（`foregroundStatus: blocked_before_pointer_input`，窗口也不会被
  置前）—— 那是环境问题不是拖拽坏了，让用户解锁再继续。
- **开机自启只在打包态给**（托盘那条勾选在 dev 下整条不出现）：`setLoginItemSettings` 写进
  登录项的是"当前这个 exe"，dev 下它就是 `node_modules/electron/dist/electron.exe` —— 一条
  指向依赖目录、卸载也带不走的假启动项。自启带起来的启动会带 `--autostart`，控制台不显示。
- **全局热键 `Ctrl+Alt+R`** = 唤起/收起控制台。注册失败（被别的程序占了）只 warn，不影响
  启动；退出时 `unregisterAll`。**不要**往"热键让角色开口"那类方向加：那是能改变主机状态的
  动作，~~operator 鉴权（P0-3）还不存在~~。**2026-09-25 订正**：P0-3 已于 09-21 闭环，但这条
  结论**不跟着变** —— 认证对**本机来源永远不看角色**（`api/access.py` 第一条短路），而全局热键
  天然就是本机的，所以鉴权拦不住它。拦它的是"这个动作压根不上桥面"。见架构审计 §11.5 的同一条订正。
- **原生目录对话框走 `pickDirectory()`，零参数**：路径由用户在系统对话框里挑，页面不给路径，
  所以它不是一条"任意路径"的口子。桥上新加的四个方法（起停 Ollama 三件 + 选目录）同理。

### 安装包怎么打（D②-4，2026-09-20 实测）

```
cd frontend && npm run build                      # ① 界面：dist 是后端静态托管的，必须先有
cd .. && .venv\Scripts\python.exe scripts\build_sidecar.py   # ② 后端 → build/sidecar/（≈2 分钟）
.venv-ocr\Scripts\python.exe scripts\build_ocr_worker.py     # ②′ 随包 OCR → build/ocrworker/（10-03 加）
cd shell && npm run package:dir                   # ③ 解包版（不装进系统，用来验打包态）
cd shell && npm run package                       # ④ NSIS 安装包 → shell/release/
```

**这几步是"手工全跑一遍"的形状；`install_package.ps1` 实跑的是 ①②②′④ 四步**（它自己的编号是
`[1/6]…[6/6]`，其中 [2/6] 备份、[3/6] 关进程、[6/6] 纯度尺子都跟打包无关）。
差的正是 ③ `package:dir` —— 也就是 `shell/release/win-unpacked/`：`probe_package_artifact.py`
那三层读的就是这一份，所以**只跑脚本不打 ③，那发探针量的是上一包的解包物**。
10-01 实测过这个形状：脚本装完之后 `win-unpacked` 里那个 exe 还是 09-30 那份，
而 `build/sidecar` 已经是新的 —— 探针 ① 会红在 `pets/hiyori/pack.json` 这一个文件上。
要"打一发包并自证"就按 ①②③④ 全跑；只想装现有那包就 `install_package.ps1 -SkipBuild`
（它会在 `build/sidecar` 缺席时 throw，不会拿旧构建物冒充新的）。
**安装包文件名那一问分两个时机，别问错**（`R28-65`）：`-SkipBuild` 那支在**动手之前**问 ——
版本线合并后名字变了而 `release/` 里还是旧的那份，这一问就该在这一步出声并列它看见了什么；
全跑那支把同一问挪到 [1/6] **之后** —— 从零打一发时那份产物本来就该由 [1/6] 造出来，
提前问等于把唯一一条重打包的路堵在门外（10-01 第十七包就是这么被拦下第一次运行的）。

**②′ 是第二份独立产物，而且只能在 `.venv-ocr` 的解释器里跑**（10-03 加，随包本地 OCR）：
`scripts/tools/build_ocr_worker.py` 用 PyInstaller 把整套 OCR 栈打成自包含的
`build/ocrworker/ocr-worker/`（本机实测 258 MB，含 onnxruntime/cv2/numpy/PIL），由
`shell/electron-builder.yml` 的 `extraResources` 落到 `resources/ocr-worker/`，运行时那半边
认它的位置只有一处（`base/paths.py` 的 `bundled_ocr_worker()`）。为什么不是"把 `.venv-ocr`
拷进包"：venv 的 `python.exe` 依赖构建机上的 base 解释器，拷过去等于把"只有我这台机器成立"
的前提发给装机的人。两个守卫都在代码里而不是靠人记：`build_ocr_worker.py` 非 `.venv-ocr`
解释器**直接拒绝出产物**（在主 venv 里打会得到一个没有 rapidocr 的空壳），打完还要过一道
**渲染文字 → 认出来**的冒烟（自己画 `HELLO-OCR-2026` 那张图，认不出就删掉产物）；
`install_package.ps1` 的 [5/6] 装完之后要问一次 `/api/services`，OCR 那一格 `available=false`
就 throw 并打出它的 reason —— **`available=true` 本身不算验收**，真传一张图回读文字才算。

**② 吃的是 ① 的产物，而且吃进去就固化了**：`frontend/dist` 是被 **PyInstaller 当数据收进
随包后端**的（`spec` 的 `datas`），所以顺序不是"建议"而是依赖：**改过任何前端文件，② 必须重跑**，
只重跑 ④ 会得到一个"构建成功、里面是旧界面"的包。09-29 那次就这么被抓过一次 —— 文案 C 类改完
只重打了安装包，`install_package.ps1` 的第①道验货当场抛
`installed bundle is NOT the fresh build (asset hash differs)`（`repo=index-gVaxJdei.js`
而装进去那份是 `index-CYjfsZ2n.js`）。**这次拦截本身就是这条规矩存在的理由**：
"构建退出码 0"从来不等于"产物是当前的"，判据只看入口资源哈希（旧包里有同名文件，只有哈希会随构建变）。

**② 的前置是"构建机装过运行时要收的每一族包"**（`R28-34`，2026-09-29 起这条由 spec 把关而不是靠人记）：`packaging/rolecard-backend.spec` 里 `RUNTIME_PACKAGES` 那八条逐一 `find_spec` 过一遍，缺一条就
**拒绝出产物**并打出该跑的那条 pip —— 因为 `collect_submodules()` 对没安装的包返回**空列表且不报错**，
少装一族 = 安静地打出一个缺东西的包，症状要等用户点到界面里那一格才出现。MCP 那两条
（`langchain-mcp-adapters` + `mcp`，实测合计 1.87 MB）就是这么被漏掉半年多的：
```
.venv\Scripts\python.exe -m pip install -r requirements-package.txt
```
**就这一条**（10-01 改的：这里从前手抄了一份"运行时五族 + 打包器"的长命令，而它**少了
`-api/-rag/-cloud`** —— 照着它装完 uvicorn/chromadb 仍然缺席，spec 第二次拒绝出产物，
"照着提示修"修不好。`requirements-package.txt` 自己 `-r` 引那五份，所以事实只有一处。）
**打一发包的前置现在写在 `requirements-package.txt`**（`R28-32`）：PyInstaller 从前没进
**任何** requirements 文件，只在某台开发机的 `.venv` 里装着（本机 09-29 实测 6.22.3）——
于是 fresh clone 的机器根本装不出打包环境，"打一包"这件事除了那台机器无处可复现。
它单独一份而不并进 `requirements-dev.txt`，是因为 dev 每条 CI job 都装，而打包只有打包机要
（与 `-ocr` / `-mcp` 同一分类口径，由 `check_consistency.py` 的 **requirements 分类** 那条把关：
磁盘上每多一份 `requirements*.txt`，要么进运行时四族，要么在这里署名写明"谁装、为什么分开装"）。

**打包机的解释器布局是一条硬前置**（10-02 实测踩出来的）：PyInstaller 假设原生运行时件
就摆在解释器旁边（`DLLs\`），而 **conda 布局把整批件放在 `Library\bin`、`DLLs\` 里一个 DLL
都没有** —— 于是 `ffi.dll` / `sqlite3.dll` / `libbz2` / `libexpat` / `liblzma` / `libmpdec-4` /
`libxml2` / `zlib` 这一族**静默漏收**：构建退出码 0，探针 ①② 两层全绿，③ 起包内 exe 时炸
`ImportError: DLL load failed while importing _ctypes`；手补那一个 DLL 只是往后推一层，立刻
撞 `_sqlite3`。用 uv 装的 standalone CPython（或 python.org 安装包）就没这问题，本仓库现在的
`.venv` 就是绑在它上面。判据形状：数一下 `_internal` 里各 `.pyd` 引用到、却没被收进来的 DLL；
或直接看候选解释器的 `DLLs\*.dll` 个数（conda=0）。**所以打完一包必须跑
`scripts/forensics/probe_package_artifact.py`** —— 它的第 ③ 层会真起包内那个 exe 问 `/api/health` 的
`build.sha`，这是装之前唯一一条能抓到"冻结件缺原生库"的判据；"构建成功"在这条链上从来不等于
产物可用（与 spec 里 `RUNTIME_PACKAGES` 那条护栏同族，`collect_submodules` 对没装的包返回空
列表且不报错，是同一件事的另一种写法）。

CI 上有一条**只在手动触发时跑**的 `发布链` job（`ci.yml` → `windows-release`，勾 `build_windows`）：
它串起 ①（用入库的 dist，判据由 `frontend` job 的 `check_dist_sync.py` 把着）→ ② build_sidecar
→ 事后尺子 `check_bundle_parity.py` → **随包后端起一次答 `/api/health`** → ④ electron-builder
→ 产物体积读数 + artifact。它替代的是那句"随包后端质量只靠台账"：本机打一发约两小时，
没人会每改一次打一次，于是过去每一发包都只有人在群里说"我装过了"。
**它不装进 runner**：第 ⑤ 步（`install_package.ps1` 的实装 + 两路验货 + 起壳窗）仍然只在本机跑，
因为那要看真窗体。Windows runner 的分钟按 Linux 的 2× 计费，所以这条不参与"CI 绿不绿"。

**版本线只有一条**（10-01 由两条合并成一条；合并那段原话按纪律留在下面，不删）：
`pyproject.toml` = `api/main.py` 的 `API_VERSION` = `shell/package.json` = `frontend/package.json`，
现在都是 **0.3.0**。安装包文件名与"下载桌面壳"那张卡读 `shell/package.json`，
`/api/health` 与 OpenAPI 读 `API_VERSION` —— 从这一版起这两个号是同一个数，
"屏幕上的应用是哪一版"只剩一个答案。
> **合并之前它确实是两条**（后端 0.3.0 / 桌面 0.1.0），当时的理由是"只改壳的那次发布后端一字
> 没动"。10-01 把它合并了，触发点很实在：同一轮取证里那行 `py=0.3.0 api=0.3.0 shell=0.1.0
> frontend=0.1.0` **第三次**被当成缺陷报上来 —— 一行需要先知道"这是两件事"才看得懂的输出，
> 本身就是一处反复产生误判的事实面。**合并的代价如实记**：以后只改壳（托盘、窗口行为）也要
> 推后端那一格版本号，于是 `/api/health` 里的号不再是"后端代码换没换"的信号 —— 那一问现在由
> 构建指纹 `build.sha` 回答（`R28-56`），它本来就该由它回答，不需要版本线替它说话。

打完包还有一道事后尺子：`.venv\Scripts\python.exe scripts\check_bundle_parity.py`
（包不存在时它跳过而不是假红）。它拿 AST 扫 `src/` 的第三方 import（**含函数体内的
lazy import** —— MCP 那句正是写在函数里的那一行），逐个去问已打好的包（PYZ 的 TOC ∪ `_internal/`
下的目录与 `.pyd`）。"刻意不进包"的例外要在 `NOT_BUNDLED_BY_DESIGN` 里**署名写理由**，空理由照样红。
它同时挂在 full 门禁与那条发布链 job 上 —— 前者防"改了三处漏一处"，后者防"打包机根本没人跑过它"。

**换过 / 搬过数据根之后，先拿纯度尺子照一遍新根**：`.venv\Scripts\python.exe scripts\check_root_purity.py`
（默认照安装根，`--root` 指别的）。为什么这是一步而不是一条注意事项：09-24 把日常根从仓库 `data/`
切到安装目录时，旧根里的**测试痕迹跟着升级成了生产数据**（`R28-49`）—— 真库 chroma 里 8 条夹具向量，
内容全是同一组假血糖数，检索会把它当用户事实喂给模型，而台账里连行都没有。这把尺子全程只读，
红只给"确证的负面"（占位哈希 / 已知夹具名 / 跨根路径），正文里出现夹具原句只 warn。
**桌宠素材有两处，别放错**：仓库自绘的那几套在 `frontend/public/pets/<包>/`（入库、随包发，改风格跑 `.venv-ocr\Scripts\python.exe scripts\make_pet_sheet.py --all`，它会连 `pack.json` 一起生成）；**你自己的模型/图集放 `<数据根>\pets\<包>\`**（Windows 是 `%LOCALAPPDATA%\rolecard-agent\pets\`）—— 那里不入库、不进安装包、升级整目录替换也碰不到它，同名还能盖掉出厂那份。一个包 = 一张 `sprite.png`（8×9、单格 192×208）+ 可选一份 `pack.json`（`label` / `kind` / `rows`）。**要用 Live2D 模型还差一步**：把 Cubism Core `live2dcubismcore.min.js` 放进 `<数据根>\pets\_runtime\`（Live2D 官方 CDN 上那份，条款要自己接受；我们**不随包分发**它）。没有它，`kind: "live2d"` 的包不会出现在下拉里，而 `/api/pets` 会回一句"缺 Cubism Core 运行时：把 … 放进 …"。`data/pets/*` 与安装根那一份都在 `.gitignore` 里 —— 用户素材与带条款的运行时都不该进仓库，一次 `git add -A` 就把它带出去是这格最容易犯的错。它同时是 `scripts\install_package.ps1` 的**第 [6/6] 步**（对着安装根跑，**报红不挡安装** ——
为一件不影响本次安装成败的事，把已经装好的应用再关一次只会逼人再去点一次「完成」）；
两臂都验过：清完的安装根 0 红 exit=0，仓库旧根 8 红而脚本照常走到最后一行。

**Live2D 那一类的三条形状规矩**（09-30 第一次放真模型时总结；官方 zip 的形状与我们的扫描对不上是常态）：
① `pack.json` 里的 `kind: "live2d"` **必须写** —— 不写就按序列帧判，症状是"放了模型却没进取选项"，
而 `/api/pets` 的 `skipped` 会老实回一句"缺入口文件 sprite.png"（那句看着误导，但它说的确实是扫描器那一层的判据）；
② 包目录 = **直接躺着 `*.model3.json` 的那一层**，扫描不递归（官方样例常把它埋在 `xxx\runtime\` 或 `models\` 下面）；
③ `motions` 的右边是模型自己的动作组名，去 `model3.json` 的 `FileReferences.Motions` 的键里抄
（官方样例普遍是 `Idle` 加 `Tap` / `Tap@Body` / `Flick*`）。另外两件事当晚实测过：库在"当前没有动作在播"时
自己随机播 `Idle` 组，所以开场就是活的、不必我们补播；名字里带 **video version** 的那几个样例动作是 `.webm`，今天画不了。

**随包那一份 Live2D 素材是官方免费样本「桃濑日和 FREE」**（`frontend/public/pets/hiyori/`，3.1 MB，
`dist` 里那份是它的构建产物 ⇒ 仓库里两份二进制）。条款原文抄在**同目录的 `CREDITS.txt`** 里，随素材一起走：
个人与小规模企业可在同意协议下商用，**中/大规模企业只能非公开内部试用**，且作品**必须署名**
（"本作品使用了株式会社 Live2D 的著作物样本数据"）。**Cubism Core 仍然不随包**（那是另一份 SDK 条款），
所以别人拿到这份包时 `skipped` 会老实回一句"缺 Cubism Core 运行时：把 … 放进 …" —— 随包素材买到的只是
"开箱就知道有 Live2D 这一档"，不是"开箱就能画"。要换掉或去掉它：删这个目录 + `git rm -r frontend/dist/pets/hiyori`，
用户外挂根那份不受影响。

**打了包但还没装的那段时间**（用户选「攒着一起打」时天天都是这个状态），拿
`.venv\Scripts\python.exe scripts\probe_package_artifact.py` 自证：**三层各打各的** ——
① 包内 dist 与仓库 dist 逐文件 sha256 全等（期望入口从 `dist/index.html` 现派生）、
② 包内 `rolecard-backend.exe` == 刚构建那份 sidecar、③ 起包内那个 exe 问 `/api/health` 里的
**`build.sha`：这一包自报"我是从哪个 commit 打的"，直接与仓库 HEAD 比**。

**③ 才是"装的是哪一版"这句话的答案**，①②比的都只是"字节一样"。10-01 实测过这个差别：
最近那一笔是纯后端改动，① 里唯一对不上的文件是 `pets/hiyori/pack.json`（界面哈希一字没动），
而 ② 需要"刚构建的那份"当尺子 —— 尺子不在就比不了。所以 ② 在缺尺子时**从"跳过并算通过"
改成了红**（旧写法 `return True`，于是"三层全绿"可以在中间一层根本没跑的情况下打印出来，
而这句话的全部意义就是三层都跑了）。

指纹从哪来：`scripts/build_sidecar.py` 在打包前把 `git rev-parse HEAD` 与脏旗写进
`build/build_info.json`，`packaging/rolecard-backend.spec` 把它收进 `_internal/` 根 ——
**缺这个文件 spec 直接拒绝出产物**（实测退出码 1），所以"绕过 build_sidecar 直接 pyinstaller"
这条路现在打不出东西。冻结态读烤进去的那份；开发态现取 HEAD 并带 dirty 旗（一个进程算一次，
`/api/health` 会被壳轮询）。两种情况判红而不是跳过：**`dirty=true`**（打这一包的时候**进包的那些
路径**还没提交，"装的就是 HEAD"本来就不成立，先提交再重打）与**指纹缺失**（老包不知道自己是谁 ——
空串比空串会"相等"，所以读不到一律回 `unknown`，见 `core/build_info.py` 那段）。

> `dirty` 这一问**带 pathspec**，只问 `BUNDLED_INPUT_PATHS`（`src` / `packaging` / `frontend/dist` /
> `pyproject.toml` / 六份 requirements）—— 这是 10-01 第十七包换来的（台账 `R28-66`）：那一次
> 烤出来的旗是 `dirty=true`，而脏的只有 `scripts/install_package.ps1`，它根本不在 PYZ 里。
> **"这一包是不是这个 commit"与"这台机器上还有别处在改吗"是两个问题**，前者才归这一格管。
> 开发态那一支**仍然问整棵树** —— `--reload` 跟的就是工作树本身，那里问宽是对的。
> **镜像里没有 `git`**（`python:3.13-slim` 不带，`.dockerignore` 也不带 `.git`），所以容器里这一格
> 老实回答 `sha=unknown`、`dirty=null`；`_git` 接住 `OSError`/超时而不是让它穿出 ASGI ——
> 10-01 就是让它穿了：`/api/health` 500 ⇒ `HEALTHCHECK` 永远不通过 ⇒ 编排器眼里"活着但没就绪"，
> 而本机 45 条一致性与两档门禁全绿都看不见这件事（台账 `R28-70`，只有 CI 的镜像那一臂看得见）。

**装完之后还有一步"看一眼"**：`node scripts/js/render_shots.js --base http://127.0.0.1:<自起的端口>`
把"给人看的那几格"在真 Chrome 里截成 PNG（`build/shots/`）—— 配色、换行、有没有重影这类判断
只有看图才作数，而 in-app browser 没有可见表面（`visibilityState=hidden`）截不到，所以取景走
本机 Chrome + `playwright-core`（与 `ui_smoke.js` 同一套装载方式，缺依赖打印跳过不算失败）。
**它要先有一个隔离实例**：副本库 + 自抢端口，别拿用户的 :8000 当取景对象（规矩见
`scripts/forensics/probe_cross_window_sync.py` 那一段）。

`ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` 对 ③④ 同样要设（builder 自己会去
下 electron 的 zip）。国内还要 `ELECTRON_BUILDER_BINARIES_MIRROR`（nsis / winCodeSign）。

**装到本机走 `scripts/install_package.ps1`，别在 git-bash 里手敲安装包**：

```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\install_package.ps1
    -SkipBuild   只装 shell/release 里现成的那份（三段都跑过了就用它）
    -NoLaunch    装完不启动
```

—— 抄一次就漂一次。**现在散文里一格都不抄**：README 首屏不出现头条数字、只给读数文件链接，

### 静默安装（⑤）：命令只有一条能用，别的都会**卡住等人点鼠标**

```
powershell -NoProfile -Command "Start-Process -FilePath '<包路径>' -ArgumentList '/S' -Wait -PassThru"
```

- **别在 git-bash 里直接 `./包.exe /S`**：MSYS 会把 `/S` 当成 POSIX 路径转换掉，NSIS 收到的
  是一个不认识的参数 ⇒ 它不报错，而是**弹出安装向导等人手点**。表现是"命令还在后台跑、
  目标目录一直是空的"，看着像装得很慢，其实是在等人 —— 判据：`Get-Process` 里那个进程的
  `MainWindowTitle` 是"rolecard-agent 安装"。
- `oneClick: false`（要能选目录）不影响 `/S` 生效，前提是参数真的传到。
- 装完的正确验收**不是**退出码：起 `rolecard-agent.exe` → `/api/health` 200 →
  `/` 里的 bundle 名与 `frontend/dist/index.html` 一致 → 抽一条**当期新增的路由**打一下
  （例如 `POST /api/session/ghost/distill` 要回"对话不存在"而不是 405/未匹配）。
  2026-09-21 装动态跑过：per-user 目录 593 MB、`resources/rolecard-backend/` 在包里、
  桌面快捷方式建了、控制台加载的是当前 dist。
- 卸载：`%LOCALAPPDATA%\Programs\rolecard-agent\Uninstall rolecard-agent.exe /S`。
  **卸载故意不动用户数据**（`%LOCALAPPDATA%\rolecard-agent` 的 sqlite/chroma/uploads、
  `%APPDATA%\rolecard-agent` 的窗口状态与 `backend.log`）—— 卸一个软件不该顺手销毁别人的
  对话、知识库和体检记录，那是要用户自己决定的事。
- **别在 dev 服务还开着的时候拿装好的那份做验证**：`Backend.ensure()` 是"端口有人应就**直接连**"
  （设计如此，防重复起后端），所以装完的壳会安静地连上仓库那个 dev 后端，随包 exe 根本不会被 spawn
  —— 看着"界面正常"，测的却不是安装包（实测：`backend.log` 时间戳没动、进程表里没有
  `rolecard-backend`）。要么先停 dev 服务，要么给壳设 `ROLECARD_API_PORT` 换一个端口再判。
- **同一件事的第二层坑：换后端=换库**。上面那条只说到"测的不是安装包"，更要紧的是**两份数据**
  —— 随包 exe 读 `%LOCALAPPDATA%\rolecard-agent`，dev 读仓库 `data/`（见下一节）。所以在两者之间
  来回"重启一下"，界面会突然少掉角色卡与历史，看着像把它删了（2026-09-24 实测：用户问
  "我的爱莉希雅的角色卡咋没有了，你删了？"，而两份库都在、一个字节没少）。
  判据两条：`:8000` 那个 PID 的 `ExecutablePath`，以及**当前** `role_card` 表里有哪几张卡。
  **这两条从 10-01 起不再只写在文档里**：`install_package.ps1` 的第 [5/6] 步自己会问"谁在答"
  —— 端口按壳的口径取（`ROLECARD_API_PORT`，默认 8000，不再写死），拿到监听者的

  （`refusing to print OK`）。以前这一步只问"有没有 200"，于是 dev 占着 8000 时它会替

落盘日志，那条保证根本无法验证。

所以"用户没看到 toast"从此不是一句猜。开发态与打包态都写同一个 userData 目录

### 进程归属：两层各自实测过谁在兜（2026-09-20，打包态）

- **随包 exe + 真父进程死亡**（绕开壳单独测）：父 `os._exit` 后 ≤10 秒后端自己走，日志里
  确实出现 `[parent-watch] 父进程 NNN 已退出` —— 这一层是**我们的**，且**在冻结态成立**。
- **强杀打包壳主进程**（`taskkill /F` 不带 `/T`）：后端 4 秒内消失、端口释放，但
  `backend.log` 里**没有**那一行 —— 先动手的是 Electron 对子进程的管理（另外：壳一死，
  管道里没落盘的日志也会一起丢）。
- 结论：开发态与打包态都是"Electron 那层通常先兜住，我们那层是第二道且被单独证明过"。
  非 Electron 壳（或壳被整树 `taskkill /T /F`）时只剩我们那层，所以它不能删。

**要验壳的起停，又绝不碰用户正在用的那个服务**：给它一个空端口，且**两个 env 必须一起设**——
`ROLECARD_OLLAMA_URL=http://127.0.0.1:11534` 决定壳"要不要再起一个"的判据，`OLLAMA_HOST=127.0.0.1:11534`
决定子进程真的绑哪个端口；只设前一个就是"探着空端口却去抢 11434"。判据：`/api/version` 在新端口
答得出来、老端口全程 200、`stop()` 之后新端口释放。（2026-09-20 就是这么实测起停的。）

## 提交

- **Conventional Commits**：`feat` / `fix` / `docs` / `test` / `refactor` / `chore`（scope 可选，如 `feat(reachout):`）。
- 一个可 bisect 的提交只做一件事：功能与它自己的测试/文档回写同提交；纯工具/环境修复独立提交。
