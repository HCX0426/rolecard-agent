## 0. 现在有什么（避免重复造）

| 能力 | 现状 | 缺口 |
|---|---|---|
| 主动消息列表 | 收件箱一行一条（`GET /api/reachouts`），红点=未读数；桌宠气泡只显示最新一条、其余折成 `+N` | **列表不分天**：一天开口 5 次就是 5 行，历史一多就糊成流水账 |

## 1. 收件箱按「角色 × 时间桶」折叠 + 角标

**决策点 A：合并窗口放 1/3/7 天三档，不做连续滑块。**

- 分组键 = `(role_id, 本地日期桶)`；桶宽由新配置 `REACHOUT_MERGE_DAYS`（默认 1）决定。
- 一行显示成：`角色名 · 今天/日期区间` + **该角色在该桶内最新一条的摘要** + 右上角**未读数角标**；
  展开后是该桶内的逐条（时间 + 内容），点任意一条都进同一个主动会话，并把**整摞**标已读
  （复用已有的 `read-by-role`，不新增端点）。
- 桌宠气泡不变（已经只显示最新 + `+N`）。

**实现位置刻意选在前端**：分组纯展示，`created_at` 已经在响应里 → **后端零改动**，只多一个配置项。
理由：把折叠做进后端会立刻产生"第二份分组逻辑"（前端展示与接口聚合各算一遍），
而这条规则唯一的服务对象就是界面。

- `REACHOUT_MERGE_DAYS` 进 `RUNTIME_FIELDS`：五处契约同步（Settings / from_env / FieldSpec /
  运行环境分组 / `.env.example`），可写入口单一放在「记忆与任务目录」帖（与主动开口总闸同帖），
  运行环境页只读展示 —— 沿用批次 5 已经定的那套口径。
- 顺手把 `REACHOUT_INTERVAL_MINUTES` 也纳入运行环境页（现在只能改 env，排查时不能把间隔调小复现）。

## 2. 主动消息「提取精华」进记忆

**决策点 B：触发选「会话结束 + 每 N 轮兜底」，不做 per-message；并给一个手动按钮。**

市面做法高度一致（SillyTavern 每 N 条滚动摘要、ChatGPT/Claude 后台 reflection、星野「事件簿」事件级摘要）。
per-message 提取被明确回避：一次提取=一次模型调用，本地 8GB 卡上按消息数放大就是不可用的成本。

- 触发：① 会话内累计满 N 轮（**默认 5**，`config.py:185`；原设计写 12，2026-09-22 按实测降到 5
  ——12 轮在真实 Usage 下几乎不触发，等于"从不提取"。本节这句话曾长期与代码相反，
  `.env.example` 也跟着留了 12，2026-09-25 才对齐，见 R26-10）；② 手动「提取精华」
  （对话页一个按钮，走同一条路）；③ **不**做定时全库夜间整理（见 §4）。
- 产物是**条目**而不是整段重写：每条一句话事实，带来源（`proactive` / `chat` / `manual`）。
- 提取用的模型走该角色当前后端；失败只留日志，绝不影响对话与开口。
- 成本可见化：提取那一次调用的 token 数写进审计，让"记忆变聪明花多少钱"是可查的。

## 2.5 主动开口时到底注入了什么（2026-09-20 实测，这一节是回答"注入的内容合适吗"）

`generate_reachout_text`（`core/reachout.py:282-321`）的 prompt 只有两条消息：

| 进了 prompt 的 | 没进的 |
|---|---|
| 人设（实测 elysia 359 字）+ 范例 3 条 + `memory_for_turn` 取到的记忆 + 三种口吻之一的任务指令；然后单轮 `invoke` → guard → 截 2000 字 | **任何"最近性"**：不看该角色的主动会话历史，也不看它自己上次主动说过什么；不看时间之外的上下文 |

实测出的三个问题（都有数据支撑，不是推测）：

1. **记忆槽是空的**：`role_memory` 只有 `general_assistant`（长度 0），elysia 没有行；全局 `memory:facts` 那行压根不存在。
   于是任务指令"结合关于用户的长期记忆"指向一个空串 —— 模型只能凭人设编，这正与
   「人设只解读不捏造」那条不变式对冲。（这条不是 bug 而是数据现状，但指令该诚实：
   **记忆为空时不再说"结合长期记忆"**，改成"凭你对他的了解自然说一句"。）
2. **重复开口**：今天 09:00 / 10:00 / 11:00 / 12:00 四条几乎同义（花海、阳光、亮晶晶）。原因不是模型差，
   是上下文里没有"我刚说过这些"。
   → **E1 注入该角色最近 K 条主动消息原文**（默认 5，一行 SQL），并明写"这些你最近说过，
   别重复同样的话和同样的由头"。零额外调用，多 200–400 token。
3. **recall 档有口无食**：`trigger_recall` 只回答"这角色有没有专属记忆"，命中就要求模型
   "提起一件之前聊过或答应的事" —— 但**没把是哪件事给它**，结构上就在邀请它编一个具体细节。
   对比 `file_event` 档就做对了：给文件名清单 + 明写"不得编造文件内容"。
   → **E2 recall 改成带素材**：从条目化后的 active 记忆里挑一条当由头，明写"只说这一条，
   不要补别的细节"；**挑不出素材就不要走 recall 档**（现在是"有 blob 就走"）。
   这也是 §2/§3 那条"记忆条目化"真正的落点 —— 条目不是为了好看，是为了能被引用与被去重。

> 顺带要改的文档口径：架构总览 §3 写着"角色也记得自己主动说过什么" —— 那一句只对
> **下一次对话**成立（消息落进了主动会话），对**下一次主动开口**不成立。两条路不对称，
> 做完 E1 才真正两边都成立。

## 3. 记忆的退役机制（你点名要的那块）

**决策点 C：失效不删 + 近因加权 + 条数上限，参数一律不暴露到界面。**

调研结论很一致：**没有一家在 UI 上暴露衰减参数**，但都暴露"逐条查看/编辑/删除/钉住"
（ChatGPT、Claude、星野事件簿都是这个形态）；工程侧的成熟做法是**标记失效而非物理删除**
（Zep/Graphiti 的 `valid_at/invalid_at`、Mem0 的 decay + `expiration_date`），因为可撤销、可调试。

落到我们这里，最小形态是给 `role_memory` 换成一张条目表（保留 blob 作为"渲染视图"，注入规则不变）：

| 列 | 作用 |
|---|---|
| `text` | 一条事实（一句话） |
| `source` | `proactive` / `chat` / `manual` / `seed` |
| `pinned` | 钉住 = 不参与淘汰，也不被覆盖 |
| `hit_count` / `last_hit_at` | 被注入过就记一次（近因与频次的依据，一行 SQL 的乘子） |
| `invalidated_at` / `superseded_by` | 失效不删；被更新的事实指向新版 |
| `created_at` | 排序与桶计算 |

- **淘汰前先整理**（用户 2026-09-20 指出"超上限不该直接删，先看能不能合并"，是对的）：
  触到 active 上限时**先跑一次整理（consolidation）**，而不是立刻失效最弱的那条：
  1. 让模型对这摞条目做一次 `MERGE / KEEP / INVALID` 判定（同义的多条合成一条、被新事实
     取代的转 `invalidated_at` 并写 `superseded_by`）；
  2. **整理后仍超限**才按 近因×频次 从最弱的开始转 `invalidated_at`；
  3. 整理只在超过阈值时跑（不是每次写入），且**可手动触发**（记忆卡上一个「整理记忆」按钮）——
     它是一次模型调用，让用户决定什么时候花这个钱；
  4. 整理是**幂等且可回滚**的：只写 `invalidated_at` / `superseded_by`，不物理删任何行，
     所以"整理坏了"最坏是回滚一个标记，而不是丢记忆。
- **注入**：只取 active，按 近因×频次 排序，装进 `MAX_MEMORY_CHARS` 能容的部分。
- **合并写入**：提取新条目时先做 `ADD / UPDATE / NOOP` 三态判定（Mem0 的形状）——
  UPDATE 就是写 `superseded_by`，而不是让两句矛盾的话一起留在库里。
- **隐私出口**：导出/分享角色卡时 **真删**记忆行（只带 pinned+active 且需显式勾选）。
  这条是我们与托管产品的关键差异：他们没有"把另一个人的隐私焊进文件里"的问题，我们有。
- 用户控制：记忆卡从 textarea 换成**逐条列表**（编辑/删除/钉住/「提取精华」/「整理记忆」），
  仍保留"原文视图"折叠展开，便于你直接看注入进去长什么样。

## 4. 明确不做

- 知识图谱 / 实体关系抽取（Graphiti 那套）——单用户本地场景收益不抵复杂度。
- 夜间全库反思重写（Letta sleep-time agent）——一次全库重写就是几百次调用，本地卡上不成立。
- user / agent / run 三层作用域（Mem0）——我们的 per-role 硬隔离已经天然是那个形状。
- LRU 容量淘汰 —— 条数上限比 LRU 可解释，也更好演示。
- ~~"用户没回则抑制下一封"——未读堆积上限已经在做同一件事，不叠加第二套。~~
  **09-26 从"不做"里挪走**：那条上限数的是"红点攒了几条"，而 `mark_all_read` 的口径是用户自己
  拍的"点进对话界面就算都看过"，于是他打开过一次控制台之后它就失效了（实测连发五条、接话 0 条，
  库里 `unread` 始终为 0）。退避改成数"她开口之后他没回过几句"（`_unreplied_streak`，只比时刻），
  封顶仍留 `unread` —— 两条出口各管一件事，见 §8.6 与审计台账 `R26-35`。

>    "它什么时候开始搞错"的那条版本链是审计唯一的证据，也是"整理坏了能回滚"的前提；

> 4. **提取用的模型走这一会话自己在用的那个**（会话覆盖 > 角色覆盖 > 默认）：换到一个更弱的
>    模型上去抽事实，症状是"记忆悄悄变笨了"，而没人会怀疑到提取这一步；
> 5. 成本可见化：模型报了 usage 就把 token 数带进审计与界面提示，**没报就是空**（不编一个数）；
>    审计只记结构与条数，**绝不记提取出来的内容**（那条由单测钉住：审计里搜不到记忆文本）；

## 6. 事件簿：把"和这个角色有关的事"按时间摊开（2026-09-21 提案 → **2026-09-22 界面已落地**）

**动机**：§2/§3 做完之后，系统里第一次同时躺着三类带时间的东西 —— 它主动找过你什么
（`agent_reachout`）、它哪天记下/更正了关于你的哪条事实（`role_memory_item`）、你们什么时候
开过哪些会话（`session_thread`）。它们各自都有界面（收件箱 / 记忆卡 / 会话列表），但**没有一处
能按时间把三条并起来看**，而"我记得它知道我搬过家"这种感受恰恰是时间线给的。星野的「事件簿」
是同一个诉求，只是它是托管产品、事件由平台生成。

**核心约束：不新建事件表。** 时间线是这三张已有表的**只读派生视图** —— 新增一张 `event` 表
就是制造第二份事实，而"两处真相"是本轮审计反复在删的东西（backends 投影、`role_memory` blob、
`content`/`items` 同源都属这一族）。

### 6.1 读侧合同

`GET /api/roles/{role_id}/timeline?limit=50&before=<游标>&kinds=reachout,memory,thread`
→ `{ items: [{ kind, at, text, from_text?, thread_id? }], next_cursor }`

| 事件种类 | 来源行 | 显示成 |
|---|---|---|
| `reachout` | `agent_reachout` 一条 | 它主动说：<原文>（可点 → 跳进那条主动会话，复用收件箱的 `onOpenThread`） |
| `memory` | `role_memory_item.created_at` | 记下：<事实> |
| `memory_correct` | 同表的 `invalidated_at` + `superseded_by` | 更正：<新事实>，下面一行划掉旧的那条 |
| `thread` | `session_thread.created_at` / `updated_at` | 开始聊 / 最近聊：<标题>（锚点，**不**逐条列消息） |

- **排序**：`at` 倒序；同一时刻按 `kind` 稳定序，避免翻页时同秒事件跳位。
- **游标**：`(at, kind, 主键)` 三元组编码成一个不透明串（与 `/api/audit` 的 `before_id` 同一目的：
  不靠 `OFFSET` 深分页）。
- **时间口径**：三张表都是 `CURRENT_TIMESTAMP`（UTC），分桶文案直接复用收件箱那套"今天/昨天/日期"
  —— 那里已经踩过一次时区，不重新踩。
- **分级**：`/api/roles` 前缀已在 `USER_ROUTES`，纯读、不写审计（读了什么不该进操作流水）。

### 6.2 界面（角色页每行一个「事件簿」→ 右侧抽屉）

抽屉而不是新页签：它是"关于这个角色"的上下文，离开角色列表就没有归属；形状复用收件箱那个
`Modal variant="drawer"`。

```
┌ 爱莉希雅 · 事件簿                        只看 ▾ ┐
│ 今天                                             │
│  ● 20:14 主动  刚路过琴房，想起你说周三要练琴。 → │
│  ● 18:02 记忆  更正：用户下周搬到杭州居住         │
│              ┄ 用户住在上海（已作废）             │
│ 昨天                                             │
│  ● 21:31 对话  开始聊：腰疼怎么缓解           →   │

│                                    加载更多 ↓     │
└──────────────────────────────────────────────────┘
```

- 左侧一条细竖线 + 圆点，种类用**小徽章**上色（主动=蓝 / 记忆=绿 / 更正=琥珀 / 对话=灰）；
  徽章是说明不是控件 —— 不做点击筛选（筛选只有一个下拉，见下）。
- 「更正」那条把旧文本划掉显示：这是 §3「失效不删」第一次**被用户看见**的地方 —— 之前它只是
  数据库里一列 `invalidated_at`，价值只在回滚与调试里。
- 顶部一个下拉筛选（全部 / 只看它主动说的 / 只看它记下的）：**一个控件而不是四个开关**，
  因为"对话"锚点单独看没有意义。
- 空态写清路径：「还没有关于它的事 —— 聊几句，或在角色卡上让它主动找你」。
  **（09-29 措辞已改为「还没有记录 —— 聊几句，或在角色卡上开启「主动找你」。」——
  那个「它」指的是一张角色卡，不是物件；判据与那一屏要做的事都没变，
  见 `称呼与性别设计稿（2026-09-29）.md` §1 #12。）**
- **只读**：编辑/钉住/删除的唯一写点仍在记忆卡（§3 那条"一个设置只有一个写点"）。

**落地时记的两笔（2026-09-22）**：

- 真机验过：`#/roles` → 爱莉希雅「事件簿」→ 按天分组（今天 / 昨天 / 9月20日）、`主动`与`对话`
  两类锚点、跳转箭头都对；再真发一次 `POST /api/settings/memory/item` 造一条记忆，看它以
  `记下：…` 落进轴里（验完删掉，演示库回到原样）。
- **"更正"那一行没有真数据样本**：用户手动删记忆走的是**物理删**（不留"已删除"的行把隐私
  留在盘上），所以 `invalidated_at` 只能由提取/整理那两条模型路径写出来。这一行由前后端
  用例钉住（含"只作废、没写替代"那一支：说"作废了一条事实"，不编一条"改成了"），
  要看到真的得跑一次 〔整理记忆〕 —— 那是一次真模型调用，没擅自替用户点。

### 6.3 明确不做

- **逐条聊天消息进轴**：按角色扫 checkpoint 既贵（每会话一次全量反序列化）又是把"对话全文"
  复制进另一个视图 —— 那里已经有对话页了。
- **把 `audit_log` 的计数混进来**（"提取了 2 条、整理 1 次"）：没有内容的计数在"我和它的故事"
  里是噪音；那些数字属于记忆卡的成本可见化，不属于这条轴。
- **导出/分享时间线**：§3 那条隐私出口已经定了规矩（导出角色卡只带 pinned+active 且要显式勾选），
  时间线把 per-role 记忆与主动消息原文摊在一起，导出它等于绕开那条规矩。

### 6.4 代价（诚实）

- 记忆条目的 `created_at` 是**被记下的时间**，不是事情发生的时间。所以轴上的措辞只能是
  "它哪天记下/更正了什么" —— 写成"你搬来杭州"就是骗人。这条约束决定了上面那张表的动词。
- 三类源没有共同主键，跨源游标必须自己编码；分页边界（同秒多条）要一条用例钉住。
- 工作量：后端一个只读聚合端点 + 一个抽屉组件 + 两端用例。不动任何写路径。

## 7. 桌宠悬停对话：不进控制台就能回话（2026-09-21 提案 → **已落地 ①②③**）

> **⚠️ 读之前先看这条（2026-09-25）**：本节是 09-21/22 的设计与实测记录，里面所有关于
> **窗口尺寸**的数字与结论（219×259、203×243、"悬停时向壳要一次 `setBounds` 长大"、
> "展开态是 380×520 那块"）**都已被取代**：桌宠窗现在是一张**永远 560×520 的透明画布**，
> 200×240 只是画布下沿居中那块**锚点**（色片），展开只往页面推一个 `shell:pet-panel-shift`。
> 为什么非改不可、以及它换掉了哪三条旧前提，见架构审计 **§12.13**（重影的载体是"变尺寸"本身）
> 与 **§12.14**（展开"左移一下"、点远处误开面板）。
> 本节其余部分（为什么一扇窗不加第三扇、手动拖为什么取代 CSS drag、趴边的几何、
> 位置记忆存锚点不存画布）**仍然成立**，逐条读时按上面这条打折。

**诉求**（用户原话）：鼠标悬停时把历史消息和输入框弹在桌宠旁边，"这样不用进界面都能对话"。
现在的形状是：桌宠 219×259、只有一张色片 + 一条会淡出的气泡，点气泡 = 让壳把**控制台**拉到前台
—— 想回一句话得开一扇大窗，这跟"抬眼就能看到"的驻留件定位是拧着的。

### 7.1 参考项目对照（2026-09-21 查的，四条直接影响判断）

| 项目 | 它怎么做 | 我们取什么 |
|---|---|---|
| **Cherry Studio**（Electron，开源）划词助手 / 浮动窗 | 一条浮动条 + 点按钮开各自的结果面板；设置项是**自动关闭 / 自动置顶 / 透明度 / 紧凑模式 / 记住大小**；它是**独立工具**，不跟主聊天共享上下文；"点了下面屏幕区域就自动隐藏" | 那套**设置词汇**照搬（用户认得）；"独立工具"正是"和控制台互不干扰"的现成先例 |
| **Open-LLM-VTuber**（Electron + Live2D）桌宠模式 | 透明 + 全局置顶 + **鼠标穿透**；但**输入与历史在网页 UI 那一侧**，overlay 只画角色和气泡 | 反面参照：它没有"悬停就能打字"，我们要的正是这一步 |
| Electron 悬浮球实现（掘金 7460779695833333811） | 展开/收起**在同一扇窗里用 CSS 做**（不调 `setBounds`、不开第二扇窗）；并明确说 `-webkit-app-region: drag` 与点击事件冲突，所以他们改成 JS 手动拖 + IPC 定位 | **它那句"drag 与点击冲突"我们实测复现了**：整块根节点是 drag 区时色片上的 `mouseenter` 一次都收不到 ⇒ 采纳它的"手动拖 + 只把增量交给壳"（见 §7.4），CSS 展开/收起那半条没采纳（我们要收起态是小窗、展开态才长大） |
| AI 桌宠实战（CSDN 95244841） | 点出这个坑：**"透明区域虽然看起来透明，但鼠标交互范围仍然是一整块矩形，容易挡住用户点击其他程序"**，作者的做法是**把窗口尺寸贴合成角色大小** | 我们现在 219×259 就是贴合的形状 ⇒ **收起态不挡桌面**这条必须保住 |

⇒ 结论：**收起态维持小窗，悬停时向壳要一次 `setBounds` 长大**。比"常驻大窗 +
`setIgnoreMouseEvents(forward)`"少动一处系统级行为 —— 穿透开关是全局的，哪条路径忘了关回来，
桌宠就再也点不动；而改窗口状态的路径我们已经有三处（托盘显隐、位置记忆、单实例）。

### 7.2 四条要拍板的判断

1. **一扇窗长出来，不加第三扇窗。** 悬停时 219×259 → 约 380×520，面板画在同一份 `frontend/dist`
   里。再加一扇 popover 窗意味着：跟随定位、拖拽同步、失焦隐藏、托盘/退出/单实例每条路径都要
   多管一扇 —— 而"不为壳重写 UI、不在壳里存第二份界面"是里程碑 D 的立身之本。
   **代价要说清**：只在展开期间，那块矩形挡住它下方的桌面点击，鼠标离开即恢复。
2. **桌宠与主动开口共用那一条线（`s_proactive_<role>`），但桌宠永不新建会话。**
   用户 2026-09-21 拍的："桌宠和主动会话应该是一条线的，不然和人交流就会断掉记忆了。"
   "与控制台互不干扰"靠的是**桌宠只 ensure 一条固定线程、控制台的"新建对话"另开随机线程**，
   不是靠把历史劈成两条 —— 详见 §7.2.1，删会话时的边界在 §7.2.2。
   > **2026-09-26 这一条被用户推翻了一半**（"这应该是一起的啊"）：既然一条线程的历史只属于一个
   > 说话人，控制台就不该再有"把角色挂到任意线程上"这种动作。现在的形态是**那个角色的固定线
   > 就是控制台的默认对话**：侧栏「她们」一栏一行一个角色（点一下幂等 ensure），头部的角色菜单
   > 也走同一个 `openLane`；旧的"新建对话"降级改名成**「＋ 开一个临时话题」**，仍然能开——
   > 它是"临时"的，不再冒充某人的一条完整关系。原句里"不靠把历史劈成两条"这半句不但仍然对，
   > 现在是唯一实现方式。桌宠侧代码一行没改：它读的本来就是这条线。
3. **流式复用 `streamChat`；收起不打断正在跑的那一轮。** 面板用对话页同一套 SSE 归约
   （`lib/stream.ts`），不写第二份。鼠标离开自动收起时**不 abort** —— "我话刚问完它还没答，
   挪开鼠标就没了"是不可接受的；只有面板里那个「停止」按钮才 abort。
4. **给三个开关**（词汇照 Cherry Studio）：自动置顶 / 透明度 / **显示消息内容**（默认开）。
   最后一条的理由不是省屏幕：桌宠常驻置顶、透明、不跟主窗一起收起，别人站在你屏幕后面就能
   读到你们聊了什么。关掉后展开只给"有 N 条新消息" + 输入框。

#### 7.2.1 会话归属：**已定 (a) —— 桌宠与主动开口是同一条线**

三个候选摆出来之后用户拍的（2026-09-21）：

> 桌宠和主动会话应该是一条线的，不然和人交流就会断掉记忆了。

| | 线程 | 结论 |
|---|---|---|
| **(a) 复用主动会话** | `s_proactive_<role>` | **采用**。桌宠上回的就是它主动说的那句，角色下次开口读的历史里就有这一段 —— 一条线不断 |
| (b) 桌宠专属一条 | `s_pet_<role>` | 否决：代价是"两边历史分叉"，而这条线正是产品的命脉（角色该记得你们聊过什么） |
| (c) 每次展开新建一条 | 随机 id | 否决：历史碎成几十条，与"记忆"这条主线相反 |

"和控制台互不干扰"因此**不是靠分叉两条线**实现的，而是靠两条更简单的规矩：
桌宠**永不新建会话**（只 ensure 那一条固定的主动会话），控制台里"新建对话"照旧是
`POST /api/session` 开一条随机线程 —— 两边写的是不同的行，谁也拦不住谁。

**后端要补一个幂等端点**：`POST /api/session/proactive {role_id}` → 确保该角色的主动会话存在并
返回 `thread_id`（照 `bootstrap.deliver_proactive` 里那段 `ON CONFLICT DO NOTHING` 写，
**不跑图、不写消息**）。角色从没主动说过话时桌宠也能先聊起来，就是靠它。

#### 7.2.2 删掉这条会话时，什么跟着走、什么留下（用户 2026-09-21 明确）

> 删掉那个对话时，除了记录到角色记忆的内容，其他都不需要了。

落成一条断言（`tests/test_api.py::test_deleting_a_session_keeps_memory_and_the_inbox_ledger`）：

| 东西 | 删会话之后 | 为什么 |
|---|---|---|
| thread 行 + 它的 checkpoint / writes | **走** | 就是"这条对话本身"，不留可被复活的孤儿 |
| 已提炼进 `role_memory_item` 的事实 | **留** | 那是关于用户的提炼物；删对话不该把"提取精华"白做一遍 |
| `agent_reachout` 那几行（收件箱） | **留**（未读数照旧、红点不谎报） | 它是"它哪天主动找过我"的账，桌宠气泡读这里。会话没了之后这些行**不再有跳转目标**（`thread_id` 回落 None），点一下只标已读 —— 不给死链 |

如果哪天要"删会话连收件箱一起清"，那是另一个动作（清空某角色的主动记录），不该藏在
删除会话这一刀里 —— 一个按钮只毁一样东西。

### 7.4 实测结果（②③ 做完，2026-09-21，全部在这台机器上跑真壳）

| 要验的 | 结果 |
|---|---|
| 悬停能不能展开 | **能，但不是原设计那样**：整块根节点是 `-webkit-app-region: drag`，而**拖拽区会把鼠标事件整个吞掉** —— 色片上的 `mouseenter` 一次都没收到，窗口纹丝不动。把色片改成 no-drag 后立刻展开（203×243 → 380×520）。那篇悬浮球实现说的"drag 与点击冲突"是同一件事，我原先以为我们能共存，实测不能。 |
| 那拖拽怎么办 | 改成**手动拖**：色片自己接 pointer 事件，只把**增量**发给壳（`movePetBy(dx, dy)`），绝对坐标与出屏夹取留在主进程。实测拖 90px 窗口跟着走 90px。用 `screenX/screenY` 而不是 `clientX`：窗口正跟着鼠标走，页面坐标会被一起拖回去，`clientX` 的差值恒为 0。 |
| 锚点 | 色片**下沿与水平中心不动**（1418+101=1519 → 1327+190=1517；下沿 1026 → 1026）。展开只向上和向两侧长，宠物不会"我想点它它跑了"。 |
| 记住的位置 | 存的一直是**收起态**那块矩形（`trackBounds` 的 `persistAs`）：实测拖完展开着退出，`window-state.json` 里仍是 `200×240`。否则下次开机就是一张透明大窗贴在桌面上。 |
| 无边框窗能不能拿焦点 | 点一下就 `isForeground: true`；③ 更进一步实测：`showInactive` 的窗**点进 textarea 就能打字**（输入法/中文原文按 UTF-16 逐字进框，`input` 事件计数在涨），Enter 发出、回答流式落在面板里。所以"平时不抢你键盘、点输入框才抢"这个设计成立，不需要额外的 `win.focus()`。 |
| 面板内容 | 展开后画的是**该角色主动会话**的最近几条（`它：…`）+ 头部「在控制台打开」，工具行不进面板。历史只在展开时读一次，收起不轮询。 |
| ③：在桌宠上说的话落在哪 | 实测（2026-09-21，真壳 + 真本地模型）：面板里敲「刚跑完步，坐下歇会儿。」→ 22 秒后回答落进 `s_proactive_elysia`，`GET /api/session/{tid}/messages` 读得到，控制台的同一条会话也看得到同一句。**没有**新开随机线程，§7.2.1 那条线在真机上闭合。 |

| ③：关掉「显示消息内容」之后 | 真壳实测（写 `pet-prefs.json` 再开机，量 `GetWindowLong` 的 exstyle + 桌面截图）：气泡变成 **「它说了话 · 内容已隐藏」**，展开面板只剩 **「内容已隐藏 —— 在控制台里读，或到托盘勾回「显示消息内容」」** + 角色切换 + 输入框，**历史请求根本不发**（藏起来的东西不该只是不画，还留在页面里等着被看到）。系统 toast 也一并只报角色名 + 「内容已隐藏」。 |

### 7.5 分期与代价

① 后端 ensure 端点 ✅（`ee962dc`）→ ② 展开/收起 + 只读历史 ✅（`6a5726b`）→ ③a 输入框 + 流式（收起不打断）
✅ → ③b 托盘三个开关（自动置顶 / 透明度 / 显示消息内容）✅。
全程不动任何写路径、不动控制台；新增的是桌宠页一个面板、壳三处 IPC（展开 / 拖动增量 / 读旗子）、
托盘三项，两端各带用例。③b 顺带修掉两条只有量窗口样式才能发现的旧账：桌宠的"置顶"此前从未兑现
（要 `"screen-saver"` 档），以及位置记忆每开机走 2px。

**③b 之后又修的一条（用户报的"越拖越宽"）**：`movePetBy` 当时写的是 `setBounds({ ...getBounds(), x, y })`
—— 而 DWM 给无边框透明窗留了一圈不可见边，`getBounds()` 报回的宽高比请求值大（实测请求 200×240、
报回 202×242）。于是**每来一个 pointermove 就把窗口撑大 2px**：一路拖到屏幕边能拖出一条宽带子
（气泡是 `w-full`，跟着窗宽走），而夹取用的 `maxX = 工作区宽 − 窗宽` 也同步变小 ⇒ 色片永远贴不到边。
同一个根因的两个症状，用户都看见了。修法与位置记忆那条一致：**宽高一律用常量**（`petSize()` 按展开态
取），只有 x/y 从窗口现状推。验证：一次 113 步的拖拽之后窗口仍是 `200×240`。

### 7.6 靠边隐藏（趴边）：2026-09-22 拍定，**已落地**（09-24 起几何搬到锚点上算，见 §12.13）

诉求（用户 2026-09-22）："有些桌宠形象靠边会趴在边上，可爱" —— 拖到边缘时只露一小条，鼠标过去再滑出来。

**拍定的三条**：吸**左 / 右 / 下**三条边；露出的目标是**色片本体 48px**；**只在拖到边上那一刻吸进去，
之后不再自动收**（放出来之后就一直摊着，要再藏得再拖一次）。

| 要定的 | 结论 | 为什么 / 代价 |
|---|---|---|
| 露的到底是什么的 48px | **色片的 48px**，不是窗口的 48px。色片 88px 居中在 200px 的窗里，两侧各 56px 是透明的 ⇒ 左右要推出 `56 + (88−48) = 96px`；下边只有 4px 下边距 ⇒ 推出 44px | 提案那版写的是"推出 40px 露 48px"，**算错了**：推 40px 藏的全是透明边，色片一格没少，看上去根本没吸进去。透明区不吃 hover，所以露出的那条必须全是有像素的色片，否则鼠标划过去没反应 |
| 什么时候吸 | **只在 pointerup 那一刻判**（离边 ≤ 24px 才吸） | 拖的过程中不判：一路拖过去会"吸上→拉开→吸上"地抖。也不自动收（用户 2026-09-22 拍的）：一条"它什么时候会自己溜走"的规则要额外解释，收益不值 |
| 怎么出来 | 鼠标进那条窄边 ⇒ 先滑回**贴边但不藏**，再按悬停展开面板 | 面板要 380 宽，藏着一半就没法看；这条不是妥协，是必然 |
| 开关 | 托盘第四项「靠边隐藏」，**默认开** | 只有"拖到边上"一个动作会触发它，不会自己动，所以默认开不构成意外。关掉时如果正藏着，当场滑回贴边位 |
| 存哪 | 藏着哪条边记进 `pet-prefs.json`（`docked: "left"｜"right"｜"bottom"｜null`）；`window-state.json` 里**仍存"贴边但不藏"那块矩形** | 存推出去之后的矩形，下次开机显示器一变（拔掉副屏）就是一扇找不回来的窗 —— 还原时那套"夹回当前工作区"（`initialBounds`）必须还能吃到一个屏内矩形，藏的那一下每次开机按当前工作区重算 |
| 下边那条的风险 | 推出 44px 会压到任务栏那条带（`workArea` 不含任务栏）| 本机实测为准：盖得住就保留"头露在外面"那副样子；盖不住/被裁就下边只做贴边不藏，左右照旧。**不做"看起来支持其实不支持"** |

代价说清：窗口一部分在屏外时，Windows 的窗口列表里它的边界就是屏外的（`skipTaskbar` 本来也不进
Alt+Tab，无影响）；真正要防的是**多显示器与改分辨率**，所以 dock 状态必须在每次开机时按当前工作区
重算一次，而不是把上次的坐标当真。

**落地记录（2026-09-22）**

- 推演时抓到一个真 bug：**拖拽必然带着悬停**（鼠标不在色片上拖不动），松手那一刻窗口是
  380×520 的展开形状 —— 拿它判边、再按它算贴边位，等于把"藏一半"作用在你正在读的面板上。
  改成"松手只记账，**面板收起那一瞬**才吸"（`petDragEnded` + `setPetExpanded(false)`），
  顺带也符合手感：拖过去、移开鼠标，它自己趴到边上。
- 量到的（本机 2560×1600 @150%，工作区右沿 1707）：贴边 `x=1507`、藏进去 `x=1603`（= 1507+96 ✓），
  而 `window-state.json` 里落的是 **1507** 那块 —— 意图（吸哪条边）另存 `pet-prefs.json`，
  每次开机按当前工作区重算，屏外坐标永不进位置档案。
- **补验（2026-09-22 晚，用户回到机器前，真鼠标 + 真截屏）**：三段都通了。
  ① 拖到左沿松手 ⇒ 日志 `桌宠吸边：left`、偏好写入 `docked:"left"`、窗口藏到 `x=-96`；
  ② 桌面截屏确认那一小条**看得见** —— 半个橙色色片贴在左沿、「爱」字还在，就是"趴在边上"那个
  样子（之前那次"只拍到壁纸"是显示器睡了，不是渲染问题，那条怀疑撤回）；
  ③ 点那条 48px 窄边 ⇒ 窗口滑回 `x=0` 并展开，动画中间帧被抓到（291×382、374×510 ⇒ 缓动在跑）。
- **验的过程里又逮到一个我上一轮自己引入的 bug**：加了"展开前记下原位、收起时回原位"之后，
  **整段拖拽被抹掉了** —— 拖的时候面板必然开着，松手后那次收起把窗口按回"展开前的位置"，于是
  宠物弹回原地、判据永远够不到边（正是用户报的"没法把它拉到靠边"）。60 条 `pet-drag` 全都到了壳、
  也没有异常，只有把"记忆位置跟着一起平移"补上才对。教训：**加了"记住原状"的机制，就得让所有改
  状态的路径都去更新它**，否则它就是一份过期的真相。
- 补上一条实现：**滑进滑出而不是瞬移**，并且**带缓动**（ease-out cubic，吸边 280ms / 展开 200ms /
  收起 160ms，16ms 一帧）。第一版给的是 140ms 线性等分，用户反馈"太快、没渐进"—— 缺的就是那条
  "起步快、收尾慢"的曲线，时长倒在其次。三处例外写死：开机恢复不滑（从屏外滑进来会让人以为宠物
  自己跑出去了）、拖的时候不滑（跟手抢那两百多毫秒）、展开时不滑（滑 + 同时长大糊成一次跳动）。

### 8.3 怎么判断"改好了"（这条比上面所有条都重要）

- **论文侧的现成尺子**：PersonaGym 的 PersonaScore = 5 类任务 × 1–5 分档（每档现生成一个示例回答塞进
  rubric），与人评 Spearman 均值 75.1%；**模型尺寸与人格分无关**（LLaMA-2-13b 在"人格一致"上优于
  70b 与 GPT-3.5，GPT-4.1 与 LLaMA-3-8b 同分）⇒ 我们本地 4B 不是死路。CharacterEval 里专门有一维
  **Human-Likeness（反机器味）**；InCharacter 提醒**别用自陈量表**（与角色指令冲突），要改"访谈 + 评审折算"。
- **零成本的那把尺子已经建好了**：`scripts/persona_meter.py`（只读 `mode=ro`，不碰模型；
  加了 `--api` 才去问在跑的后端要回复侧）。它就是 8.1 那几条症状的镜像，不需要评审模型：
  ① 原文/正文**首 6 字去重率**；② **长度标准差**与范围；③ 与最近 5 条的 **4-gram Dice**
  （均值/最大/≥0.85 条数）；④ **动作括号开头比例**；⑤ **记忆条数**。
  **2026-09-23 补了第 6 族（`3ec3ac4`）**：型例比 / 词面复用 / **高频意象**（直接写出她反复念的
  是哪几个字组）—— 它补的正是 8.1 那个"句式全绿、读起来空转"的盲区：elysia 最近 12 条
  逐字复读 0 条、重合最大 0.29，而词面复用 0.26、「今天」「哎呀」「乐土」各 8/12。
  读法上的两条硬规矩：TTR **只在同一个 `--limit` 下横比**（分母变了数就变了）；
  词面用字符二元组近似"词"，所以「土的」这类跨词边界的碎片会混进来。
  **改前基线已入库（见 8.1），此后每一步改完都跑一次同一命令**，用数说话而不是用感觉说话。
  两个已经踩过的坑写进了脚本 docstring：**去重量错位置**（前 6 字落在动作括号里 → 必须剥括号）、
  **侧数错对象**（最难看的复读在回复侧，不在 `agent_reachout` 里）。
- 记忆侧别用 DMR（已饱和：Zep 复现"整段塞"就有 94.4%），要看 LoCoMo 五类 F1 / R@k。

### 8.4 明确不抄

GPT-4 的用法，4B 会全挤在低分区 —— 要就改 3 档或启发式）；CFG 与向量摘要（ST 官方自己标"存疑"，
且向量摘要与 prompt caching 互斥）；让模型自报心情/状态栏进正文（见 8.2 末条）。

### 8.9 P1 第一条：长度纪律（2026-09-22，同一段对话前后各跑一次）

深度注入那条 `VOICE_DEPTH_PROMPT` 加了第 6 条：**一条消息只说一件事，一到三句就收；
别把"共情一句 + 一段道理 + 一句叮嘱"排进同一条里**。同一段 8 轮日常对话、同一个云端模型、
同一套生产代码（在 app.db 副本上跑），前后对照：

| | 改前 | 改后 |
|---|---|---|
| 长度范围 | 161–202 字 | **74–95 字** |
| 长度 σ / **CV** | 12.0 / 0.075 | 6.1 / **0.076** |
| `/distill` 落库的记忆 | 5 条 | **8 条** |
| 动作括号开头 / 逐字复读 | 0% / 0 | 0% / 0 |
| 用户问"你今天过得怎么样" | 不答，转去安慰用户 | **答了**（看花、逗凯文） |

三点值得记下来：

1. **绝对 σ 会骗人**。均值从 ~180 腰斩到 ~85，σ 自然从 12.0 掉到 6.1，看着像"更单调"，
   其实 CV 几乎没动（0.075 → 0.076）。尺子因此补了 `长度变异系数` 一列，读法也改成看 CV。
2. **改短之后记忆反而多提取出 3 条**。合理：她不再把三件事塞进一条长回复，用户下一轮就只
   会针对其中一件说话，事实被逐条摊开，`/distill` 拿到的原料更干净。这条是顺带的收益，
   不是设计出来的 —— 记下来免得下次以为它是必然。
3. **"三段式小作文"不是角色卡的锅**。爱莉希雅的三条范例是 39/79/61 字（均值 ~60），
   比改后的实际输出还短 —— 卡一直是对的，是模型自己"什么都要接住 + 什么都要安慰"。
   所以 §8.2 第 3 条"改范例"那条**不必为长度而做**（它仍然为题材多样性而待办）。

### 8.10 还剩什么（P1 后两条 + 一条等点头）

  现在只有"贴最近 5 条求别重复"这条软约束，而真库里那条 88 字逐字相同的开口就是它没兜住。

  属内容层，**等用户点头才动**（§8.2 第 3 条）。
- 记忆注入 K 降到 5–8 并带时间标签（LoCoMo：top-5 优于 top-50）。**已落地（`0228945`）**。

### 8.11 P1 第二条落地：复读硬约束 + 套话清洗（2026-09-23，阈值全是量的）

一套机制两处用，同一个 `core/anti_repeat.py`、同一把 4-gram 尺子（与 `persona_meter.NGRAM` 同源）：

| 落点 | 做什么 | 关键取舍 |
|---|---|---|
| `nodes._scrub_own_repeats` | 把她历史里**重复的小句**从"送给模型的那份拷贝"里删掉 | 原文一个字不动（守 `trim_history` 那条口径）；拷贝用 `model_copy` 生成，改了一定留 `history_scrubbed` 这条 trace |
| `reachout.generate_reachout_text` | 草稿太像旧话 → 带 avoidance 指令**重生一次** → 两条都过分就**不投递**（`why="repeat"`） | 重生失败（空正文/被 guard 拦）时**保留第一条**，不因为重生的故障吞掉一句能发的话 |

**打分口径换了**：照抄参考实现的 BM25 之后发现 IDF 随语料条数增长 —— 同一次逐字复读在 12 条语料时
52.7，攒到 100 条会翻一倍，写死的阈值必然随着她用久了越收越紧，而症状是"她忽然不主动说话了"。
改成**覆盖率**（草稿的材料里有多大比例是她用过的，近因加权），值域 0~1。实测（真库 elysia 12 条开口）：
逐字复读 **1.000**（语料灌到 400+ 条仍是 1.000）/ 口癖最重一条 0.472 / 其余 ≤0.40。
阈值取 **重生 >0.55、不投递 >0.92**：回看那 12 条 ⇒ 触发重生 **0** 条、吞掉 **0** 条，只有那条逐字复读会被拦。
**这条闸门管不到"口癖"**（0.3~0.7 那一档）—— 那是三条范例同型造成的，属内容层（§8.2 第 3 条）。

**清洗的门槛分两条线，不是一条**：小句 0.75、整条**只允许逐字相同**（1.0）。
两处都是被测试逼出来的，不是推演：
先给整条也用了相似的线（0.85），既有的深度注入用例发现「第一件小事我记下了」vs「第二件小事我记下了」
被整条换成替身 —— 那点差别正是要紧的信息（医疗档案角色就是两次复查只差一个日期那种形状）。
小句侧同理：「指尖轻点裙摆」vs「指尖轻点下巴」= 0.33 必须留，「要好好看着我哦」vs「要好好看着我」= 0.86 该断。
回喂历史在真数据上的读数：那条会话 11 条里改 5 条、整条替换 1 条，剩下的标点与括号一字不动（分段完整覆盖原文是断言）。

**验收判据要更正**：§12.1 原先写"两侧 `复读条` 与 `重合度最大` 都到 0"。后半句做不到 ——
"重合度最大 = 0" 要求与前面每条**零共用 4-gram**，中文里「，今天的」这类一定撞。能达成、也已达成的是
**判为逐字复读条数 = 0**。改文档，不迁就指标。

**真机第一条读数（2026-09-23 12:44，她主动开口一次）**：`reachout_sent` 带出 `score=0.0` 与
`tokens=1144` —— 那一句与她前面 12 条开口零重合，闸门既没误伤也没触发重生（1144 也是 §12.8
那本账的第一条真数：一次主动开口 ≈ 1.1k token，重生一次就是两倍）。
还要攒的是反面样本：真冒出一句逐字复读时它拦不拦得住 —— 离线回放那条 88 字的是 1.000（会拦），
真机得等。落点与完整读数见审计 §12.1 / §12.8。


### 8.12 范例到底要不要：一次三选一的实测（2026-09-23，用户倾向"不需要范例"）

清单 §12.2 挂着的那条 🔒 说"三条范例同型 ⇒ 题材塌"，而 ST 文档的原话是"模型从范例抄风格
与长度，比抄任何别的东西都多"。用户给的判断是"感觉不需要范例吧"——**这句话比我的推断便宜，
但不该直接照做**，所以拿三种条件各跑 5 次真开口量了一遍（只在库的副本上跑，

| 条件（各 5 次） | 型例比 | 词面复用 | 动作括号开头 | 长度 | 反复出现的字组 |
|---|---|---|---|---|---|
| 现状同型 3 条 | 0.94 | 0.08 | **100%** | 53–66 | 指尖 5/5、乐土 4/5、发梢 3/5 |

| 无范例 | 0.89 | 0.14 | **80%** | 63–82 | 水晶 3/5（没有哪个身体部位到 5/5） |

1. **"换三条异构"与"干脆没有"实测等效**（0.89/0.13 vs 0.89/0.14）—— 那就没必要由我来编一套

3. **两种改法都治不了题材塌**：三组都还在念乐土 / 水晶台阶。「乐土」来自**人设 prompt 里的

### 8.14 显著性这一维落地：importance 三档 + 打分改加法（2026-09-24）

§8.5 那条 P2 做完了。形状与两处偏离写在这里，因为它们都会影响下一次的判断：

**改了什么**：`role_memory_item` 加 `importance`（0 随口一提 / 1 常规 / 2 要紧，默认 1），
提取的行协议多一个可选档号（`ADD [2] 用户青霉素过敏`），召回打分从
`近因 × log1p(hits)` 换成**三维各归一后加权相加**：`0.35·近因 + 0.30·频次 + 0.35·显著性`。

**读数**（同一批局面，旧/新各算一遍分数）：

| 局面 | 旧（乘法） | 新（加法） |
|---|---|---|
| 60 天没提、被注入过 3 次的"青霉素过敏" vs 今天随口一句 | 0.402 **vs** 0.693（新闲聊赢） | 0.567 **vs** 0.525（过敏赢） |
| 400 天没提、被命中 30 次的旧条目 | **0.000**（被近因一笔抹掉） | 0.475（仍排得上） |
| 200 天、命中 5000 次的口癖(0 档) vs 200 天、从没被提过的治疗事实(2 档) | 前者靠次数无限赢 | 0.303 **vs** 0.353（要紧的那条赢） |

**两处有意偏离 §8.5 的原写法**（原写法是"min-max 归一"）：

* **各维用固定上限归一，不按桶内 min-max。** 按桶归一会让"新加一条事实"把整桶分数重标一遍 ——
  旧事实只应被新事实**超过**，不该因为别人来了而自己掉分。固定上限（`HIT_CEIL = 24` 次、
  半衰期 30 天、档数 2）之下，一条事实的分数只取决于它自己。
* **`importance` 只升不降**：`add_item` 命中判重时写 `MAX(importance, 新值)`，`MERGE` 继承源条目里
  最高的那档。降档是「整理记忆」或用户做的判断，不该是"同一件事又被提了一次"的副作用。
  钳制集中在 `memory.clamp_importance` 一处（写它的来源有三条：面板、提取模型、工具），
  认不出的值退回 1 而不是 0 —— 把要紧的事误判成随口，代价是它被挤出 prompt。

**当时没做的两件，现在都做了**（2026-09-24 夜）：

* 面板上有了"这条要紧"的三档下拉（次要 / 一般 / 要紧 = `importance` 0/1/2），走
  `PATCH /api/settings/memory/item/{id}` 的 `importance` 字段。写它的入口里 `set_importance` 是
  **唯一允许降级**的那个 —— `add_item` 那条"只升不降"是给模型定的，用户在面板上点"次要"
  就是判断，不该被 `MAX` 挡回去。标签用「要紧」这个词与注入侧的 `【要紧】` 前缀同源：
  界面标的档与模型看到的标记必须是同一个词。
* 采样惩罚上了界面（设计稿 §8.2 那条欠账）：对话页模型菜单「采样 ▾」三栏，
  **默认全部 null = 一个都不传**。见审计 §12.14 与 `core/graph.py::_init_model` 的注释。
  注入侧对 2 档条目加 `【要紧】` 前缀这条不变（只加在注入侧 —— 面板那段文本会被整行覆写回

### 8.15 「打断语义」这条 P3 的前提被实测推翻（2026-09-24）

原判断（照 Open-LLM-VTuber 的形态推的）：用户点「停止生成」后，她那半句只存在于浏览器里，
**服务端历史里没有** ⇒ 用户说"继续"时她不知道说到哪儿。

**真机读数不支持这个前提。** 在库副本上起一个隔离实例（8100），走完整生产链路
（`/api/chat` SSE → `run_turn` → 同步 `SqliteSaver`），客户端只读第一帧就断开：

| 场景 | 客户端收到 | 服务端最终历史 |
|---|---|---|
| 短回答（默认云端模型） | 9 字 | **整段已提交**（末条是 assistant，长度远超 9 字） |
| 600 字长文 | 1–2 字 | **831 字全文**，且在断开后约 40 s 才落库 |
| 独立探针（慢生成 + 大帧，无模型参与） | 第一帧即走 | 生成器 `finally` 在 **0.3 s** 就跑了 |

也就是说：真实链路上"停止"没有打断任何事——**节点照样跑到提交**。探针证明取消机制本身是通的
（Starlette/anyio 在 0.3 s 就把 `finally` 送到了），所以问题不在"没人收尾"，而在
**收尾拦不住那次已在线程池里跑起来的模型调用**（同步生成器被 cancel 的 `await` 不会中断
线程池里在飞的那一次 `next()`）。

我按原判断实现过一版 `_record_spoken_part`（补写已投送的半句）+ 6 条单测，单测全绿——
但它们绿在"测试自己调 `gen.close()`"上，端到端一跑就不成立。**代码已回退**，不留死逻辑与
假绿测试。

**剩下的真问题换了个方向**（比原来那个更值钱）：点「停止生成」**不省任何钱、也不停推理**。
云端是白花一轮 token；本地更糟——Ollama 串行推理（§12.9 量过），那句被取消的生成长度
按 800 字算要把下一个请求排在它后面。要做的是"让它真的停"：投送层持一个 stop 标志，
`_iter_turn` 每个事件边界检查一次并退出，同时把底层 HTTP 流关掉；那时"半句没进历史"才会
成为实际问题，`_record_spoken_part` 那一套才有用武之地。这条另立任务，不混进本轮。

> **这条任务已于 2026-09-25 做完**（架构审计 §12.15），但**落点不是这里写的那个**：标志不在
> 投送层，而在**生成层** —— `call_model` 自己拿住分块流（`_collect_model_stream`），每个块边界
> 问一次旗子，收手时 `close()` 掉底层 HTTP 流。原因正是本节上面那条实测：投送层被取消并不会
> 中断线程池里已经在跑的那次 `next()`，所以"在投送层检查"根本检查不到东西。
> 实机读数：按下停止到 SSE 结束 **0.07s**，屏幕上那半截与历史里那条**逐字相同**，
> 停完之后下一句与安静时同量级（30.5s vs 基线 33.2/36.2s）。
> 而本节原命题 —— "半句没进历史" —— **从此没有对象**：停在哪儿，历史就到哪儿，
> `_record_spoken_part` 那一套不需要存在。

### 8.16 主动开口的原话现在也进对话侧（2026-09-26，用户拍"并进来"）

**缺口是查出来的，不是猜的**：她主动说过的话只落进 `s_proactive_<role>` 那一条线程，而控制台
「新建对话」另开一条 —— 那条里她不知道自己提醒过什么。证据两行：`recent_own_texts` 全仓只有
一个调用点（`reachout.py:780`，喂 anti-repeat 打分），而 `core/nodes.py` 里连 reachout/proactive
这两个字都没有 ⇒ 对话侧跟着角色走的只有 `role_memory_item`。

**修法落在宿主那侧，不在内核**：`memory_provider` 的契约多加一个参数（本轮 `thread_id`），
`chat_memory` = `memory_for_turn(...)` + `recent_reachout_lines(limit=CHAT_ECHO_LIMIT=3)`。
内核不新增任何 SQL —— 它一直不碰库（`nodes.py` 里 `conn` 零出现）。
**在那条主动会话里不抄**：同一句话本来就在她的历史里，再抄进 system 等于把复读喂回给模型
（`_scrub_own_repeats` 治的就是这个），还白花 token。

**代价说清**：3 条 × 120 字 ≈ 每轮多两百 token，而 `R26-29` 实测过本地档"prompt 与输出越长、
首字越慢"是思考长度跟着涨 —— 这个数就是那儿定的，5 条是主动开口自己用的那一份，聊天这一截更窄。

**因果不是"她答得像"，是"这句话只能从哪来"**（副本库 + 自起隔离后端 + 云端档）：新开一条线程
（`history_before_turn = 0`）、问「你之前担心我什么东西没检查来着？」，她答
「诶，你忘啦——是鞋带啦♪ 上次还看见你差点被自己绊了个跟头…」。而那个角色的
`role_memory_item` 里含"鞋带/绊倒"的是 **0 条**，角色卡 `system_prompt` 也不含 ⇒
这条信息在这一轮之前对她不存在，只可能来自刚并进去的那一截。
用例在 `tests/test_proactive_echo.py`（两臂各变异核验：摘掉注入红在第一臂，摘掉线程闸红在第二臂）。
