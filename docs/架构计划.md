# 架构计划

> 定位（2026-09-18 拍板，所有功能决策以此为准）：
> **属于我自己的角色 agent：有长期记忆，会主动找我沟通。** 本地、可信、可塑造。
> 角色 = 人格 + 权限 + 工具 + 记忆的完整运行单元；不做功能清单竞争，做"最难的可信层"。

本文是系统性规划文档：描述目标形态（B/S + C/S 双壳单后端）、现状资产复用映射、里程碑路线图（A/B/C/D）、安全模型总纲与质量纪律。具体实现细节在里程碑展开时另行细化，本文件只定骨架与边界。

---

## 1. 目标形态：一套后端，双壳

浏览器（B/S）与桌面壳（C/S）共用**同一个本机后端进程**（localhost FastAPI），共享同一份前端产物：

```
浏览器（B/S，现有）
        │  HTTP + SSE                ┌── 权限模型 ──┐
        ▼                            │ 角色白名单    │
Tauri 壳（C/S，内嵌同款前端）→ 后端进程 │ 路径边界      │ = 唯一真源
        │  HTTP + SSE                │ guard / 熔断  │
        ▼                            │ 审计          │
原生能力桥（仅 C/S）                  └──────────────┘
 托盘 / 置顶 / 透明窗 / 自启 / 热键
 原生目录对话框 / 系统通知 / 桌宠渲染(复用开源)
```

**原则**：
1. 全部权限、工具、记忆、agent 逻辑只存在后端，与端无关；
2. 前端同一份 `dist`：浏览器打开 = B/S；被 Tauri WebView 加载 = C/S，零重写；
3. C/S 只多一个"原生能力桥"，前端通过能力探测决定是否显示桌宠/系统集成入口；
4. 桌宠能力（常驻/置顶/透明/自启/热键）仅 C/S 可用——浏览器给不了系统级驻留。

## 2. 现状资产与复用映射（不重复造轮子）

| 目标需求 | 复用现有机制 | 缺口 |
|---|---|---|
| 文件读写 | `fs_read/fs_write/fs_list` + `_resolve_within` 路径守卫 + `WORKSPACE_DIR` | 任务目录不可配置、无权限档、无目录浏览 API |
| 记忆 | `memory_save` + `kernel_meta` + system prompt 记忆区 | 无（已完成） |
| agent 能力 | `build_graph_config(agent_mode)` + 规划指令 + 工具循环熔断 | 无（已完成） |
| 主动开口 | — | **事件触发 + 选择性开口（全新）** |
| 能力扩展 | registry（白名单过滤在 bind_tools 之前） | MCP 接入（`langchain-mcp-adapters`） |
| 代码执行 | `_invoke_tool` 线程池 + 超时 + `.venv-ocr` 独立解释器先例 | 任务目录独立 venv + 审批 UI |
| 桌面壳 | 前端 dist / 后端 API 全是现成 | Tauri 壳 + 能力桥（全新目录） |
| 多人 | `user_id` 列已预留（v1 单用户 demo） | 登录 + 数据隔离（长期） |

## 3. 里程碑路线图

```
A  角色接触电脑（文件权限）          ✓ 已实现（含实机演示验证）
B  角色主动开口（事件触发）           ✓ 已实现（定时首版，见 core/reachout.py）
C  能力扩展（MCP + 独立 venv 执行）   ✓ 已实现（§6.1 MCP 通道 + §6.2 run_command 均交付）
D  桌宠化（Tauri 壳，复用开源渲染）   ○ 未开工
[长期] 多人身份隔离                   ○ 未开工
```

排序理由：A 是 B 的地基（主动开口要"有东西可说"——能读文件/盯事件）；B 是差异化招牌，先于"拼能力"（C）；C 是开放生态，不做功能自研；D 是体验收尾，**决策已定、实现靠后**（A 中已预留原生对话框 provider 接口，避免返工）。

## 4. A · 角色接触电脑（文件权限，file1）

> **【已实现 2026-09-18】** A 核心交付（门禁全绿）：
> - 后端 `core/workspace.py` + `api/routers/workspace.py`：`GET /api/workspace/dir`、`PUT /api/workspace/dir`（持久绑定、热切生效，复用 runtime override）、`GET /api/workspace/tree`（受路径边界约束的只读浏览）；
> - 路径边界 `_resolve_within` 兜底：目录外读写一律拒绝（原有行为保持）；
> - fs 工具 `core/tools/files.py` 的读/写/列表**全部进 `audit_log`**（仅记路径与字节数，不记内容）；
> - 前端 `SettingsPage.tsx`「任务目录」卡片（路径输入 + 树浏览抽屉），`api.ts` 已接入；
> - 权限档位按 §4.2 交付（目录内读/写 auto、目录外拒绝）。
> - **有意收敛（非遗留）**：A 原规划的"手动/完全档""目录外受控访问"**延后至 C**，与执行审批共用确认 UI；文件事件开口已后置到 C（见 §5.2 / §6）。

### 4.1 目标
让角色按**显式授权的任务目录**读写文件，默认安全：目录内读/写自动放行，目录外一律拒绝，全部操作进审计。

### 4.2 设计要点
- **目录 provider 抽象**（关键，避免桌面化返工）：
  - `TaskDirectoryProvider` 接口：`resolve() -> Path`；
  - B/S 实现：目录树浏览 API（内置，见下）+ DB 持久绑定；
  - C/S 实现：同一接口后端不变，仅前端换 Tauri 原生对话框（D 阶段）；
  - **后端 fs 边界 / 审计 / 热切机制一个不动**。
- **目录树浏览 API**：`GET /api/workspace/tree?path=`（受路径边界约束的只读浏览）、`PUT /api/workspace/dir`（持久绑定，存 DB 覆盖热切，复用 runtime override 机制）。
- **权限档位（本次交付：一档半）**：
  - 目录内：读 = auto、写 = auto（`fs_write` 保持非幂等不重试）；
  - 目录外：一律拒绝（现 `_resolve_within` 行为，保持）；
  - 手动/完全档：**延后**，与 C 的执行审批共用一套确认 UI。
- **审计**：fs 读/写/列表全部记入 `audit_log`（当前缺失，本次补齐），审计凭据只记路径与字节数，不记内容。
- **前端**：设置页「任务目录」卡片（路径输入 + 树浏览抽屉）；对话页文件能力提示随授权状态变化。

### 4.3 出口条件（2026-09-18 已满足）
- ✅ 任务目录可配置且热切生效；目录外读写被拒且说明可读；
- ✅ fs 工具全部进审计；前端可完成"选目录 → 让角色读写 → 审计可查"；
- ✅ 门禁全绿（ruff 0 / mypy 0 / 覆盖率 ≥85 / consistency 24 / 前端 build+test）；⏳ 实机演示尚未执行，列为收尾验证项。

## 5. B · 角色主动开口（事件触发 + 选择性开口）

### 5.1 目标
角色在**不由用户发消息的时刻**主动找我——这是"属于我的角色"区别于豆包的结构性差异点。

### 5.2 设计要点
- **事件源**：
  - 定时：用户设置的"到点提醒/每日汇报"（简单 interval + 防重入）—— **B 首版已实现**（`core/reachout.py`）；
  - 文件事件：任务目录变化（新建/修改，poll 或目录哈希差量）—— **后置 C**。单独发一句
    "目录有变"没有内容价值；只有"读任务目录当开口素材"才成立，而这与 C 的读取/执行能力
    强耦合，故并入 C 一次做透（防功能堆积，见 §10）。`;
  - 自定义"盯X"：角色定期执行指定 agent 任务，结果有变化才开口（依赖 C 执行能力，后置）。
- **触发 → 执行 → 选择性开口**：
  - 触发后以该角色 agent 模式跑一轮，产出"要不要打扰"判断（话痨抑制：静默时段、频率上限、无变化不打扰）；
  - 开口 = 前端收到"角色来找你"（B/S：回到页面看到积压消息；C/S：系统通知/桌宠气泡）。
- **边界**：主动动作与用户动作走同一套权限/审计/guard——**主动不绕过任何授权**。
- **依赖**：连续运行（web 下依赖浏览器驻留，严格主动推送属 C/S；B 首版按"积压可查 + C/S 通知接口预留"收敛）。

### 5.3 出口条件
- 定时/文件事件能触发角色按 agent 模式产出主动消息；
- 抑制逻辑生效（不刷屏、静默时段不打扰）；全部进审计；
- 前端可查"角色主动找过你"的历史。

## 6. C · 能力扩展（MCP 通道 + 任务目录独立 venv 执行）

### 6.1 MCP 扩展通道
> **【已实现 2026-09-18】** MCP 通道已交付（门禁全绿，测试见 tests/unit/test_mcp.py）：
> - `core/tools/mcp.py`：用 `langchain_mcp_adapters.MultiServerMCPClient` 按 server 拉取工具，
>   每 server 独立 client（失败隔离）；工具名加 `{server_id}__` 前缀防冲突、描述裁剪到 1024 字符
>   防 bind_tools 载荷过大；`AuditedMcpTool` 包装每个工具，调用前后写 `audit_log`（actor="agent"）。
> - 配置：`MCP_SERVERS`（JSON 数组，env 双源 + `.env.example` 已登记）；`Settings.mcp_servers`
>   为 `McpServerConfig` 列表（stdio / http 两种 transport）。依赖 `langchain-mcp-adapters`
>   （requirements-mcp.txt），**未安装时即便配置了 MCP_SERVERS 也只 warning 跳过，不阻塞启动**。
> - 启用：配了 MCP_SERVERS 即把域 `"mcp"` 加进 `enabled_domains`，工具走既有角色白名单 / 超时 /
>   熔断 / 审计；`domains/registry.py` 在 build_registry 时 `register_many(..., domain="mcp")`。
> - remote HTTP transport 已支持（transport="http" + url/headers），但**首版聚焦本地 stdio**；
>   工具名冲突 / 描述过大的治理规则已落地。

- 接入 `langchain-mcp-adapters`（官方适配，langchain 栈内）：MCP 工具作为**域工具**注册进 registry（指定域如 `mcp`），走既有角色白名单、超时/熔断、审计；
- 本地 stdio server 给"用户自装工具"，remote HTTP 给第三方服务（后置）；
- **边界声明**：MCP server 给"裸能力"，权限模型（白名单/路径边界/档位）仍在自家（铁律：guard 与路径守卫不委托）；
- 工具名冲突、描述过大（bind_tools 载荷）等治理规则在接入时定。

### 6.2 代码执行（run_command）
- 任务目录独立 venv：`.venv-tasks/<目录名>`（复用 `.venv-ocr` 隔离先例），主 `.venv` 只读引用、禁止安装；
- 复用 `_invoke_tool` 线程池/超时 + 输出字节上限 + 熔断；
- **默认手动批准**：审批 UI 与 A 的写确认共用（B/S 确认卡，C/S 系统弹窗）；
- 执行动作全部进审计（命令、目录、退出码、耗时，不记输出内容）。

> **【已实现 2026-09-18，v2.6】** run_command 本功能已交付（门禁全绿）：
> - 表 `command_approval` + 状态机（core/approvals.py 的 `ApprovalService`）：
>   pending → approved（后台执行中）→ done（结果回填）；rejected 为终态。同一命令跑过
>   （done）后，工具再被调用只回放历史结果，**批准一次跑 N 遍被结构性禁止**。
> - `core/tools/run.py`：`execute_command`（Popen + 进程树终止，Windows 超时不漏跑）、
>   `make_run_tool`（run_command，内核工具 domain=None、不可重试）、
>   `run_approval_execution`（批准后的后台执行，独立线程池，进程退出路径关闭）。
>   cwd 必须落在任务目录内（`_resolve_within`）；`.venv-tasks/<目录名>` 的 Scripts/bin
>   自动前置进命令 PATH；stdout/stderr 按 64KB 截断；机密号不落审计（detail 只含
>   命令/退出码/耗时/字节数）。
> - 配置：`RUN_TOOLS_ENABLED`（总闸）与 `RUN_APPROVAL`（manual 默认 / auto 绿色通道），
>   env 双源 + 「运行环境」页可热切。
> - API：`GET /api/approvals`（含 pending 计数）+ `POST /api/approvals/{id}/decide`；
>   审批动作写 operator 审计，执行写 agent 审计。
> - 前端：侧栏「命令审批」入口 + 红点（10s 静默轮询）+ 审批抽屉；「运行环境」页
>   「命令执行」组（总闸开关 + 审批档下拉）。
> - **C 剩余待做**：任务目录文件事件主动开口（由 B 后置，依赖 C 的读取/执行能力，待做）；
>   桌宠化（§7）未开工。

## 7. D · 桌宠化（Tauri 壳）

### 7.1 范围
- Tauri 壳内嵌 WebView 加载现有 `dist`（前端零重写）；壳 = 原生能力桥：托盘、置顶、透明无边框窗、开机自启、全局热键、系统通知、**原生目录对话框**（替换 A 的树浏览 provider）；
- 桌宠显示/语音**全程复用开源**（Live2D/VRM 渲染、sherpa-onnx 等 ASR/TTS）——自研只留差异化内核；
- 桌宠 = 角色卡的显示层：角色 → 形象/情绪映射（后续迭代）。

### 7.2 边界
- 桌宠相关系统集成仅 C/S；B/S 维持全功能但无桌面驻留；
- 不引入新语言重写后端：Python 后端原样，Tauri 壳只做桥。

## 8. 安全模型总纲（贯穿所有里程碑）

1. **授权唯一出口**：工具在 `bind_tools` 之前按角色白名单过滤（模型不可见未授权工具）；
2. **路径边界唯一出口**：`_resolve_within`（web/桌面/MCP 工具一视同仁）；
3. **guard 不可绕过**：在 `call_model` 内、无独立图边（防重构/子图绕行）；
4. **主动不特权**：B 的主动动作走同一套授权/审计；
5. **一切留痕**：fs / 执行 / 主动开口 / 配置变更全进 `audit_log`；
6. **有界放大**：agent 模式步数翻倍有界，熔断两档均成立。

## 9. 质量与门禁纪律（延续既有）

- 每里程碑：pytest 覆盖率 ≥85%、ruff 0、mypy 0、`check_consistency` 24 项、前端 build + 测试；
- 提交约定：`git add` 指定文件（不用 `-A`），后端改动后重启服务验证，前端改动后 Crtl+F5 硬刷新；
- 文档同步：本文相关新增/变更必须回写本文与本索引（见 docs/README.md 约定）；
- 测试铁律：测内核行为，不测 LLM 本身（ScriptedChat 注入）。

## 10. 风险登记

| 风险 | 缓解 |
|---|---|
| 主动开口变话痨 / 打扰 | 选择性开口 + 抑制逻辑是 B 的核心验收项 |
| 本机执行被提示注入利用 | 默认手动批准 + 独立 venv + 输出上限 + 全审计 |
| MCP 工具引入不可信行为 | 白名单 + 审计 + 限长，能力可随时拔 |
| 桌面化返工 | A 即引入 provider 抽象，C/S 只换前端入口 |
| 做偏成"功能堆积" | 本文件 §1 定位为准绳，与定位无关的功能砍 |
