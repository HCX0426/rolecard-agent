## 0. 全景：一个功能的一生

```
想法 ─→ ① 需求行(US-x + 验收口径) ─→ ② 后端设计(契约/不变式→架构总览)
     ─→ ③ 界面设计(矩阵行→前端设计) ─→ ④ TODO(一条=一个可独立验证的行为)
     ─→ ⑤ 先写红测试 ─→ ⑥ 实现到绿 ─→ ⑦ 局部检查(≈2s)
     ─→ ⑧ 提交(Conventional Commits + dist 同提交) ─→ ⑨ 阶段末 gate --fast(≈84s)
     ─→ ⑩ push → CI 四臂并行(门禁/前端/镜像/Windows 分片×4)
     ─→ ⑪ 满足触发条件 → gate 全量(≈4min) ─→ ⑫ 打包链①②②′④ + 三层自证
     ─→ ⑬ bump 版本 → tag v* → Release(镜像 ghcr + 安装包)
     ─→ ⑭ 用户机上：双日志 / health / 自动更新(latest.yml)
     ─→ ⑮ 每晚：真机体检 + 评测；每周：锁刷新；常驻：Renovate / 审计 / 密钥扫描
     任何一环的发现 ─→ 回写文档与台账 ─→ 回到 ①
```

白话版：**先把要什么写成能验收的字，再把接口和界面在写码前摆出来，然后小步实现（测试先行、
改哪跑哪、每步秒级反馈），阶段末过一次快档门禁，push 后让 CI 四臂在云端复核；要发布时走
打包链、三层自证、打 tag 出 Release；装出去之后靠日志、health 和夜间体检知道它活得怎么样；
依赖、漏洞、文档一致性由机器人每周维护。** 全程任何环节发现的事实（bug、偏差、教训）都要
落回文档/台账 —— 这是四步流的第④步，也是本仓唯一不可跳的环节。

## 2. 日常循环：四步流 + 编码内循环 + 节奏

### 2.1 四步流（设计先行，顺序不可颠倒）

| 步 | 做什么 | 产出落在 | 出口（过了才进下一步） |
|---|---|---|---|
| ① 后端设计 | 定数据契约（表/列）、接口契约（端点/入参/错误码）、不变式 | `docs/架构总览.md` 模块地图与不变式节 | 契约白纸黑字，能对着评审不用猜 |
| ② 界面设计 | 为该能力在矩阵**先加一行**：落在哪个页签、可见/可控什么、四态（加载/空/错/成功）、刻意不做也要写理由 | `docs/前端设计.md` 能力↔界面覆盖矩阵 | 这一行 + 线框级描述确认 |
| ③ 实现 | 后端按契约写 + 离线单测（LLM 用脚本替身）；前端按矩阵行写，数据只从 api 层出 | 代码 + 测试 | 局部检查绿（见 2.2） |
| ④ 对照回写 | 矩阵行改最终状态（✅/⚙️/⬜）；架构总览里程碑/待办同步；触及需求则同步 `docs/需求与验收标准.md` 追溯矩阵 | 各活文档 | 文档与代码现状一致 |

### 2.2 编码内循环（分钟级反馈）

1. 读目标文件 docstring（不变式写在里面）→ 2. 先写/补测试，**在改动之前就是红的** →
3. 实现到绿 → 4. 跑受影响的那几个测试文件（≈2s）→ 5. `ruff check .`（顺手 autofix）→
6. 满足下列任一才提交。

铁律速览（全文与"为什么"在 `CONTRIBUTING.md` §1，违反即拒绝合并）：不改公共签名；不动
安全 prompt 与拼接顺序；不改表结构列名；不在 domains/ 下定义 user/tenant；不让 LLM 碰
权限边界；异常堆栈只进日志；新增依赖先改清单；不跨文件顺手重构；不提交密钥与真实数据；
不删 TODO 却不实现。

### 2.3 提交

- **Conventional Commits**：`feat:` / `fix:` / `docs:` / `test:` / `refactor:` / `chore:`，scope 可选。
- 一个提交只做一件事（功能与它的测试/文档回写同提交），保持可 bisect。
- **改了 `frontend/src` 就把重建的 `frontend/dist` 放进同一提交**（dist 有意入库：clone 免
  node 可跑 + 随包后端托管它；pre-commit 钩子会自动重建，但钩子要启用过一次）。
- 提交前 `git status` 自查：没有意外文件、没有无关大块改动。

### 2.4 节奏表（什么时候跑什么 —— 治"测试比改码慢"的那张表）

| 时点 | 跑什么 | 实测 |
|---|---|---|
| 每次提交前 | ruff + mypy + **只跑受影响的测试文件** | ≈10s |
| 每个大阶段末 | `gate.py --fast` 一次 | ≈84s |
| 全量的触发条件（满足任一） | `gate.py` 全量：删改公开配置/API 形状、动前端渲染的数据面、改装配根或进程生命周期、发布/打 tag 前 | ≈4min |
| push 之后 | CI 四臂（异步，不必等） | 见 §3 |
| 每晚 / 每周 | nightly 真机体检 / 锁刷新 | 见 §6 §7 |

**"每项整改都跑一次全套"是反模式**（一轮 6×88s ≈ 9 分钟纯浪费；多数失败秒级就能暴露）。
阶段末失败时按提交二分定位，不回头整片重改。

## 3. 门禁与 CI

### 3.1 gate 三档（口径唯一出处 `scripts/gate.py`；计时为 2026-09-19 实测校正）

| 档 | 命令 | 实测 | 内容 |
|---|---|---|---|
| fast | `--fast` | ≈84s | ruff · mypy×3 档（win32 / scripts / linux 档，防"本机绿容器红"）· 依赖方向（import-linter）· pytest 快趟（`-x`，live 用例被 `-m 'not live'` 挡住）· consistency · 前端 vitest |
| ci | `--ci`（CI 用） | ≈320s | fast + baseline 比对 + 依赖审计（出网问 OSV，新告警=红）+ 密钥扫描（gitleaks）+ README 可跑性；**覆盖率与冒烟不进 CI** |
| full | 默认 | ≈4min | + 覆盖率三档（全局 ≥90 / 单文件地板 ≥85 / 改动行 ≥95）+ 前端 tsc+build + dist 入库同步 + 随包 parity + 冒烟 14 项 |

**红了怎么办**：看 gate 输出里红的那一步 → 快照证据与红跑重试日志在 `build/` 下
（`pytest_with_evidence.py` 对已知偶发签名会自动重跑取证，屏幕标 FLAKY-RECORDED）→
修完只重跑该档。门禁读数分槽落盘（覆盖率家族进 `docs/gate-readings.json`，快档计数进
gitignore 的 scratch），**别把数字抄进散文**（反向守卫断言看着）。

### 3.2 CI 四臂（`.github/workflows/ci.yml`，push main + PR 触发，四臂并行）

| 臂 | 跑什么 | 守住什么 |
|---|---|---|
| 门禁 --ci | uv 装锁 → gate.py --ci（三层墙钟：步超时/进程内看门狗/外部 timeout，保证挂死必留红与日志） | 提交自洽：静态+单趟测试+一致性+审计+密钥 |
| 前端 | 壳 typecheck + 升级清理判据 + `npm run build`（含 tsc）+ vitest；main 上 dist 漂移由 bot 自动重建回写，PR 上漂移=红 | 前端可构建、dist 与源码同步 |
| 镜像真跑 | docker build → compose 解析与必填变量护栏 → 裸容器拒绝启动（非回环+无鉴权）→ 带鉴权起容器走真 API 往返（401/建会话/首页托管/存云端后端/非 root/HEALTHCHECK 真报 healthy） | 镜像这个交付物本身是活的 |
| Windows 分片×4 | 快档用例按路径哈希切成 4 片跨机并行（`fail-fast: false` 保日志） | Windows 专属分支（WinDLL/图标/PowerShell）被机器接住 |

省时机制：`paths-ignore: docs/**`（纯文档不烧 CI）· concurrency 同 ref 只跑最新 ·
uv 装锁（冷装 303.9s→27.8s 实测）· mypy 增量缓存 · 手动档（full-gate 全量、
windows-release 打安装包进 artifact）把最贵的检查放低频位。
**CI 红了怎么查**：先看哪臂 → 哪步 → 该步日志末尾（多数步骤自带取证输出）；cancelled
的 job GitHub 不传日志，所以分片臂 fail-fast 关着。

## 4. 构建与打包（①②②′④，顺序是硬依赖）

| 步 | 命令 | 产出 | 关键守卫 |
|---|---|---|---|
| ① 界面 | `cd frontend && npm run build` | `frontend/dist`（入库） | dist 同步由 CI/hook 把关 |
| ② 随包后端 | `.venv\Scripts\python.exe scripts\build_sidecar.py`（≈2min） | `build/sidecar/rolecard-backend/` | 打包前写入 git HEAD 指纹，spec 缺它拒绝出产物；`RUNTIME_PACKAGES` 逐条 find_spec，缺一族拒绝出产物 |
| ②′ OCR worker | `.venv-ocr\Scripts\python.exe scripts\tools\build_ocr_worker.py` | `build/ocrworker/ocr-worker/` | 非 .venv-ocr 解释器拒绝出产物；打完"渲染→认出"冒烟不过就删产物 |
| ④ 安装包 | `cd shell && npm run package` | `shell/release/*.exe` + `latest.yml`（自动更新 feed） | 产物核对点名 ocr-worker/backend 在包内 + 体积下界 |

**为什么顺序是硬依赖**：② 把 ① 的 dist 用 PyInstaller 收进产物，"吃进去就固化" —— 改过
前端只重跑 ④ 会得到"构建成功、里面是旧界面"的包（真踩过）。打完必跑三层自证
`scripts\forensics\probe_package_artifact.py`：①包内 dist 与仓库逐文件哈希 ②包内后端 ==
刚构建那份 ③真起包内 exe 问 `/api/health` 的 build.sha 与 HEAD 对账。装到本机走
`scripts\install_package.ps1`（备份→关旧进程→静默装→两路哈希验货→起服务验健康→纯度尺子）。

## 5. 发布

1. **版本单源**：`scripts\tools\bump_version.py` 从 `pyproject.toml` 派生另外三处
   （`api/main.py` API_VERSION、`shell/package.json`、`frontend/package.json`），
   "version parity"断言看着 —— 屏幕上的应用是哪一版只有一个答案。
2. **打 tag** `v*` 并 push → `release.yml` 四 job：发布前快档门禁（tag 可能从历史 commit
   打，不假设那时 CI 还绿）→ 镜像 push ghcr.io → Windows 安装包 → 建 GitHub Release。
3. 自动更新守三条红线（不静默装、不降级、装完清临时文件），口径在
   `docs/更新机制与OCR随包.md` §3。
4. CHANGELOG 目前手写（自动化在 §9 P5）。

## 6. 运维观测与夜间体检

- **双日志**：`backend.log`（每次启动覆盖）与 `shell.log`（追加）都在 `%APPDATA%\rolecard-agent`，
  关键保证（如进程归属、通知弹没弹）各有一行日志可查。
- **健康面**：`/api/health` 鉴权豁免、带 build.sha 构建指纹（脏旗带 pathspec，只问进包路径）；
  Docker HEALTHCHECK 由 CI 真测过"报过 healthy"。
- **夜间**（`nightly.yml`，self-hosted runner，北京 02:00）：真机冒烟 + 真模型评测
  （`-m live` + run_eval）+ persona/延迟测量，证据 JSON 落 `docs/eval/`；失败只报警不拦 PR。
  没注册 runner 时自动跳过。
- **缺口的登记**：崩溃上报与诊断导出见 §9 P2 —— 目前用户机上炸了只能靠用户说。

## 8. agent 时代要点（本仓既定事实）

骨架由强模型写好、细节由多模型分批补全（`CONTRIBUTING.md` 开头即宣言）。由此三条：

1. **文档即执行上下文**：设计写得模糊，agent 按自己的理解填空 —— 所以 §2.1 的①②不可跳。
2. **防"局部正确、全局漂移"**：靠不变式、不可改清单、TODO 可独立验证、TDD 二元反馈
   （弱模型最擅长优化二元目标）—— 全是本文已有机制。
3. **人审机器、机器审机器**：CI + 一致性断言先行初审，人终审产出。

## 9. 未完善清单（按价值排序；"不考虑改动量，只考虑值不值"的口径）

> 每项：做什么 / 为什么 / 验收。落地后状态翻 ✅ 并在 §十一 记一行。

### P1 — OpenAPI 契约 → 前端类型自动生成 ⬜

做什么：脚本从 `app.openapi()` 导出 schema → openapi-typescript 生成
`frontend/src/api/schema.d.ts` → 前端请求层逐文件迁移 → gate 加"schema 漂移"步
（生成物与入库版 diff 非空 = 红，同 dist 同步的形状）。
为什么：消灭"后端改字段、前端类型没跟"整类 bug；契约从 markdown 靠人执行升级为机器执行。
验收：改一个响应模型不动前端 → gate 红，报错指向生成的类型文件。

### P2 — 观测最小版：错误签名 + 一键诊断包 + 夜间静默告警 ⬜

做什么：① 未捕获异常计数+签名（异常类型 + 顶部栈帧哈希）追加写 `error.jsonl`，
`/api/health` 带 `error_count_recent`；② 设置页加"导出诊断包"（zip：双日志 + error.jsonl +
版本指纹 + 环境），用户报 bug 附带现场；③ nightly 加一条死信开关 —— 连续 N 晚没跑成
（runner 没接/失败）要有一条提醒路径，不然夜间臂静默消失没人知道。
为什么：§6 是差距最大环；"崩溃有签名可查 + 报障自带现场"是桌面应用在无服务端前提下的
观测上限。刻意不做网络自动上报（隐私 + 无服务端，知情取舍）。
验收：人为触发未捕获异常 → health 计数可见、jsonl 有签名行；诊断包能一键产出并被
check 工具读出摘要。

### P3 — 测试套件本身提速：收敛每用例自建库开销 ⬜

做什么：给 chroma/sqlite 建库开销做一次专项 —— session 级 fixture 复用 + 每用例事务回滚 /
临时目录复用，把"每条用例自建一套库"改成"每模块建一次"。这是快档 88% 时间在 pytest 的根。
为什么：本仓已实证 xdist 并行在此形状下反而更慢（建库开销吃光并行收益），**提速的正路是
让每条用例更便宜**，不是更多 worker。全量趟压下来之后，fast/full 两档与 CI 门禁臂同时受益。
验收：同一套用例全量墙钟显著下降（以 gate 读数为准），用例零语义改动（通过的还通过）。

### P4 — pre-commit 扩容（L0 本地即时拦截）⬜

做什么：`.githooks/pre-commit` 在 dist 重建之外加 `ruff check .`、`ruff format --check`、
mypy（增量缓存）。慢的不挂（pytest / consistency 仍走 gate）—— hook 超 10 秒就会被
`--no-verify`，那它就死了。
为什么：ruff 能抓的错误类（未定义变量、没用 import）没理由等到 84s 的 fast 档。
验收：提交一个未定义变量 → commit 当场被拦。

### P5 — CHANGELOG 自动生成（release-please）⬜

做什么：release-please 读 Conventional Commits 自动维护 CHANGELOG、开 release PR（版本
走 bump_version.py 单源口径同步四处）；与 release.yml 分工 —— 它管"从提交史算版本"，
release.yml 管"从 tag 出产物"。
为什么：提交规范已严格落地，只差最后一公里；手写 CHANGELOG 是持续人力税。
验收：合并几个 feat/fix → 自动开出带 CHANGELOG diff 的 release PR。

### P6 — API 集成测试补强 🟡

做什么：对 `api/routers/` 每个 router 至少一条 `httpx.AsyncClient` 直打 app 的集成用例
（不起真进程），优先覆盖鉴权豁免矩阵与 `CONTRIBUTING.md` §5 统一错误结构。
为什么：单测管函数、镜像臂只走一条真链路，中间"路由→服务→存储"接缝靠覆盖率平均数兜。
验收：每个 router ≥1 条集成用例；api 层改动行覆盖率 ≥95% 不靠豁免。

### P7 — 一键开发环境（dev 脚本 + 自检）⬜

做什么：`scripts\dev.ps1` 一个命令同时起后端（uvicorn --reload）+ 前端（vite）+ 壳，
前置自检（venv 在不在、锁装没装、钩子启没启用、端口占用），缺什么打一条修法。
为什么：三件套分开起是每个新环境的重复税；README 可跑性探针只管"从零能起"，不管
"日常快速进入状态"。
验收：新 clone 后装完依赖，一条命令 30 秒内三件套全起、互连健康。

### P8 — 前端 ESLint ⬜

做什么：上 eslint + typescript-eslint + react-hooks 规则族，挂进前端 build 前与 CI 前端臂。
为什么：前端目前只有 tsc（类型对、逻辑反它管不着），hooks 依赖数组这类整族错误是
ESLint 的招牌地盘。
验收：一条坏 hooks 依赖 → lint 红；CI 前端臂含该步。

### P9 — 路径感知 CI + 预算按实测收敛 🟡

做什么：① dorny/paths-filter 之类按改动路径选臂（纯前端改动不跑镜像臂与 Windows 分片，
纯后端不跑前端臂）；② 等 `--ci` 尾部四步攒够绿趟每步 ⏱ 读数后按实测收回 STEP_TIMEOUTS
与 job 预算，并评估依赖审计（OSV 出网 ≈54s）挪 nightly 的取舍。
为什么：--ci 是每次 push 都付的墙钟；本仓预算治理的既定原则是"按实测不按估计"。
验收：纯前端提交的 CI 只跑相关臂；预算调整的提交里引用读数。

### P10 — beta 更新通道（桌面版灰度）⬜

做什么：electron-updater 增加 beta 通道（latest-beta.yml），设置页三档自动更新开关旁加
"尝鲜"档；发布流程允许先发 beta、观察几晚 nightly 与自用反馈再转正。
为什么：桌面应用没有金丝雀，但自动更新天然是发布通道 —— 分通道就是桌面版的灰度发布。
验收：beta tag 产出独立 feed；切换通道能各自收到正确的版本。

### P11 — 任务池统一 GitHub Issues 🟡

做什么：bug / 新需求 / 技术债全部进 Issues 打标签（bug/feat/debt），文档只留"为什么"与
验收口径；需求追溯矩阵的 US-x 编号进 issue。
为什么：现在待办散在文档 TODO 注释与台账里，无排序视图；"债"不可见就会烂掉。
验收：新 bug 从 issue 到提交可追溯（commit 引用 issue 号）；backlog 有一个能排序的地方。

### P12 — 重要改动走分支 PR 自审 ⬜

做什么：风险改动（动装配根/公开契约/进程生命周期）先推分支开 PR（自己批自己合），
CI 绿再进 main；日常小改仍直推。
为什么：main 上的红是全员可见的坏状态（历史上有过两次带红推上 main）；PR 是"让 CI 先看
一眼"的最便宜形态，还能强制过一遍 diff 自审。
验收：分支上的红不再出现在 main；PR 模板一页（改了什么/怎么验的）。

### P13 — SAST 静态安全扫描（CodeQL）⬜

做什么：CodeQL（个人仓免费）挂进 CI 周级跑 Python + JS 两语言。
为什么：从"缓做"挪入 —— 按"只看价值不看改动量"的口径重排后，它对注入/反序列化这类
模式化漏洞的机器覆盖仍有独立价值（gitleaks 管密钥、pip-audit 管依赖，都不扫自家代码）。
验收：CI 出现 CodeQL 臂并绿；发现项走 issue 登记。

### 缓做 / 不做（有登记的取舍，不是遗漏）

| 项 | 判定 | 理由 |
|---|---|---|
| SBOM | 缓做 | 等真实分发诉求（企业用户/合规问起）；pip-audit + 锁已覆盖大头。价值判断，非工作量 |
| Playwright 持续 E2E | 缓做 | smoke_check 14 项 + 截图冒烟已覆盖关键路径；某条用户路径反复手测时再自动化它 |
| branch protection 强制 | 不做 | 单人仓无强制对象；P12 的自审 PR 是自愿版 |
| staging 环境 | 不做 | 桌面应用结构性不适用（等价物：artifact → 本机验收 → Release） |
| 变异测试 | 不做 | 慢且只解决"审验证"问题的一半 |
| 实时监控/告警全托管（Prometheus/Sentry 类） | 缓做 | 需服务端；P2 是它在本产品形态下的最小可行等价物 |
