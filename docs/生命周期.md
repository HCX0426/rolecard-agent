## 一、全流程现状（①→⑩，每环：怎么走 → 状态）

状态标记：**✅ 已完善** / **🟡 有但弱** / **⬜ 缺**。每环末尾括号给出对应的执行文件/命令。

### ① 需求 ✅

- 怎么走：用户故事 + 验收口径写在 `需求与验收标准.md`（US-x 编号 + 追溯矩阵）；
  界面侧需求先进 `前端设计.md` 的能力↔界面覆盖矩阵（与②衔接）。
- 无独立 backlog 排序层（单人开发，待办住在文档与 TODO 注释里）—— 接受现状，不补。

### ② 设计 ✅

- 怎么走：四步流的前两步，顺序不可颠倒 —— 后端设计落 `架构总览.md`（数据契约 / 接口契约 /
  不变式），界面设计落 `前端设计.md` 矩阵行（页签 / 可见可控 / 四态 / 刻意不做也要写理由）。
  出口：契约白纸黑字能评审，才进实现。（`开发流程.md` §①②）

### ③ 拆任务 ✅

- 怎么走：TODO 粒度规约 —— 一个 TODO = 一个可独立验证的行为，写 in/out/done-when；
  「要读超过两个文件才能开始的 TODO 太粗」。完成定义 DoD 九条在 `CONTRIBUTING.md` §7。

### ④ 编码 ✅

- 怎么走：测试先行（红 → 绿 → ruff → consistency → 提交）；10 条铁律 + 不可改清单
  （`CONTRIBUTING.md` §1/§4）；依赖方向契约由 import-linter 机器执行。

### ⑤ 本地验证 ✅

- 怎么走：分级反馈 —— 改哪跑哪（≈2s）→ 提交前局部（ruff + mypy + 相关测试文件）→
  阶段末 `gate.py --fast`（≈84s）→ 触发条件满足再全量（≈4min）。
  纪律：**不要每项小改都跑全套**（`开发流程.md` 门禁节明文）。
- 🟡 弱点：ruff/mypy 靠自觉跑，pre-commit 只管 dist 重建（见 §三 P3）。

### ⑥ 提交 / CI ✅

- 怎么走：Conventional Commits + 可 bisect 提交；dist 与源码同提交；push 后 CI 四臂并行
  （门禁 --ci ∥ 前端 ∥ 镜像真跑 ∥ Windows 分片×4），路径过滤 docs/**、并发取消、uv 装锁。
- 🟡 弱点：`gate.py --ci` 每趟 ≈5.5 分钟（单趟 pytest + 四个尾部新步骤），是当前反馈
  周期的最大头 —— 优化项见 §三 P6。

### ⑦ 构建 ✅

- 怎么走：① frontend build（dist 入库）→ ② build_sidecar（PyInstaller，构建指纹
  build.info）→ ②′ build_ocr_worker（独立 venv + 冒烟）→ ④ electron-builder（NSIS）。
  顺序是硬依赖（② 吃 ① 的产物）；打完 `probe_package_artifact.py` 三层自证。
- ⬜ 缺：SBOM（缓做，等分发诉求，见 §三"缓做"表）。

### ⑧ 发布 ✅

- 怎么走：tag `v*` → release.yml 四 job（发布前快档门禁 → ghcr 镜像 → Windows 安装包 →
  建 Release）；版本单源 `bump_version.py`（pyproject 派生另外三处）；
  自动更新 feed（latest.yml）三条红线（`更新机制与OCR随包.md` §3.3）。
- ⬜ 缺：CHANGELOG 手写（P2：release-please 自动生成）。

### ⑨ 运维观测 🟡（差距最大的一环）

- 已有：`backend.log` / `shell.log` 双日志；`/api/health`（带 build.sha）+ Docker
  HEALTHCHECK；nightly 真机体检（冒烟 + 真模型评测 + persona/延迟测量，证据落 `docs/eval/`）。
- ⬜ 缺：崩溃/异常上报路径 —— 用户机上炸了你不知道（P4 补最小版）。

### ⑩ 维护演进 ✅

- 怎么走：Renovate + 每周 lock-refresh（pip-compile 刷新锁、自动开 PR）+ pip-audit
  （新 CVE = 红）+ gitleaks（密钥扫描）；文档一致性 70+ 条断言机器把守；做完的设计稿
  搬 `docs/archive/`。

### 横切线 ✅

- 文档回写：四步流第④步 + DoD 强制；一致性断言兜底。
- 安全左移：gitleaks + 依赖审计 + 运行时护栏（非回环 + AUTH_MODE=off 拒绝启动，CI 真测过）；
  权限审查固化为 `权限审查（2026-10-09）.md`。

## 二、agent 时代流程要点（本仓的既定事实）

本仓骨架由强模型写好、细节由多模型分批补全（`CONTRIBUTING.md` 开头即宣言）。由此成立的
流程要点，本文只列与"怎么干活"直接相关的：

1. **文档即执行上下文**：设计写得模糊，agent 按自己的理解填空 —— 所以①②不可跳过，
   这是流程不是美德。
2. **防"局部正确、全局漂移"**：靠不变式、不可改清单、TODO 可独立验证、TDD 二元反馈 ——
   全是 §一 里已有的机制，不是新东西。
3. **人审机器，机器审机器**：CI + 一致性断言先行，人终审产出。

## 三、未完善清单（按性价比排序；落地一项改一份，本节跟着回写)

> 每项给：做什么 / 为什么 / 验收。做完把条目标 ✅ 并在末尾追加"完成记录"一行（日期 + 关键提交）。

### P1 — OpenAPI 契约 → 前端类型自动生成 ⬜

- **做什么**：加脚本从 `app.openapi()` 导出 schema → `openapi-typescript` 生成
  `frontend/src/api/schema.d.ts`；前端请求层逐文件迁移到生成类型；
  gate 加一步"schema 漂移"（生成物与入库版 diff 非空 = 红，同 `check_dist_sync.py` 形状）。
- **为什么**：消灭"后端改字段、前端类型没跟"整类 bug；契约从 markdown 靠人执行升级为
  机器执行。
- **验收**：改一个响应模型不改前端 → gate 红，报错指向生成的类型文件。

### P2 — CHANGELOG 自动生成（release-please）⬜

- **做什么**：上 release-please GitHub Action：读 Conventional Commits 自动维护
  CHANGELOG.md、开 release PR（版本号走 `bump_version.py` 单源口径同步四处）、tag 后产
  GitHub Release。与现有 release.yml 分工：release-please 管"从提交史算版本"，
  release.yml 管"从 tag 出产物"。
- **为什么**：提交规范已严格执行，只差最后一公里；手写 CHANGELOG 是持续的人力税。
- **验收**：合并几个 feat/fix → 自动开出带 CHANGELOG diff 的 release PR。

### P3 — pre-commit 检查集扩容 ⬜

- **做什么**：`.githooks/pre-commit` 在 dist 重建之外加三步：`ruff check .`、
  `ruff format --check`、`mypy`（带增量缓存）。**慢的不挂**（pytest / consistency 仍走
  gate）—— hook 超 10 秒人就会 `--no-verify`，那它就死了。
- **为什么**：L0 本地即时拦截现在只有一条；ruff 能抓的错误类没理由等到 84s 才暴露。
- **验收**：提交一个未定义变量 → commit 当场被拦。
- 前置提醒：`git config core.hooksPath .githooks` 每个 clone 手动启用一次（DoD 已写）。

### P4 — 崩溃/异常上报最小版 ⬜

- **做什么**：后端未捕获异常计数 + 签名（异常类型 + 顶部栈帧哈希）追加写本地
  `error.jsonl`；`/api/health` 带 `error_count_recent`；夜间臂加一条：读本机 error.jsonl
  最近签名。**刻意不做**网络自动上报（隐私 + 无服务端，知情取舍）。
- **为什么**：⑨ 是差距最大环；"崩溃有签名可查"把"用户报 bug 靠猜"变成"报 bug 附带现场"。
- **验收**：人为触发一次未捕获异常 → health 可见计数，jsonl 有签名行。

### P5 — 后端 API 集成测试补强 🟡

- **做什么**：盘点 `tests/` 现状，对 `api/routers/` 每个 router 至少一条
  `httpx.AsyncClient` 直打 app 的集成用例（不起真进程），优先覆盖鉴权豁免矩阵与错误码
  契约（`CONTRIBUTING.md` §5 的统一错误结构）。
- **为什么**：单测管住函数、CI 镜像臂只走一条真链路；中间那层"路由→服务→存储"的接缝
  目前靠覆盖率的平均数兜。
- **验收**：每个 router 文件至少一条集成用例；改动行覆盖率 ≥95% 在 api 层不靠豁免达成。

### P6 — CI 单趟墙钟再收敛 🟡

- **做什么**：等 `--ci` 尾部四步（密钥扫描 / 依赖审计 / README 可跑性 / baseline）攒够
  绿趟每步 ⏱ 读数后（`ci.yml` 门禁步注释里挂着的账），把 `STEP_TIMEOUTS` 与 job 预算
  按实测收回；同时评估依赖审计从每次 push 挪到 nightly（OSV 出网 ≈54s 是尾部最贵一步）
  的取舍。
- **为什么**：`--ci` 是每次 push 都付的墙钟；预算治理在本仓的原则是"按实测不按估计"，
  读数没回来之前不动。
- **验收**：连续 5 趟绿 run 的每步 ⏱ 落盘；预算按新读数调整且 comments 里引用读数。

### 缓做 / 不做（有登记的取舍，不是遗漏）

| 项 | 判定 | 理由 |
|---|---|---|
| SBOM | 缓做 | 等真实分发诉求（企业用户/合规）；pip-audit + 锁已覆盖大头 |
| SAST（semgrep/CodeQL） | 缓做 | 攻击面小；gitleaks + 权限审查 + 运行时护栏已盖高危面 |
| Playwright 持续 E2E | 缓做 | smoke_check 14 项 + 截图冒烟已覆盖关键路径；E2E 脆且慢，单人项目净负债 |
| branch protection / PR 模板 | 不做 | 单人 trunk-based，无评审对象 |
| staging 环境 | 不做 | 桌面应用结构性不适用（等价物：artifact → 本机验收 → Release） |
| 变异测试 | 不做 | 慢且只解决"审验证"问题的一半 |
| 实时监控/告警全托管 | 缓做 | 需要服务端；P4 是它的最小可行前置 |
