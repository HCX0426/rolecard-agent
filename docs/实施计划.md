## 0. 本轮改了什么

1. **组织方式**：从"排 Day1~Day28 工期"改为**按开发生命周期**（需求 → 设计 → 实现 → 测试 → 部署 → 迭代），每个阶段都有明确的**出口条件**
2. **范围切分**：v1 只保留四个里程碑（M1~M4，含最小 HTTP 层），其余全部进 v2 roadmap。（2026-09-14 增补：**M5 控制台前端工程化**自 v2.3 提前进 v1，见 §3 P2）
3. **补齐两个缺失的生命周期环节**：**需求与验收标准**（P0）、**测试与评测**（P3）——原方案这两块是空的
4. **设计阶段纳入两处修正**：数据一致性状态机（`05` 的 A1）；`user_base` 从 `domains/health` **上移到 `core`**（用户/租户是内核概念，不是领域概念）

## 3. 阶段详情

### P0 · 需求与验收标准　（权重 5%）

**产出**：`docs/需求与验收标准.md`

- 一页 PRD：目标用户、三个核心场景、**可度量的成功标准**
- 用户故事 + 验收清单（对应验收标准写清楚怎么测）
- v1 / v2 边界与"非目标"清单

**出口**：成功标准全部可量化，每条都有测试方式。
**为什么必须有**：这是"别人给你需求"和"你自己定义需求"的分界线，也是面试里回答"这个项目解决了什么问题"的依据。

### P1 · 设计（数据契约冻结）　（权重 10%）

**产出**：

- 三份 DDL：
  - `core/schema.sql` —— **五张内核表**：`tenant` / `app_user` / `session_thread` / `plugin` / `audit_log`
  - `roles/schema.sql` —— `role_card`（含 `is_builtin` / `model_name`）
  - `domains/health/schema.sql` —— `user_base` **已移除**（用户是内核概念），只保留报告与指标表
- **`tool_epoch` 机制**：会话状态记录工具集版本号，插件启停时递增。跨版本恢复会话时，历史里可能引用已下线的工具，执行器必须回答「该能力已下线」而不是抛异常（解决 `docs/技术评审与决策.md` C14）
- **`ingestion_task` 状态机**：`pending` → `parsed` → `indexed` / `failed`，配 `file_hash` 幂等键 + 补偿重试（解决 `05` A1 的 SQLite / Chroma 一致性问题）
- **接口契约**：chat / roles / plugins / admin 四组端点（OpenAPI 或手写）
- **错误码规范**：工具异常统一结构，堆栈只进日志不进返回值
- **评测集用例格式**：`输入 / 期望工具 / 断言 / 备注`（出题原则见 `06` §五）

**出口**：数据契约冻结（之后改表要走变更记录）；接口契约可以用 mock 跑通。

### P3 · 测试与评测　（权重 20%）

| 层次 | 测什么 | 怎么测 |
| --- | --- | --- |
| 单元测试 | 工具层（纯函数）、Prompt 装配、白名单过滤 | pytest，不需要模型 |
| 集成测试 | 图的路由分支 | **mock 掉 LLM** 返回固定响应，断言走了哪条边 |
| **评测集** | Agent 端到端行为 | 20~50 条用例，指标 = 工具选择准确率 + 数据引用正确率 |
| 手工验收 | 主流程可用性 | 按 `docs/需求与验收标准.md` 的用户故事清单逐条走 |

> **不测 LLM 本身。** 模型是外部依赖，"回答得好不好"用评测集度量，而不是写成单元测试。这个区分很多人搞不清，讲清楚是加分项。

**出口**：有一个**可复现的通过率基线数字**（例如"工具选择 62%"），后续每次改动重跑对比。

### P4 · 部署与交付　（权重 20%）

- `README.md`：3 条命令可跑 + 架构图 + v2 roadmap + 免责声明
- 60 秒演示视频

**出口**：干净环境按 README 操作能跑起来。

- **出口**：未做的部分有清晰计划，不是一句"以后再说"

## 4. 工程实践规范（原方案缺，补上）

| 项 | 约定 |
| --- | --- |
| 代码风格 | ruff（lint + format），提交前跑 |
| 类型 | 全程类型标注，可选 mypy 基础检查 |

| 依赖管理 | **`pyproject.toml` 是唯一事实来源**；依赖按范围拆成 `requirements*.txt`，`requirements.txt` 只含 v1 内核；**OCR 依赖必须独立 venv**（否则第一天就会拉入 paddle 全家桶，见 `docs/技术评审与决策.md` C2） |
| 密钥 | `.env` 不入库；部署走环境变量 / secret 挂载 |

## 5. 时间分配（权重制，不排死日期）

| 阶段 | 权重 |
| --- | --- |
| P0 需求与范围 | 5% |
| P1 设计 | 10% |
| P2 实现（M1~M5） | 50% |
| P3 测试与评测 | 20% |
| P4 部署与交付 | 15% |

**为什么不再排 Day1~Day28**：原计划把学习、开发、文档混在一起按天排，一旦某天卡住就整条链崩塌（`05` R1 的风险来源）。改成阶段权重后，**每个阶段都能独立停下来并交付一个完整的东西**。

| 系统设计 | ✅ 架构分层、技术选型到位 | ✅ P1 补数据契约 / 接口契约 / 一致性状态机 |
| 实现 | ⚠️ 有里程碑，但无工程规范 | ✅ P2 三个迭代 + 编码规范 + 分支与提交约定 |
| 测试 | ❌ 只写了"单元测试" | ✅ P3 分层测试 + 评测集 + 通过率基线 |
| 部署 | ⚠️ 提到 Docker，无 CI | ✅ P4 CI + 依赖锁 + README 可复现 |
| 维护 / 迭代 | ❌ 无 | ✅ P5 v2 roadmap + issue 模板 |

**结论：原方案只有「设计 → 实现」两段，头（需求）和尾（测试/部署/迭代）都是空的。本计划把六个环节补齐，并且每一环都有可判定的出口条件。**
