## 0. 总体结论

**架构叙事成立，版本清单不可直接使用。**

分层的方向是对的——编排层 / 业务服务层 / 存储层解耦、强类型边界、可观测、区分短期会话记忆与长期持久档案，这些都是企业 Agent 工程的标准做法，作为面试作品的主线足够扎实。

但 `requirements.txt` 里存在 **2 个硬冲突**，照抄会直接 `ResolutionImpossible`，一个依赖都装不上。另有若干设计层问题，其中 3 条（D1 白名单生效时点、D2 switch_role 自我授权、D7 健康数据上云）恰好是面试官最爱追问的点，提前改掉就是加分项。

## 1. 阻断级问题（P0，必须修正）

### P0-1 `langgraph==1.2.6` 与 `langchain==1.4.0` 互相矛盾

实测 PyPI 元数据（2026-09-14）：

```
langchain 1.4.0  requires_dist:
  langchain-core<2.0.0,>=1.6.0
  langgraph<1.3.0,>=1.2.11        ← 关键
  pydantic<3.0.0,>=2.7.4
```

方案同时锁 `langchain==1.4.0` 和 `langgraph==1.2.6`。`1.2.6 < 1.2.11`，两者不可共存。

**修正：`langgraph==1.2.11`**（当前 1.2 补丁线的版本，也是与 langchain 1.4.0 配合的正确版本）。

### P0-2 `langchain-ollama==0.2.0` 属于上一个大版本

实测：

```
langchain-ollama 0.2.0  requires_dist:
  langchain-core<0.4.0,>=0.3.0    ← 0.3 时代的约束
  ollama<1,>=0.3.0

langchain-ollama 1.1.0  requires_dist:
  langchain-core<2.0.0,>=1.2.21   ← 与 1.x 对齐

```

而 `langchain 1.4.0` 要求 `langchain-core>=1.6.0`。`<0.4.0` 与 `>=1.6.0` 无交集。

**修正：`langchain-ollama>=1.1.0`**。0.2.0 是 2024 年 LangChain 0.3 时代的包，被"官方维护包"这句话误导了。

## 2. 事实性表述风险（影响面试可信度）

作品集里写不实的技术论断，风险远大于写得不漂亮。以下三条需要改写：

1. **"langgraph 1.2.6 是 2026 LTS 稳定版"**
   LTS 描述的是 **1.x 整条大版本线**，不存在"1.2.6 是 LTS"的说法。时间线需要说准：LangGraph 1.0 发布于 2025-10-22，1.1 于 2026-03-10，1.2 于 2026-05-11，当前补丁线为 1.2.11（2026-08）。说成"LangGraph 1.x 是当前 LTS 线，我们锁在 1.2.11"就完全站得住。

   Klarna / LinkedIn / Uber / Replit 在公开资料里被反复引用，JPMorgan 未核实到。**建议直接删掉厂商名单**，改成"LangGraph 官方公开的落地案例"，或者更好的做法——只讲你自己做的工程设计。面试官不会因为少一个公司名扣分，但会因为你说错而质疑你的严谨度。

3. **"langchain-core 1.4.x，与 LangGraph 1.x 配套"**

   > ⚠️ **更正（2026-09-14，实测）**：本文原先写"`langgraph.prebuilt` 已废弃"，**这是错的**。
   > 在 langgraph 1.2.11 里 `langgraph.prebuilt` 导入正常、**无任何告警**，而且

## 3. 设计层问题（面试真正的得分/失分点）

### D1 ⭐ 白名单必须在 `bind_tools` 阶段生效，而不是调用时拦截

方案 SKILL-3 写的是"Agent 调用工具前，检查当前角色的 `tool_whitelist`，不在白名单内的工具直接拒绝调用"。这只做了**事后拦截**：模型依然"看得见"全部工具的 schema，会持续尝试调用被禁工具，浪费轮次，并输出"我无法调用该工具"这类幻觉式解释。

**修正**：每轮按 `current_role_id` **过滤工具列表后再 `bind_tools`**——模型根本看不到白名单外的工具；执行器里再保留一次校验做纵深防御。

这是"权限控制应该前置还是后置"的经典问题，能答好的人不多。

### D2 ⭐ `switch_role` 交给 LLM 自主调用 = 自我授权

让被约束的对象自己决定切换成哪个角色，本质上是把自己的权限边界交给自己管。更直接地说：用户可以 prompt injection 诱导它换角色，绕过角色设定。

**已决策（2026-09-14，见 `docs/技术评审与决策.md` C5）**：

> **`switch_role` 不绑定给模型。** 角色切换是 API / UI 动作，写 `session_thread.current_role_id`；LLM 只读不写。

理由：让模型改自己的权限边界属于**自我授权**，一次 prompt injection 就足以让它切换到工具更多的角色。
审计照旧保留（每次切换写 `audit_log`），但定位从"补偿措施"变成常规可追溯性。

角色切换仍然保留历史：只改角色 id，不动 messages。

**在面试里主动提出这一点是强加分**——它证明你会从攻击者视角看自己的系统，而不只是把功能做出来。

### D3 System Prompt 不能落进 messages 历史

如果 checkpointer 里存的是含 system message 的完整消息列表，切换角色后会出现**多条 system message**、旧人设残留，模型行为变得不可预测。

**修正**：`messages` 只存 `user` / `assistant` / `tool` 三类；system prompt **每轮调用前现场拼装**，永不写入历史、永不进 checkpoint。

### D4 全局安全规则的三条硬约束

1. **存在代码里，不在数据库里** → 角色卡的 `system_prompt` 无论怎么被改，都覆盖不掉它；
2. **拼接在角色 prompt 之后** → 后置位置对模型的优先级更高；
3. **拼接逻辑写成不可绕过的单一函数** → 所有 LLM 调用必须经过它，不允许任何节点绕过。

**同时必须承认**：提示词层的"禁止诊断"是**软约束**，不是安全机制。
面试时把它讲成"纵深防御的一层"——`提示词约束 + 输出侧关键词/意图拦截 + 拒绝诊断类意图的意图分类`——可信度远高于"我在 prompt 里写了不许诊断"。

### D5 `is_verified` 不能让 LLM"记得说"

方案要求"未人工确认的数据，Agent 回答时必须提示【该指标为 AI 自动提取，尚未人工校验】"。如果依赖 prompt 让模型自觉附加这句话，**必然漏**，尤其是多轮对话里。

**修正**：把标记**拼进工具返回的文本本身**——工具返回 `总胆红素 21.3 μmol/L（参考 5–21）【AI 自动提取，未经人工校验】`。模型只是转述工具文本，漏不掉。这是"用数据通路保证一致性，而不是用提示词"的典型思路。

### D6 表结构缺字段

| 表 | 缺失 | 为什么必须补 |
| --- | --- | --- |
| `role_card` | **`is_builtin`** | 方案说"内置角色不可删除"，但表里**没有任何字段标识哪个是内置**，这条规则无法实现 |
| `role_card` | `model_name` | 企业里不同角色挂不同模型很常见；这也让"动态角色"的叙事更完整 |
| `medical_index` | **`is_verified`** | OCR 规则里要求打这个标记，但表定义里没有这一列——自相矛盾 |
| `medical_index` | `source`(ocr/manual)、`verified_at`、`raw_text` | 医疗数据**没有溯源链是硬伤**：要能回答"这个数值是从哪张报告、哪段原文来的" |
| `medical_report` | `file_hash`、`status` | 去重 + 解析状态机 |

另外，`tool_whitelist` 用 TEXT 存 JSON 可用且简单，但牺牲了可查询性（想查"哪些角色能用某工具"就得全表扫）。演示项目保留 JSON 没问题，**但要在面试里主动说出这个取舍**，并指出生产会拆成 `role_tool` 关联表——这比闷头用 JSON 好得多。

### D7 ⭐ 健康数据上传 LangSmith 云端（必须主动处理）

这是全方案最应该主动交代的合规风险：开启 LangSmith 后，**报告原文、指标值会原样上传到 SaaS**。一个"健康档案"项目把病历传到第三方云，与项目自身的隐私叙事直接冲突。

**修正（择一，并写进 README）**：
1. **推荐**：演示一律使用虚构/脱敏数据，README 显式声明"所有演示数据均为构造数据"；
2. 关闭云端 tracing，仅保留本地结构化日志；
3. 自托管 LangSmith（需企业授权，个人项目不现实）。

再补一句"真实场景需考虑《个人信息保护法》对**敏感个人信息**的处理要求（单独同意、最小必要、去标识化）"。这类表述放在面试里是明显的加分项，而且**成本极低**。

### D8 OCR 依赖隔离（Python 3.11 的真正理由）

PaddleOCR 会带入自己的 numpy / OpenCV / onnxruntime 依赖树，与 chromadb 的上游依赖存在版本摩擦。

> ⚠️ **更正（2026-09-14）**：本文原先把"`paddlepaddle` 的 wheel 对 Python 版本支持滞后"写成选 3.11 的主要原因。
> 实测后这个理由**不成立**——`paddlepaddle 3.3.1` 已提供 `cp39`–`cp313` 的全部 wheel。
>
> **最终决定：用 3.13**（见 §8）。实测 3.13.14 上 v1 全套依赖 + chromadb 装通并跑过测试；
> v2.2 的 OCR 链路在 3.13 上也安全：`paddleocr` / `paddlex` 是 pure-python，`paddlepaddle` 有 cp313 wheel，
> OpenCV 走 `cp37-abi3`。
>
> 这条更正带来的真正结论是：**要关注的是依赖隔离（独立环境），不是 Python 版本。**

**修正**：OCR 放**独立 venv / 独立进程**，主进程通过接口调用（本地版本的"OCR microservice"）。并且**只在 Week 3 再引入**，避免前两周被环境问题拖死。

顺带：`paddleocr>=3.7.0` 会拉入 `paddlex[ocr-core]>=3.7.0,<3.8.0`，整条依赖链不轻（实测元数据）。

### D9 摘要压缩的副作用

"超长会话自动摘要压缩、丢弃原始长消息"要注意：**摘要本身会产生幻觉**，而医疗场景对数值极度敏感。

**修正**：只对**闲聊轮次**做裁剪/摘要，**工具返回的结构化数值不参与摘要**；需要精确数值时一律回工具查。这也正好呼应方案原有的"短期记忆 vs 长期持久档案"的划分——把它讲成一致性规则而不是省 token 手段，立意更高。

### D10 命名：`SKILL-0..SKILL-5`

把内部开发规范叫 "Skill"，容易让面试官联想到 Claude Skills / MCP 的 Skill 概念，造成沟通歧义。

**修正**：改成 `SPEC-0..SPEC-5` 或「模块开发规约」。

## 4. 时间线评估
