## 1. 项目梳理

### 1.1 技术栈与运行形态

| 层 | 技术 | 说明 |
|---|---|---|
| 后端 | Python 3.13 + FastAPI + LangGraph 1.2.11 / LangChain 1.4.0 | 单进程 uvicorn（`scripts/run_api.py`，绑 127.0.0.1:8000） |
| 存储 | SQLite（WAL + busy_timeout，`ThreadLocalConnection` 按线程分发）+ Chroma（向量库，`data/chroma`） | 演示单机形态，生产替换是 v2.5 议题 |
| 前端 | React 18 + Vite + Tailwind v4，自研 hash 路由 + `React.lazy` 分包 | 产物 `dist/` 有意提交，由后端静态托管 |
| 模型 | Ollama 本地（`qwen2.5:7b` / vl 变体）或任意 OpenAI 兼容云（SiliconFlow/DeepSeek） | 回退链 ≤2 级，`with_fallbacks` |

### 1.2 分层与模块划分

```
api/            HTTP 面：main.py（纯装配）+ routers/（roles/sessions/records/console/
                settings/services/domains）+ deps.py（AppContext DI + 错误映射）
core/           内核与配置面：graph.py（StateGraph 装配）、nodes.py（model/tools 节点、
                输出审核）、state.py、plugins.py（插件启停 + tool_epoch）、
                model_settings.py（模型后端表 + 供应商目录 + client_style 归一）、
                services.py（服务端点实例表 + 可用性）、ingestion.py、observability.py
rag/            检索：retriever.py（Embedder/Reranker 抽象 + 工厂）、parser.py（扩展名
                分派摄取）、ocr.py（可插拔 OCR）、chroma_store、rerank
domains/        可插拔领域插件：registry.py（DOMAINS 显式注册 + 工厂装配）+ health/
                （service/tools/schema/extract）+ finance/（数据型示例域，无工具）
roles/          角色卡服务 + 表（内置 general_assistant / medical_archivist）
storage/        db.py（connect / ThreadLocalConnection / bootstrap 按 REGISTERED 域应用 schema）
frontend/src/   api.ts（fetch 封装 + SSE）· pages/（Chat/Data/Knowledge/Roles/Plugins/
                Settings）· components/（ServicesPanel、ToolStepCard、Toast、ui/）
scripts/        run_api / smoke_check / check_consistency / init_db / ocr_worker 等
```

分层规则（现状）：`api → core → {rag, domains, roles, storage}`；`domains/registry.py` 是
唯一的域装配点（api 层不 import 具体域）；rag 不 import core（`endpoints` 参数用鸭子类型，
避免反向依赖）；前端只经 `api.ts` 触达后端。

### 1.3 核心业务逻辑（三条主线）

**① 对话主线**：`POST /api/chat`（SSE）→ 按 session 取 checkpoint → 图执行
`model → tools → model → end`。三个"热生效"支点：`enabled_domains`/`tool_epoch`/
`model_resolver` 都是**实时 callable**，插件/角色/模型变更不重建进程；system prompt 不进
checkpoint，每轮现场拼；输出审核在 `call_model` 内部（guard 规则锚定第二人称，排除否定式）。

**② 知识主线**：上传 → `ingestion_task` 登记 → `rag/parser.py` 按扩展名分派（txt/md 直读、
pdf 用 pypdf、OOXML 用标准库 zipfile+ElementTree、图片走 `rag/ocr.py` 可插拔后端）→
切片入 Chroma（scope 隔离）→ 检索时 embedder/reranker 按**服务端点行优先级**实例化 →
`search_knowledge` 内核工具按角色 `knowledge_scopes` 鉴权检索。health 域另有结构化抽取
管线（三层校验：schema 约束 → 确定性校验 → 原文锚定 grounding，双模型交叉验证只写一致项）。

**③ 配置主线**：三张配置表 + 两条热生效通道。
- `model_backend`（模型后端 CRUD + 回退链；api_key 只写不回读，GET 回掩码）
- `service_endpoint`（OCR/嵌入/重排的端点**实例**：云端行可增删改带各自 key/base_url/model，
  本地行 builtin；优先级 = sort_order 第 1 位生效；嵌入/重排变更触发 `rebuild_runtime`，
  OCR 每次上传实时读行序）
- `role_card` + `plugin`（注册在代码 `registry.DOMAINS`，启停在表）
- 热重建通道：`rebuild_runtime()` 按"有效模型配置 + 服务端点行序"重造 embedder/reranker
  → KnowledgeBase → registry → 图，一次性换装 `ctx` 三引用。

### 1.4 模块依赖与数据流向（文字图）

```
浏览器 ──fetch/SSE──▶ api/routers ──▶ core 服务层 ──▶ storage(SQLite) / chroma
                          │                │
                          │                ├──▶ domains/registry（装配工具，域隔离）
                          │                ├──▶ rag（parser/ocr/retriever 工厂）
                          │                └──▶ roles（角色卡/审计）
                          └── ctx.rebuild_runtime() ─▶ 图/KB/registry 一次性换装

数据写路径：UI 写操作 ─▶ service.commit() + roles.audit(...)（同事务或紧邻提交）
数据读路径：页面 GET ─▶ 视图组装（状态视图/目录/列表），不含密钥明文（只回掩码）
```

### 1.5 数据模型（SQLite 表清单）

| 表 | 归属 | 说明 |
|---|---|---|
| tenant / app_user / session_thread / audit_log / kernel_meta / ingestion_task | core | 租户、用户、会话、审计、内核元数据（tool_epoch/迁移 flag）、摄取任务 |
| plugin | core | 启停状态（注册在代码，启停在数据） |
| model_backend | core | 模型后端（provider=供应商 id，key 落盘明文·本地演示不出机） |
| **service_endpoint**（新） | core | 服务端点实例（category+id 主键；enabled/sort_order/builtin） |
| ~~service_policy~~（死） | core | 旧策略表，代码已退役，**仍在建表**（见 M1） |
| role_card | roles | 角色卡（内置 seed + 自定义） |
| medical_report / medical_index | domains/health | health 域富模型 |
| domain_data | core（通用） | 非 health 域的结构化数据（finance 即用此表） |
| checkpoint（langgraph 表） | 内核 | 会话状态回放 |

## 2. 问题清单

> 严重度定义：**高** = 阻碍后续扩展 / 有安全或正确性风险 / 双源真相；**中** = 债务明确、
> 近期会咬人；**低** = 卫生问题。架构类条目给出归一化方向（架构优先，不受最小改动约束）。

### 高（H）

**H1 · 服务配置双源复制：服务页与模型页各自持有云端凭据（架构）**
- 位置：`core/services.py::ServiceEndpointService`（云端行内嵌 api_key/base_url/model）；
  前端 `ServicesPanel.tsx` 的「新增云端」自由表单、「编辑」按钮、「删除」直删行。
- 问题：同一云端凭据（如 SiliconFlow key）会在模型页与服务页**各存一份**；服务页的编辑/
  删除语义跨页冲突——删服务行不删模型配置、两处改 key 互不同步。这正是"扩展性不足"的
  典型：新增一个云端账号要在两个页面重复配置。
- **归一化方向（用户已定调）**：**模型页 = 云端端点配置的唯一事实面**（provider + key +
  base_url + 模型名都在那里维护）；服务页降级为**引用面**——`service_endpoint` 行改为
  `(category, ref_backend_name, enabled, sort_order)`：
  - 新增 = 从模型页已配置的后端中**下拉选择**（不再是自由表单）；
  - 编辑 = 只在模型页（服务页去掉编辑按钮）；
  - 删除 = 仅把该后端从本服务的优先级序列中**摘除**，绝不删模型页配置；
  - 同一后端可被多类服务引用；引用的后端被模型页删除时，服务行标记失效并提示（不静默）。
  - OCR 这类非模型凭据（如 OCR.space）在模型页以"非推理凭据"形态配置，同样走引用模型。

**H2 · rebuild_runtime 无锁：并发配置变更会撕裂运行时（正确性）**
- 位置：`api/main.py::rebuild_runtime`（`ctx.knowledge/registry/app_state["graph"]` 三个
  引用分步换装，无互斥）。
- 问题：模型设置保存与服务端点变更都会触发重建；两个请求并发重建时，换装序列交错可能
  让"新图配旧 KB"之类的组合短暂存在，SSE 请求在此窗口可能用到不一致的工具集。历史上
  审计已标记过，至今未修。
- 归一化方向：重建期互斥锁（`threading.Lock`）+ 完整构建后再一次性换装（构建在锁外做、
  换装在锁内做，缩小临界区）；或引入不可变 RuntimeSnapshot 单引用替换。

**H3 · 管理面审计缺口 + 密钥入审计（安全/合规）**
- 位置：`api/routers/settings.py::put_model_settings`（**无任何审计**：默认后端、回退链、
  key 变更不留痕）；`api/routers/services.py:136`（服务端点 PATCH 的审计 detail 曾直接
  `model_dump()`，操作员填的 api_key **明文进 audit_log 且审计页浏览器可见**——本日已热修
  为"字段名清单"脱敏，需补一条回归测试钉住）。
- 归一化方向：管理面写操作统一走一个审计依赖/装饰器，密钥类字段（api_key/key）在审计
  序列化层一律脱敏（写字段名不写值）；补"密钥永不入审计"的回归断言。

**H4 · 嵌入 key 双源旁路（与 H1 合并解决）**
- 位置：`rag/retriever.py::_find_embedding_key`（env `SILICONFLOW_API_KEY` → model_backend
  的 openai 类 key 兜底）。
- 问题：服务端点行已自带 key，但工厂的 env-auto 路径与该兜底函数仍构成第二、第三 key
  来源；同一把 key 可能同时存在于 env、model_backend、service_endpoint 三处。
- 归一化方向：H1 完成后删除 `_find_embedding_key` 的 model_backend 兜底，嵌入 key 只来自
  被引用端点行；env 仅保留"首次播种引导"一次性语义（seed flag 已实现）。

### 中（M）

**M1 · 死表与死代码清理**：`core/schema.sql:106` 仍创建 `service_policy`（旧策略表，代码
已全部退役）；`core/services.py::check_availability` 里 cloud 分支已移除但函数仍保留
`"cloud_ocr"` 遗留语义注释。方向：出一次性迁移（DROP + 归档说明），schema 注释标注退役。

**M2 · finance 数据型域的边界未文档化**：finance 注册进 `DOMAINS` 但无工具 → 不出现在
`/api/tools/catalog`（行为正确），但它出现在插件启停列表、会话 `enabled_domains` 与审计里。
方向：在 `domains/registry.py` 注释与 README 明确"数据型域"概念，避免被误认为缺工具的 bug。

**M3 · 端点播种的 key 冻结语义**：`seed_once` 以 flag 保证只播一次，云端行 key 取自**首次
启动时**的 env。无 env 的环境（如当前演示 shell）播出的行 key 为空 → 需在 UI 补填；env
后来加了 key 也不会回流。方向：文档化"UI 是唯一事实源"边界；可在服务页对 builtin 云端行
提供"从 env 引导一次"按钮（显式、幂等），替代隐式期待。

**M4 · 服务状态视图的小性能与可读性**：`service_status_view` 的 models 类别调
`ms.list_backends()` 两次（items 循环一次、`effective_kind` 生成器再一次）。方向：一次取用。

**M5 · `_endpoint_dict` 弱类型**：`api/routers/services.py` 用 `e: object` + 6 处
`type: ignore[attr-defined]`。方向：给 `EndpointConfig` 加 `to_api()`（或 pydantic 视图
模型），router 不做字段搬运。

**M6 · 文档漂移（本轮改动后未同步）**：README/《技术评审与决策》尚未反映：provider 语义
变更（供应商 id + client_style）、`service_endpoint` 表与端点实例模型、finance 数据型域、
对话菜单模型名主选。方向：改造批次里带一次文档对齐（consistency 脚本可加"service_endpoint
在 README 出现"类断言）。

**M7 · 审计与列表无限增长**：`audit_log` 只读侧有 limit=100，但表本身无保留策略；domain
数据/会话列表无分页。演示可接受，公网部署前需定保留策略。

**M8 · 部署期安全清单（沿用旧审计未清项）**：A1 密钥落盘明文（生产换 secret manager）、
P6 无限流、P3 CI 未真跑。当前绑 127.0.0.1 + 默认无鉴权是演示形态，公网前必须开
`AUTH_MODE=on` 并重估这三项。

**M9 · ChatPage 巨石（~740 行）**：会话栏/功能行/上传/抽取/模型菜单/深浅色适配同居一文件，
状态 20+。方向：沿用 S4 组件库路线渐进拆分（会话栏、功能行、上传区各自成组件）；非紧急。

### 低（L）

**L1 · api.ts 删除方法命名**：泛型删除叫 `del`、领域记录叫 `deleteDomainRecord`（语义一致
但命名不齐）。方向：统一 `del` 为底层、包装器统一动词。

**L2 · 测试脚本卫生**：本会话的 CDP 驱动脚本留在 TEMP 未入库。CDP 实测抓到过 vitest 抓不
到的 UI 断层（按钮文案/序列化假象），建议沉淀一条最小化 CDP 冒烟入 `scripts/`（可选）。

**L3 · `settings.put_model_settings` 的凭据预检与 save 内归一化的顺序耦合**：预检用**原始**
provider 判断 keyless，save 内才归一化；若未来目录加入"归一化后变 keyless"的新别名，预检
会误报缺 key。方向：预检复用 `normalize_provider` 后的值判断。

**L4 · 会话误触积累**：对话页未建会话时切角色/模型即静默建会话（产品语义如此），误触会留
下空会话。方向：空会话（无消息）在列表聚合或自动清理，属 UX 细节。
