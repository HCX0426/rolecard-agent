## 1. 要解的痛，和今天缺的那两格

今天这张卡（设置 → 记忆与任务目录）能对一条记忆做四件事：**钉住 / 要紧程度三档 / 删除 / 手动加一条**。
缺的两件恰恰是"记忆池脏了"之后唯一有用的两件：

| 今天能做 | 今天不能做 | 后果 |
|---|---|---|
| 删掉一条 | **改一条的文字** | 事实本身是对的、话说错了（"用户住在北京"其实后来搬去上海了）→ 只能删了重打，`hit_count`（用过几次）与来路一起丢 |
| 「整理记忆」（模型批量 MERGE/INVALID） | **人工合两条** | 模型不在场、或它合得不对时，用户只能"清池重抽" —— 这是这个项目里最老的那句抱怨 |

`PATCH .../item/{id}` 的后端**早就有**（`edit_item`），只是界面把文本渲染成了只读；
合并端点是这一稿新加的（见 §5）。

```
│ └                                                        │          │

│ ┌──────────────────────────────────────────────────────────────────┐│
│ │○ 用户住在上海，在一家医院工作                          [改] [📌] [删]││
│ │  ai 检测 · 用过 4 次 · 要紧程度 [ 要紧 ▾ ]                         ││
│ ├──────────────────────────────────────────────────────────────────┤│
│ │○ 用户养了一只猫，叫雪球                    [改] [取消钉住] [删除]  ││
│ │  手动 · 用过 0 次 · 已钉住 · 要紧程度 [ 一般 ▾ ]                   ││
│ └──────────────────────────────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────────┘
```

三处变化，其余一格不动：

1. 每行行首多一个**勾选框**（只在"选了至少一条"时才长出顶上的「合并 (N)」，见 §3）。
2. 每行的操作里加一个**「改」**（不是把文本直接变成可编辑 —— 理由见 §3.1）。
3. 元信息那行（来源 · 用过 N 次 · 钉住 · 要紧程度）**一字不改**，只是被 `改` 撑开时整行进入编辑态。

## 3. 两个动作的形状

### 3.1 「改」= 行内换成输入框，回车存、Esc 撤

```
┌──────────────────────────────────────────────────────────────────┐
│ │ 用户住在上海，在一家医院工作                                    ││  ← 单行输入框，宽度=整行
│ │ [ 21/200 ]                        [ 取消 ]  [ 保存 ]           ││
│ └──────────────────────────────────────────────────────────────────┘
```

- **为什么不"直接可编辑"（contenteditable 那一套）**：这一行右边还挂着三个控件，
  点哪儿算编辑哪儿、点哪儿算选勾选框会变成一堆歧义；而"看得见字数上限"这件事
  只有独立输入框能干净地做到（200 字是后端的硬上限 `MAX_ITEM_CHARS`，超了会被**截断**，
  不报错 —— 所以计数器不是装饰，是"再打下去要被切掉"的唯一提示）。
- **保存走已有的 `PATCH`**（`text` 那一支），保存成功后这一行回到常态、`Toast` 说"已更新"。
- **空文本 = 不改**（后端 `edit_item` 今天就是这个口径：空串交给删除去做那件事）。
  所以界面在文本被清空时把「保存」置灰，而不是存一个空句子。
- Esc 与「取消」都是放弃本地改动，不发请求。

### 3.2 「合并」= 勾两条 → 一个可编辑的预填框 → 确认

```
勾了两条之后，顶上长出来这一条（不是浮层，就在列表上方）：
┌──────────────────────────────────────────────────────────────────┐
│ 已选 2 条                                       [ 取消选择 ]       │
│ 合并成一条：                                                       │
│ ┌──────────────────────────────────────────────────────────────┐ │
│ │ 用户住在上海；用户在上海一家医院工作                            │ │  ← 预填=后端那个兜底拼法
│ └──────────────────────────────────────────────────────────────┘ │
│ [ 21/200 ]                        [ 取消 ]  [ 合并（留 1 条） ]    │
└──────────────────────────────────────────────────────────────────┘
```

- **只能勾两条**（不是 N 条）：`merge` 这条链是"谁取代了谁"，两条之间才成立；
  三条一起合的话，被合掉的两条都指向同一条，来路就糊了。勾第三条时顶上的框说
  "一次合两条"，并把先勾掉的那条取消 —— **不做多选下拉**（Cursor/ChatGPT 的记忆面板也都没做批量合并）。
- **预填那句就是后端的兜底写法**（两句用「；」拼起来，超 200 字截断）。它是**起点不是结果**：
  用户在这个框里把句子改顺，改完点「合并」才发请求。
- **留下的那条 = 先勾的那条**。它的 `id`、`created_at`、`hit_count`、`pinned`、`importance` 全部保留；
  后勾的那条退役（`invalidated_at` + `superseded_by` 指向留下的那条），**不物理删**。
  界面上明说这一点：按钮文案是「合并（留 1 条）」，旁边的说明写"另一条会被退役，不删，可回滚"。
- **钉住不参与判定**：勾了两条、其中一条钉住 → 照样能合（钉住的意思是"不参与**自动**淘汰与整理"，
  用户手动要合就是用户的意思）。但**留下的那条如果是没钉住的那条**，钉住状态就跟着掉了 ——
  所以顶上的框在"先勾的那条没钉住、后勾的那条钉住"时提示一句：
  "会留下『未钉住』的那条，钉住状态不跟着搬。要反过来留那条，先点掉这条的勾选再按顺序重选。"
  （这是"顺序有含义"这件事唯一的代价，说清楚比偷偷帮你换更好。）
- 合并成功后列表刷新、`Toast` 说"已合并成一条"。

### 3.3 为什么不做"撤销"按钮

退役本来就是可回滚的（只写了两个标记列），但**这一稿不做 UI 撤销**，理由不是省事：
撤销要把"谁被我合掉了"做成一个可操作的列表，而那需要一个新的读端点（今天没有任何读端点
会给出已退役的条目），加一个端点就要给它定分级、定测试、定界面位置。真要撤销，
现在的路径是：角色页的「事件簿」看得到"哪天更正了什么"（只读），加上"手动记一条"把话说回来。
这一稿先把这个缺口**写清楚**而不是假装它没了。

## 4. 复用了什么，不新造什么

| 需要的东西 | 用现成的 |
|---|---|
| 输入框 / 按钮 / 计数 | `components/ui` 里那套（`Input`/`Button`），与同一张卡里"手动记一条"那个输入框同款 |
| 破坏性动作的二次确认 | `useConfirm` —— 但**合并不弹确认框**：它已经在"顶上那条"里给了可编辑的句子和「取消」，再弹一层是把同一个决定问两遍 |
| 结果提示 | `ToastProvider`（与"已钉住 / 已删除"同一处） |
| 一个写点 | 所有写都走 `PATCH`/`POST` 到 `settings.py` 那几个端点，界面不本地改状态再"顺手保存" |

参考的是 ChatGPT 的 Memory 面板（一条一行、行内编辑、只能逐条删）与 Cursor 的 Rules
列表（勾选 + 顶部批量条），两家的共同点是**没有**"批量合并"这种大动作 —— 记忆这种东西，
用户一次只敢确认两条。

## 5. 后端契约（这一稿已落地，界面照它画）

```
POST /api/settings/memory/item/{keep_id}/merge/{drop_id}
     body: { "text": "合并后的句子" }        # 可省 → 退回"两句拼一起"
     200 → 与 GET /api/settings/memory 同形状的载荷（含刷新后的整桶）
     400 → 自己跟自己合 / 跨桶（全局 ↔ 某角色）合
     404 → 任一条不存在
```

三条挡在门口的判定都不是参数校验，是"这一步会不会污染记忆"：
**跨角色的"合并"其实是把一个人的事实搬进另一个人的脑子**，那是污染不是整理，所以直接拒。
零迁移：`invalidated_at` / `superseded_by` 两列本来就在表里（不变式 15 的那条"退役不物理删"）。

## 6. 代价与顺序

| 项 | 代价 | 说明 |
|---|---|---|
| 行内编辑（§3.1） | 1 文件 / ~40 行 / 半小时 | 纯前端，端点早就有 |
| 勾选 + 合并框（§3.2） | 1 文件 / ~90 行 / 1.5 小时 | 含"只许两条""顺序决定留哪条"两处提示的文案 |
| 用例 | 前端 vitest ~6 条 / 后端已 1 条 | 后端那条已钉住"链还在"（看落库形状，不看接口口径） |
| 撤销 UI（§3.3） | **不做**，另计 | 要先加一个"读已退役条目"的端点并定分级 |

建议顺序：**先做 §3.1 那半**（最小、纯前端、当天就能用），看完手感再做 §3.2。
两半之间没有依赖，合并那半不需要编辑那半先存在。
