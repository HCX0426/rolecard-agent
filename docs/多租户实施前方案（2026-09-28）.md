- **形态**：`app_user` 长出第二行之后，同一台（或两台）实例上两个身份互相不可见 —— 列表里没有、
  进不去（404 不是 403）、改不掉。M6 已经为"一台实例、两次登录"把这个断言跑通。
- **边界**：`service_endpoint` 的默认/回退序列与 `token_usage_day` 是最后两张"真欠决断"的表
  （架构总览 §4.1 M2 的尾巴）；其余表的取舍在 M2 系列已定（继承/设备级，各有用例钉着）。

## 3. 第一件：`service_endpoint` 的归属切法（已按方案 A 落地）

这一张列最绕 —— 因为一行里**混着两种语义**（`category` 见 schema 注释）：

| category | 它回答的问题是 | 该跟谁 |
|---|---|---|
| `ocr` / `embedding` / `rerank` | "这台机器用什么能力解析/检索引擎" | **设备**（换个人不变；M2 的 `ServiceEndpointService(owner=…)` 是构造期收的实例主人） |
| `chat`（引用行） | "**这次对话的默认后端与回退链是啥**" | **跟人**（与 `model_provider` 同族：花谁的 key 由谁定） |

**落地的是方案 A**：`service_endpoint` 加可空 `user_id`（老 chat 行回填本机主人）。语义定死：
**仅 `chat` 引用行按人过滤，能力端点（ocr/embedding/rerank）永远设备级**（`user_id` 恒 NULL）。
`effective_for` 里那句"对话默认从那一条**本身份的** chat 引用取" —— 界面的"当前默认"从此对得上
实际跑的那台；A 存一次对话序列不会抹掉 B 的。

**迁移**：`_migrate` 一次做完「加列 + 回填」两步（补列器不碰这张表，因为它属于
`_SHAPE_MIGRATED_TABLES`）—— 只见加列、没回填，老单身份库一升级对话默认就当场消失。
其余 chat 引用行的写入口（服务页序列、模型页整表保存、添加/删除模型、env 播种、入层迁移）
全部显式带主人。

## 4. 第二件：`token_usage_day` 的归属（已按方案落地）

PK 现在是 `(day, backend)` —— 用量按天×后端累计。"花谁的 key"已经是按人解析的（09-28），
但**账本本身没人**：多身份共库时，两个身份各自的用量会累计进同一格。

**落地（B1a）**：PK 改 `(day, user_id, backend)` **整表重建**。写入点 `record_usage` 加
`user_id` 参数；PK 迁移走"建新表→导旧数据（旧行为 `local-user`，语义是"上线前测得的使用"）→
删旧表"。与 `role_proactive_state` 一样，是"换主键"那类一次性工程。
**不做**的情形成立吗：单个身份自用形态下，拆不拆都能用；但"多租户"那天它**必须**拆 ——
不拆的话用量页会把两个人的钱混成一行，而"花钱"恰恰是按人解析才成立的。所以这一步**不放在
"等真有多身份"**里，跟着多租户第一批走（已走）。
