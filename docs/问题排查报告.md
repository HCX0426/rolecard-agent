# rolecard-agent 项目排查报告

> 排查时间：2026-09-16 ｜ 范围：后端 `src/`（core / api / rag / domains / roles / storage）、前端 `frontend/src/`、脚本与测试
> 方法：直接通读核心模块源码（非凭记忆），按代码质量 / 逻辑正确性 / 性能 / 安全 / 可维护性 / 架构分层六个维度审查。
> 结论基调：整体工程质量**高于一般个人项目**——分层清晰、文档充分、测试覆盖广（pytest 291、smoke 12/12、一致性 23/0、ruff clean）。以下问题多为中低频，但有两处是**真实功能缺陷**，应优先修。

---

## 一、总体架构（正面，先说清楚）

- **分层合理且意图明确**：`api`（接入）/ `core`（内核：图、节点、工具注册、插件、服务策略）/ `rag`（检索）/ `domains`（可插拔领域）/ `roles` / `storage`。每个模块都有详尽的 docstring 解释"为什么这样设计"，读起来能还原决策过程。
- **图编译一次、策略实时生效**：`core/graph.py` 编译一次，`enabled_domains` / `tool_epoch` / `model_resolver` 全用 callable 实时读取，插件启停/切角色/换模型无需重启——这是本项目最值得称道的设计。
- **权限模型正确**：工具过滤分两阶段（启用域 → 角色白名单），在 `bind_tools` 前就过滤，模型根本看不到无权工具；检索作用域由内核注入、模型无法指定集合。输出 guard 在 `call_model` 内部（不可被边绕过），fail-closed。
- **安全细节到位**：`api_key` 写-only 不回读；tracer 按 key 脱敏；认证用常量时间比对；`fail-closed` 的 `on` 档无凭证即全拒。
- **可测试性**：`build_kernel` 接受注入模型、`Settings`/`ServicePolicy` 纯函数可单测、DB 可注入临时库。

## 二、问题清单（按严重程度）

### 🔴 高 — 真实功能缺陷（建议优先修）

**H1. 重排器（reranker）的 key 只从环境变量读，配置页保存的 key 不生效**
- 位置：`src/rolecard_agent/rag/retriever.py` `make_reranker()` 第 250 行 `key = os.environ.get("SILICONFLOW_API_KEY")`。
- 对比：`make_embedder()` 用的是 `_find_embedding_key(settings)`，该函数会**先查 env、再查 DB 合并后的后端配置**（设置页存的 key）。
- 影响：用户在「模型」页签填入 `SILICONFLOW_API_KEY`（落 DB）后，嵌入器能正常工作，但**重排器因为只读 env 而永远为 None**——"检索重排"服务端开关形同虚设，且界面没有任何提示。这是刚交付的「服务」模块里的一个沉默失败。
- 建议：让 `make_reranker` 也走 `_find_embedding_key(settings)`（或把 key 解析统一提到 `Settings` 上），与 embedder 完全对齐。

**H2. `rebuild_runtime` 热重建是无锁的多步状态替换（并发下可能观察到不一致）**
- 位置：`src/rolecard_agent/api/main.py` `rebuild_runtime()`（274–320 行）依次赋值 `ctx.knowledge = knowledge_new` → `ctx.registry = registry_new` → `app_state["graph"] = graph_new`，三步之间**没有任何锁或原子容器**。
- 影响：设置页/服务策略保存（PUT）触发热重建的瞬间，若恰有进行中的对话请求，可能读到"新 KB + 旧 registry"或"新 registry + 旧 graph"的过渡态。单进程、低频管理操作下概率低，但在并发流量下是确定的正确性隐患（搜索工具闭包持有 KB，graph 持有 model_resolver，三者需一致）。
- 建议：把 `knowledge / registry / graph / effective / default_model` 收进一个不可变 `Runtime` 对象，一次性 `app_state["runtime"] = new_runtime` 替换；或用一个 `threading.Lock` 包住整个替换。前端每次请求从同一容器取，杜绝半换装。

### 🟠 中 — 架构耦合 / 可维护性 / 数据安全

**M1. 分层倒置：`core` 反向依赖 `rag` 的私有符号**
- 位置：`src/rolecard_agent/core/services.py` 第 193 行 `from rolecard_agent.rag.parser import _default_ocr_python`、第 204 行 `from rolecard_agent.rag.retriever import _find_embedding_key`。
- 影响：`core` 概念上是更底层的基础设施层，却去 import `rag`（更高层能力）的**下划线私有函数**。可用性检测逻辑（`check_availability`）本属数据层，却直接窥探 rag 内部；一旦 rag 重构重命名这些私有符号，`core` 会静默崩。这是最典型的耦合味。
- 建议：把"OCR 解释器是否就绪 / 嵌入 key 是否存在"这类**能力探针**提到 `rag` 公共 API（如 `rag.availability.ocr_ready(settings)` / `rag.availability.embedding_key(settings)`），`core/services` 只调用公共面。

**M2. 热重建泄漏 httpx / Chroma 客户端句柄**
- 位置：`rebuild_runtime`（同上）每次保存都 new 一个 `SiliconFlowEmbedder` / `SiliconFlowReranker`（各自 `httpx.Client`）和新的 `KnowledgeBase`（`chromadb.PersistentClient`）。旧实例**从不 `.close()`**。
- 影响：反复改设置会累积未关闭的 httpx 连接与 Chroma 文件句柄，长时间运行的进程可能耗尽连接/句柄。
- 建议：在替换前 `close()` 旧 KB 与旧 embedder/reranker（给它们加 `close()`，Chroma client 用 `close()`）；或把 embedder/reranker 做成可复用单例，仅在 key 真正变化时重建。

**M3. 工具重试不区分幂等性，写类工具可能被重复执行**
- 位置：`src/rolecard_agent/core/nodes.py` `execute_tools()` 第 307–329 行，对任意工具失败**用相同参数重试最多 2 次**；`ToolSpec` 无 `idempotent` 标记。
- 影响：领域工具里有写操作（`domains/health/tools.py` 的 `upload_medical_report` 写 ingestion 台账；`records` 补录/抽取写库）。若工具在**部分产生副作用后**抛异常，盲目重试会重复写入。`upload_medical_report` 自身有 sha256 幂等键兜住，但框架层面不保证其他写工具安全——这是数据完整性隐患。
- 建议：`ToolSpec` 增加 `idempotent: bool`（默认 False）；`execute_tools` 只对 `idempotent` 工具重试，写类工具失败直接返回 `TOOL_FAILED` 并由 tracer 留痕。文档需明确"工具若写副作用必须自带幂等"。

**M4. 没有数据库迁移机制（运维天花板）**
- 位置：`src/rolecard_agent/storage/db.py` 文档明确写 "No migrations in v1"，全是 `CREATE TABLE IF NOT EXISTS`。
- 影响：改 schema（加列/改约束）后，旧 `app.db` **不会自动演进**，只能 `rm app.db` 重建——已有演示数据全丢。生产化前必须引入 Alembic 或等效迁移。当前是已知 v1 折中，但属于会卡住"公网部署"的硬限制。
- 建议：v2.5 生产化阶段引入 Alembic；在此之前至少在 README 显著标注"升级前备份/重建 DB"。

**M5. 前端巨石组件 + 组件库半途而废**
- 位置：`frontend/src/pages/`：`ChatPage.tsx` 33.7KB（~900 行）、`RolesPage.tsx` 25KB、`SettingsPage.tsx` 20KB、`DataPage.tsx` 20KB。S4 建的 `components/ui/`（Button/Card/Switch/Tag）**实际只被 2/6 页面引用**（PluginsPage 用 Switch、DataPage 用 Tag；ChatPage/KnowledgePage/RolesPage/SettingsPage 全部内联 Tailwind）。
- 影响：4 个大页面把 UI + 取数 + 状态揉在一起，改动成本高、回归风险大；`Card`/`Button` 几乎无人用，成为冗余。可维护性与扩展性受限。
- 建议：以 `ui/` 为单一组件出口，分两批把 RolesPage/SettingsPage/ChatPage 的重复片段抽成 `Card`/表单组件；删掉未使用的 `Button`/`Card` 或强制采用，消除"两套样式"漂移。

**M6. 前端"写"路径长期未被端到端测试覆盖（流程教训）**
- 背景：`api.ts` 曾漏 `JSON.stringify(body)`，导致浏览器里所有写操作静默 422，而四门后端测试（pytest/smoke/一致性/ruff）全绿——因为它们直连 API，绕过了前端契约。
- 影响：仅有的护栏是事后补的 `test_frontend_contract.py`（静态检查）。没有真实"前端写操作→后端"的 E2E，类似契约错误仍可能漏。
- 建议：加一个 vitest + 轻量 mock server（或 Playwright 冒烟）验证一次真实 `PUT/POST` 往返；或把 `api.ts` 的契约独立成可单测模块。

### 🟡 低 — 代码质量 / 性能 / 部署细节

**L1. 嵌入/重排的 `base_url` 写死 env-only**：`SILICONFLOW_BASE_URL` 仅 env 可读，设置页无法改；与"DB 覆盖 env"的整体策略不一致（见 H1）。低。

**L2. `service_status_view` 冗余计算**：`check_availability` 对同一候选被多次调用（排序、循环、降级判定各算一遍），每次还重新 import 解析 key。量极小，仅风格问题。低。

**L3. `call_model` / `turn_context` 每轮各读一次 DB**（角色、启用域）。功能正确（实时生效），但可用 `ThreadLocalConnection` 上的短缓存削峰；并发高时才有意义。低。

**L4. 新增一个服务后端要改多处**：候选列表在 `core/services.py`、实际提供方在 `rag/parser.py` + `rag/ocr.py` + `check_availability`，责任分散（与 M1 同源）。扩展性扣分项。低。

**L5. 认证默认 `off` 且未配 CORS / 限流**：本地演示可接受，但公网部署必须把 `AUTH_MODE=on` 写进部署清单，并补 CORS（当前控制台同源静态托管，无跨域需求）。低。

**L6. 测试文件放在 `src/`**：`frontend/src/api.test.ts` 与源码同目录（通常应进 `tests/` 或 `__tests__`）；`vite build` 不会打包未引用的 `.ts`，但结构不规范。低。

**L7. `api.test.ts` 中 SSE 解析**：`streamChat` 按 `\n\n` 分帧、取 `data: ` 行——与 `api/chat.py` 协议耦合，协议字段改了需要前后端同步；建议把事件 schema 也进 `api.ts` 的类型契约（已部分做）。低。

## 四、优先修复建议（仅列出，未执行）

1. **H1** 最小改动、最高性价比——统一重排器与嵌入器的 key 解析来源（推荐 `Settings` 上新增合并字段）。
2. **H2 + M2** 一起做：把运行时对象收进不可变 `Runtime` 容器，一次性替换并 `close()` 旧资源。
3. **M3** 给 `ToolSpec` 加 `idempotent` 标志，写类工具不重试。
4. **M1** 把 rag 能力探针提到公共 API，消除 core→rag 私有依赖。
5. **M5** 渐进地把 RolesPage/SettingsPage/ChatPage 迁到 `ui/` 组件。
6. **M4** 列入 v2.5 生产化清单（Alembic）。
