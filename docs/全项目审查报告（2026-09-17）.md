## 2. P0 —— 不可逆损失或服务不可用

> **状态：三条已全部修复（同日，见文末"修复记录"）。** 保留原文以便对照问题本身。

### P0-1 工具循环无上界，`recursion_limit` 用库默认值 10007

- **位置**：`src/rolecard_agent/core/nodes.py:551`（`route_after_model` 只要模型返回 `tool_calls` 就无条件回到工具节点）+ `src/rolecard_agent/api/routers/sessions.py:251`（`graph_config` 里只有 `configurable.thread_id`）
- **影响**：模型只要持续返回 `tool_calls`（提示注入、模型抽风、或工具总是报错被反复重试），整轮对话**不会终止**。云端后端 = 数千次真实计费调用；checkpoint 持续膨胀；SSE 长时间无响应且界面没有中断理由，用户只能杀进程。
- **证据**：
  ```
  $ grep -rn "recursion" src/ tests/          # 无任何命中（从未设置）
  $ ./.venv/Scripts/python.exe -c "from langgraph._internal import _config; print(_config.DEFAULT_RECURSION_LIMIT)"
  10007
  ```
- **建议**：在 `graph_config` 显式 `{"recursion_limit": N}`（如 25），并把 `GraphRecursionLimit` 转成可读中文错误 + 落审计；顺带对"同一工具同一参数连续重复调用"做熔断。

### P0-2 向量索引以「文件名」为键，同名不同文件静默互相覆盖

- **位置**：`src/rolecard_agent/api/routers/sessions.py:637`（`ctx.knowledge.index("health_reports", safe_name, text)`，传的是**原始文件名**）→ `src/rolecard_agent/rag/retriever.py:387`（`_chunk_ids` = `md5(f"{source}:{i}")` 确定性推导）→ `:439`（同 id upsert）
- **影响**：落盘用的是 `<uuid8>_<name>`（不会撞车），但**索引 key 用的是原始文件名**。`报告.pdf` / `IMG_0001.jpg` 这类重名在真实使用里必然出现：后上传的文件直接 upsert 覆盖同 id 分块，**先前的知识永久消失且无任何提示**，检索会拿错文档的内容回答。
- **证据**：
  ```
  sessions.py:523  safe_name = _sanitize_filename(Path(file.filename or "report.bin").name)   # 索引用它
  sessions.py:637  chunks = ctx.knowledge.index("health_reports", safe_name, text)
  retriever.py:387 return [hashlib.md5(f"{source}:{i}".encode()).hexdigest()[:16] for i in range(n)]
  ```
- **建议**：source 换成稳定且唯一的键（ingestion task id 或 `sha256` 前 16 位 + 原名），文件名只作为元数据展示；`index()` 的 docstring 已承诺"同 source 幂等"，键选错让这个契约变成数据杀手。

### P0-3 本地 Ollama 后端的 `timeout` 被静默丢弃，挂起即拖停整个对话服务

- **位置**：`src/rolecard_agent/core/graph.py:142`（`kwargs["timeout"] = int(settings.model_timeout_seconds)`）
- **影响**：这是**默认主路径**（本地 `ollama`）。`ChatOllama` 不认 `timeout` 参数，必须走 `client_kwargs`。模型挂起时（显存不足、模型正在换入换出、服务假死）请求**永不超时** → `with_fallbacks` 永不触发 → SSE 永不结束 → `_CHAT_POOL` 的 8 个线程被逐个占死 → 整个对话服务拖停。`graph.py` 上方的注释写着"本地模型挂起会让 SSE 与 fallbacks 永久等待"，但代码实际没解决。
- **证据**（实测同一参数在两类后端上的落地情况）：
  ```
  init_chat_model(model='qwen2.5:7b', model_provider='ollama', timeout=120)
    → 类: ChatOllama | 有 timeout 属性: False | client_kwargs: {} | 底层 httpx timeout: None
  init_chat_model(model='gpt-4o-mini', model_provider='openai', timeout=120, api_key='sk-x')
    → request_timeout: 120.0        # 云端这条路是对的
  ```
- **建议**：按 provider 分别传参（ollama → `client_kwargs={"timeout": N}`），并补一条**真正断言客户端超时值**的测试（现有 `tests/unit/test_model_kwargs.py` 把 `init_chat_model` patch 成假函数，只断言 kwargs 字典，所以这条漏网）。

## 4. P2 —— 改进项

### 4.1 性能
- **每 token 全量重算 + 全量重渲染**：`ChatPage.tsx:262`（`buildTurns` 无 `useMemo`）、`:283`（`ctxUsed` 每渲染 O(n)）、`:344`（每个 token 换新对象 `setLive`）。数百条历史时每个 token 都重跑 O(n) 扫描并重渲染全部轮次。
- **自动滚动绑在 `[messages, live]`**：`ChatPage.tsx:160`。生成期间想往上翻历史会被立刻拽回底部（实测 5 个 token 触发 4 次 `scrollTo`）。
- **服务页对同一端点重复探活**：`core/services.py:450`（填 `item`）与 `:458`（选 `effective`）各调一次 `endpoint_available`，而该函数对视觉类端点是真的 3s HTTP 探测 → OCR 分类 3 行最坏约 18s 白屏。
- **`DOWNLOAD_MAX_BYTES` 名不副实**：`core/tools/web.py:171`，`resp.text[:2MB]` 是**先整包读进内存再按字符截断**，一个 1GB 响应即可打爆进程内存。
- **每次 consensus 新建 N 个模型客户端且从不关闭**：`core/consensus.py:53,73`（`model_builder(name)` 每次实例化）；模型客户端全项目无缓存、无 `close()` 路径。
- **同步阻塞调用放在 `async def` 路由里**：`api/routers/sessions.py:230`（chat）、`:328`（edit/regenerate）内直接 `conn.execute` / `graph.get_state`，卡事件循环，其它会话的 SSE 一起变慢。
- **无分页**：`/api/records`（`records.py:117`）、`/api/session/{id}/messages`（`sessions.py:415`）、`/api/knowledge`（`console.py:52`）全量返回（仅 `/api/audit` 有游标分页）。
- **N+1 查询**：`domains/health/service.py:216` 每条报告一次子查询；`core/services.py:204` 的 `_backend_map` 每次调用全表重读。

### 4.2 健壮性与一致性
- **无 lifespan / shutdown**：`api/main.py:421`，`conn.close()`、`KnowledgeBase.close()`、`_CHAT_POOL` 从不释放（测试里表现为 `ResourceWarning`）。
- **静默 `catch` 导致页面永久加载中**：`DataPage.tsx:11`（`.catch(() => undefined)` → 永远"正在加载领域…"）、`ChatPage.tsx:136,148,151`（模型/角色加载失败 → 菜单空白）、`RolesPage.tsx:91,96,101`。
- **`reset_scope` 吞掉全部异常**：`rag/retriever.py:612` + `routers/console.py:68`，非法作用域也返回 `removed_chunks: 0` 并写审计，用户以为清空了。
- **消息级删除不清理旧 checkpoint**：`api/routers/sessions.py:347,391`，`update_state` 只追加新 checkpoint，被"删除"的原文仍留在 `checkpoints` 表里可恢复。
- **`patch_session` 分两次 commit**：`sessions.py:180,197`，title 更新失败会留下半套变更。
- **同一 thread 并发 `POST /api/chat` 无互斥**：`sessions.py:221-288`，两请求各自 `get_state` 后各自注入 input，checkpoint 交错写入。
- **502 响应体未脱敏**：`api/routers/records.py:220`（`detail=str(exc)`），而同函数的审计分支用了 `scrub_endpoints(...)`——模型异常常带内部 `base_url`，会原样回给客户端。
- **上传/解析的空结果只有 `parsed` 状态**：`sessions.py:649`，扫描件 PDF 无文本层时用户看不到任何提示。

### 4.3 安全（自用场景下优先级低，但成本也低）
- **请求体长度上限不一致**：`sessions.py:431`（`/api/prompt/enhance` 的 `text` 无上限）、`:298`（`/messages/edit` 的 `content` 无上限）、`:341`（`message_ids` 无 `max_length`），而 `:89` 的 `ChatMessage.message` 有 8000 上限。
- **服务层就地拼列名**：`core/domain_data.py:101`（`", ".join(f"{k} = ?" ...)`），当前不可注入仅仅因为上层 Pydantic 模型没有 `extra="allow"`——服务层自身不设防。
- **`react-markdown` 把 `node` 属性铺进真实 DOM**：`components/Markdown.tsx:20-60`，实测渲染出 `<p class="x" node="[object Object]">`（react-markdown 10.1.0 的 `passNode`）。

### 4.4 可维护性
- **分层违规**：`api/routers/domains.py:71-110` 路由层直写 SQL（沿用上一轮评审结论）。
- **死代码**：`components/ui/Card.tsx` 经 barrel 导出但全项目零引用；`api.ts:320,322,380`（`getProviders` / `getKnowledgeScopes` / `deleteMessages`）导出零调用——契约只改一处、另一处静默失效；`lib/stream.ts:52` 的 `StreamMeta.role` 无人消费。
- **同一逻辑两处实现**：前端删除所选消息在 `api.ts:380` 与 `ChatPage.tsx:485` 各有一份路径。
- **类型是手抄两份**：SSE 帧在 `api.ts:431,487` 只校验 `type` 是字符串就 `as ChatEvent`，后端字段改名既不会被 tsc 也不会被运行时发现。
- **超大文件**：`ChatPage.tsx` 1164 行、`SettingsPage.tsx` 770 行、`DataPage.tsx` 661 行；后端 `sessions.py` 678 行、`retriever.py` 660 行。
- **无障碍**：对话列表是 `div+onClick`（键盘不可达，`ChatPage.tsx:562`）；模型/角色菜单无 `Esc` 关闭、无 `aria-expanded`（鼠标移出是给鼠标的，键盘用户没有第二条退路）。
- **仓库卫生**：`start.bat:19-23` 硬编码 `D:\code\Ollama` 与 `qwen3-vl:8b`（本机专属路径进了仓库）；`docs/` 10 个 md 无索引。
