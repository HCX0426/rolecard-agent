# 细粒度权限审查（2026-10-09）

> 范围：HTTP API 的鉴权与授权面。产出形式：只读审查（本文件 + 账本一格），
> 不改行为 —— 发现的观察项逐条给出处置建议，是否实施另定。

## 0. 结论

**现有权限机制四层齐整，未发现可越权的洞**。本次审查没有产生"必须修"的缺陷；
下文 §4 有 3 条观察项（2 条是文档/口径类，1 条是低危加固建议），供拍板。

## 1. 机制全景（四层，自外向内）

| 层 | 出处 | 判据 |
|---|---|---|
| ① 来源标识护栏 | `auth.origin_guard_violation`（R102-45） | off 档：Host 必须回环（防 DNS rebinding）；全档：Origin 必须同源（`Origin: null` + `Sec-Fetch-Site: cross-site` 仍拒） |
| ② 认证 401 | `auth.auth_required` | `off`=全放（语义=本机单人）；`on`=一律要凭据（无凭据可配也拒，fail-closed）；`auto`=非回环要凭据；豁免名单**精确路径**（`_exempt_hit`，`GET /path` 单方法形态；宽前缀形状已废） |
| ③ 分级 403 | `access.allowed`（main.py 中间件） | operator 面 = **本机来源 或 operator 凭据**；`roles_declared` 未声明任何 `operator:` 时分族关闭（单人兼容，写明理由）；user 档清单 `USER_ROUTES` 逐条写明"为什么在这一档"，**未表态默认 operator**（fail-closed） |
| ④ 资源归属 | 各路由 + storage | 数据读写一律 `user_id=ctx.current_user()` 盖章；无任何路由接受路径参数里的 user_id（全仓 grep 0 命中） |

另有两条**跨层**机制：
* **出站目标护栏**（`access.outbound_target_allowed`，R102-58）：user 档的 `/api/sync/*`
  只能推到回环或 operator 允许清单里的地址 —— 关掉的是"持 user 凭据把全量数据推到
  自己服务器"那条洞；来源 IP 与 roles_in_effect 由中间件挂 `req.state`，路由**不重算**
  （第二份实现的口子被 docstring 明令封死）。
* **审批决定令牌**（`decide_token`，R102-46）：读侧令牌只发给 operator（或 off 档本机）；
  decide 时 operator 可用凭据做第二因子，off 档匿名必须持令牌 —— "猜自增 id 就批"与
  跨源盲 POST 两头都堵。

## 2. 逐层验证过的要点（审查时实际查过的，不是泛泛而谈）

1. **XFF 伪造链**（`auth.client_ip`）：默认只认 TCP 对端；可信代理网段内才解析 XFF，
   且**右向左**跳可信跳、链内回环=伪造签名整链作废 —— 追加式反代 + 注入 `127.0.0.1`
   的旧洞（docstring 里的 curl 复现）已被两代修正盖住。
2. **常量时间比较**（`auth._eq`）：按 UTF-8 字节比（中文口令 500 那次的修复仍在位）。
3. **匿名身份的 role 恒为 user**（`Actor` 默认），不会因"没配 operator 凭据"升级成 operator
   —— 升级靠 `roles_in_effect=False` 的兼容分支，语义单测在 `tests/test_auth.py:282-288`。
4. **user 档越权**：sessions/records/reachouts/memory 全族按 `current_user()` 过滤；
   `patch_memory_item` 里的 `owner` 是 `current_user()` 的同值别名（读原码核实，非第二个事实源）。
5. **限流**在认证之后、按身份 + 来源分桶；本机来源不设卡（与 403 层同一信任模型，注释写明）。
6. **operator 面点名清单**（access.py L83-91）：settings.runtime / services / mcp /
   plugins toggle / workspace / approvals decide / local-service / shell-release / audit ——
   逐条与 USER_ROUTES 对照过，无重复、无遗漏档位冲突。
7. **配套用例**：`test_route_access.py`（枚举运行时路由断言清单无死条目 + 未表态=operator）、
   `test_auth.py`、`test_error_contract.py` 的分族语义；本轮实跑 17 支全绿。

## 3. 与"细粒度"目标的差距（如实说）

当前是**两档制**（user / operator）+ 资源归属，不是按能力位的细粒度 RBAC。产品形态
（单机单人为主、多凭据为辅）下这是刻意取舍 —— access.py 头注释明写"多一档只会让
'谁该被挡在外面'重新变成没有答案的问题"。若未来需要第三种角色（如"只读审计员"），
扩 `USER_ROUTES`/新档位即可，现有结构不需要重构。

## 4. 观察项（3 条，均不构成洞）

| # | 观察项 | 处置建议 |
|---|---|---|
| 1 | `USER_ROUTES` 里 `/api/roles` 是 `_ANY`：user 凭据可建/改/删**角色卡本体**。多凭据部署下，使用者能改别人的角色卡（role_id 无 user 归属列，角色卡是实例级资源） | 文档化即可：把"角色卡是实例级、user 档可编辑"写进 access.py 那行注释（现有注释只说了"日常用法"）。真要按人隔离需要 schema 动作，产品上未必想要 |
| 2 | `/api/settings/models` GET 在 user 档（模型菜单要用），但 **model-providers 是 `_ANY`**：user 凭据可增删供应商模板行 | 与 #1 同族：模板行是否含凭据引用决定了这格该不该收紧。建议下一版把"含 key 的行"挪到 operator 档（改动小：USER_ROUTES 摘一行 + 用例改一行） |
| 3 | `AUTH_EXEMPT_PATHS` 命中 operator 级端点时**告警不拦**（`operator_level_exempts` 的设计） | 维持现状（告警+403 分级层兜底的双层设计已在 docstring 论证）；建议在 `.env.example` 的豁免注释里补一句"豁免到管理面会打启动告警" |
