## 2. 三条规则（把拍板写成可判定的形式）

优先级从上往下，一条句子只要落在靠前那条就不往下看：

- **R1 能去称就去称**：去掉代词之后句子仍然**只有一种读法**，就删代词、改用名词或直接用已有的名字。
  判据写死成一句话：*这句旁边有没有已经在屏幕上的名字？* 有（组头、卡片标题、按钮所在那一行）→ 代词一律删。
- **R2 非人对象不许用「她/他」**：一次生成、一条线程、一个模型、一扇窗、一条投递记录 —— 这些用名词，
  用「它」只在"中文里不说出来就断层"的地方保留，且那一处必须**紧邻名词出现**（先名词后代词）。
- **R3 界面确实想要人称温度时，读角色卡上那个字段**：字段只喂**真的缺了代词就变冷**的句子（实测下来是 #7 那一处，两处页面共用一句占位）。
  默认值 = 现值「她」，所以**改完之后不点任何东西的现有角色，屏幕上一个字都不变**。

## 3. 数据面（**本节不采用** —— 拍板选了 (b)，整节留在这里记"为什么不加这一列"）

> **不做的理由（09-29 实测之后）**：把 #1–#16 逐条走一遍 R1 之后，唯一还"想要人称温度"的句子
> 只剩 #7 那一句占位，而它去掉代词换成「对方」反而更准（那半截气泡可能来自桌宠那扇窗，也可能来自
> 控制台，说话的人不一定是当前会话的角色）。**为一句占位加一列 + 一套 CHECK 校验 + 一个表单格子 +
> 一条 `reconcile_columns` 迁移 + 前后端各一根线**，代价与收益不成比例；
> 而"格子摆在界面上却全仓只有一处消费"本身就是一种冗余（09-28 轮立的口径：没有格子的复选框比不给出更坏，
> 反过来也一样：给了没人读的字段等于给下一个人留一个"这是干什么用的"的问号）。
> 将来若真出现第二处消费（角色卡页想显示一行带称呼的简介、或提示词要跟着称呼走），再回来做这一节。

`role_card` 加一列：

```sql
pronoun TEXT NOT NULL DEFAULT '她'
        CHECK (pronoun IN ('她', '他', '它')),
```

- **为什么是「称呼」不是「性别」**：界面需要的是一格能直接拼进句子的字，不是生物学属性。
  存 `gender='female'` 然后在前端映射成「她」= 同一件事两个真相，迟早各说一套（这条仓里栽过）。
- **为什么默认「她」**：内置三张卡与用户已有的卡都是女性人称，默认值换方向会让现有观感一夜改变，
  而这一轮拍的是术语一致性，不是重新给角色定性别。
- **值域里放「它」不放「无」**：选「无」的语义是"这句别用代词"，那是 R1 的事，不该由一个字段去表达。
- 迁移走既有的 `reconcile_columns`（旧库按声明补列，与 `reachout_keep` 那几列同一条路），
  归属仍按 `user_id`，不加新概念。
- 读侧：`roles/models.py` + `service.py` 带出这列 → `api/routers/roles.py` 的序列化 → `frontend/src/api.ts` 的 `Role` 类型。
  **写侧**：`PUT /api/roles` 收这三档之一，收到别的值 400 并带一句人话（与现有校验同形）。
- **它不进提示词**。角色的自称由卡片里的 `system_prompt` 决定，那是用户自己写的字；
  界面这一个字段只管"我们替角色说话时怎么称呼她"。这条是**说出来的不一致**：
  将来若要让提示词也跟着称呼走，那是一次产品改动（会重编所有人格），不是补一个字段。

## 4. 界面（要点头的地方）

**① ~~角色卡编辑抽屉：「称呼」那一格~~ 不采用**（随 §3 一并作废；这一格的样子留在下面，是因为
**将来真做它时形状不用再讨论一次**）——放基础信息那一组（与角色名、描述同组），不进「主动」那组，
控件用现成的三选一单选（与「要紧程度三档」同款形状），不引入新组件：

```
称呼        (○ 她)  (○ 他)  (○ 它)
            只影响界面上的措辞，不会改写你写的人设。
```

那一句说明**必须在界面上**：这一格的默认行为与用户预期之间的落差是"我改了它，她的人设会变吗"，
一行字就堵掉这个疑问（与"不可用控件要配一句怎么才能点"是同一条纪律）。

**② 侧栏组名**：「她们」→「角色」（拍板走 (a)：不留「她们（角色）」那种过渡括号——半改的组名会让两个人都以为是不同的两栏）。同时 #2 #3 那三处徽章/提示跟着去称，#6 那句提示里的「「她们」那一栏」改成「「角色」那一栏」。

**③ 桌宠与对话页的 aria-label**：「它说」→「对方说」。读屏需要的是"这一行不是我说的"，不是性别；
「对方」在两方对话里永远成立，也顺手解掉 #10 那处与「她在说」的自相矛盾。
「我说」不动。**这一处连改 5 个测试断言**（`getByLabelText("它说")` 四处 + `getAllByLabelText` 一处）
—— 实测另外两处跟着改：右键菜单那条 `getAttribute("aria-label") === "它说"` 的判断在**实现**里，
漏了它就是"菜单里再也不出「重新生成这一轮」"，而单测只会红在断言那、不会红在原因那。

**④ 那唯一一处本来想保留代词的句子**：设计时算的是 `{pronoun}在说…`，**落地按 (b) 走 `对方在说…`** ——
理由在 §3 那一节开头：那半截气泡可能来自桌宠那扇窗也可能来自控制台，"当前会话的角色"并不保证是说话的人，
用代词反而不如用"对方"准。

## 7. 明确不做

- **不加 `pronoun` 列**（09-29 拍板，理由见 §3 开头）——包括不加它的 CHECK 校验、表单格子与迁移。
- 不把称呼注入提示词或任何模型输入（角色的自称归 `system_prompt`，那是用户自己写的字）。
- 不做"她/他/它/Ta"里的第四档。
- **不改注释与 docstring 里的代词** —— 除非那句注释**引用了我改掉的那串字面量**（本轮改了两处这样的：
  `ChatPage.tsx:784`、`PetPage.tsx:211`）。区分线是"这句还在说清代码吗"，不是"这句里有没有她"。
- 不做角色卡的 `gender` 独立属性（没有消费方）。
- 不顺手改 A 类（实现视角泄漏）与 C 类（语气格式）—— 那是另一次提交，混在一起会让"这次到底改了什么文案"无法回溯。
