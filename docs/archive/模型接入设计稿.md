## 0. 现在为什么别扭（对着代码说的）

| 症状 | 根因 |
|---|---|
| `siliconflow` 和 `siliconflow-vl` 两行，看起来重复 | 一行 `model_backend` 把**凭据 + 模型名 + 用途 + 能力位 + num_ctx** 焊在一起。同一个 key 要用两个模型，就只能把凭据复制一份 —— 改 key 得改两处 → ✅ **已拆两层**：`model_provider`（一供应商一把 key）+ `model_backend`（模型行），见架构审计 §10.18 与 `core/model_settings.migrate_to_provider_layers` |
| "这行是干什么的"有两处答案 | `model_backend.usage` 要手填，而服务页的端点行**又**引用了一次（`core/services.py:484` 还拿 usage 过滤候选）→ P1-5 那一族没收干净的尾巴 → ✅ **usage 列已删**（`schema.sql:178`），用途改由服务引用行**派生**（`services.py:483` 那句注释就是新口径） |
| 添加模型时不知道能不能用 | 保存即入库 + 热重建；校验只看"这个 provider 要不要 key"，**没有测连这步**。反而是 MCP 那边做了"添加即自动测、连不上标红" → ✅ **已做**：`POST /api/settings/models/probe`（三态：探测到 / 探不到 ≠ 不行），添加抽屉 `AddModelDrawer.tsx:115/130` 在保存前调它，并把结论回填能力位（`:155-158`） |
| 模型名要手抄 | 供应商目录已经有了（`GET /api/settings/model-providers` → `provider_catalog()`），但没做"从这个供应商拉一份模型列表来选" → ✅ **已做**：`POST /api/settings/models/catalog` → `model_probe.list_models`（Ollama 走 `/api/tags`、OpenAI 兼容走 `/models`）。**刻意是 POST 不是 GET**（key 不进 query string），**拉不到回 200 + detail 并退回手填**（中转站经常给不全列表，一次列表失败不该显示成配置失败） |

## 1. 目标流程（就是你描述的那个）

新增模型 = **选供应商 → 选模型名（拉它的列表；拉不到就手填，中转站经常给不全）→ 填 key（同供应商填过就复用，不再问）→ 自动测连 → 通过才入库**。
用途不在这里选（见 §2），能力位默认人勾、可选探测（见 §3）。

## 2. 结构决策：把"供应商"和"模型"拆成两层

- **provider 行（凭据面）**：显示名、`base_url`、`api_key`、是否中转站。**一个供应商一份凭据**。
- **model 行（模型面）**：属于哪个 provider + 模型名 + 能力位 + `num_ctx`。**同 key 下 N 个模型就是 N 行，凭据不再复制**。
- **用途（chat / embedding / rerank / ocr）不再是字段**：它由「服务页哪一类引用了这一行」**派生**。
  于是"用于对话还是语义"真的只需要在服务页配一次，模型页不再问第二遍。
- 迁移：`_migrate` 幂等建表 + 现有行按 `(provider, base_url, api_key)` 归并出 provider 行；
  `usage` 列**保留但停止手填**（改成派生值回显）—— 不改列名、不破坏公开签名是本项目纪律。

> 这一步顺带消灭的是"同一个事实两处各写一遍"，不是只为少点两下鼠标。

### 2.1 批次① 落地时改了哪四条原稿（2026-09-21，代码为准）

写着"保留列"和实际做出来是两件事，落地的偏差必须记下来，否则下一轮有人会照原稿"修回去"：

1. **`model_backend` 的 `provider`/`base_url`/`api_key`/`usage` 四列直接删掉**，不是"留着但不用"。
   原稿说保留列名以不破坏签名 —— 但**读侧签名本来就不断**：`raw_backends()`/`list_backends()`/
   `effective_settings()` 走 JOIN + 派生，仍给出这四个字段，内核与 services 一行没改。
   留在表里的死列才是本项目一直在删的东西（P1-5 那五个"保存了什么都不发生"的字段就是它的前例）。
2. **chat 也做成一条引用行**（`service_endpoint.category='chat'`）。不然 `used_by` 只能派生一半：
   嵌入/重排/OCR 从引用行来，对话从一列来 —— 那正是"两处答案"的老毛病。代价要说清：
   对话默认 = chat 序列第 1 位，回退链 = 其后，**链长不再由保存当场拒绝**（原来是"最多 2 级"
   直接 400，四行 chat 就永远拖不动序），改由运行时 `resolve_fallbacks` 截断，序列里第 4 位
   以后只记录不参与回退。这一档事实面只有一处，写它的入口只有一个（服务页的
   `PUT /api/services/models` → `save_chat_pool`）。
3. **留空的 base_url 折叠到该厂商的默认端点**再分组（`endpoint_key`）。否则"硅基流动 + 没填 URL"
   与"硅基流动 + 填了默认 URL"是两个组，那把 key 就又有了两个家 —— 用户在旧界面加第二个模型时
   天天会走到这条路。
4. **能力位从 bool 改成三态**（`NULL` = 没测过）。写入侧规则：请求里**没带这一列 = 库里是什么
   就还是什么**，只有根本没这行（新增模型）才落到出厂默认。否则一次无关的整表保存就会把
   "没测过"写成"不支持"，界面上 `?` 变 `✗`，而 `✗` 会触发调用前拦截 —— 那是改行为，不是保留原状。
   运行时那侧仍要确定值，未探测一律按"放行"解释（与 P1-2"只拦确定的否"同一条纪律）。

**迁移的一处行为副作用**（不是 bug，但用户可能察觉）：旧库里 `usage='chat'` 却没进回退链的行
（演示库的 `siliconflow-vl`）搬层后会出现在序列尾部，于是它成了新的第 3 位 —— 由于运行时截断
到 2 级，它**实际参与**回退。拆层前它是"chat 用途但不在链上"，那是旧界面写不出来的状态
（服务页一拖序就会把它写进链）。如实记在这里。

## 3. 测连时到底能测什么（这一节必须诚实）

| 探测项 | 怎么测 | 代价与边界 |
|---|---|---|
| 连通 + 凭据有效 | OpenAI 兼容 `GET /v1/models`；Ollama `GET /api/tags` | 一次 HTTP，免费 |
| 模型存在 | 命中上面那个列表 | 0 |
| 真能出字 | 一次最小 completion（`max_tokens=1`） | **1 次调用**，云端扣配额 → 默认不做，勾上才做 |
| 工具能力 | 带一个 no-op 工具的最小请求，看是否返回 `tool_calls`（有些云端 VLM 附工具就空返回） | **1 次调用**，同上 |
| 视觉能力 | 只能真发一张图 | **不能静默做** —— 图片外发是红线（与云端 OCR、SauceNAO 反向图搜同一条义务） |

**结论**：「测试连接」默认只做上面前两项（免费、不外发内容）；能力位仍然人勾，但加一个
**「探测能力」** 按钮，点它之前把代价写在按钮边上（两次模型调用；测视觉会向你选的供应商
发一张测试图），确认后才执行。本地 Ollama 的视觉可以白嫖（`/api/show` 的 `capabilities`，
P1-2 已经做了那个探针），所以**云端和本地的探测能力天生不对称**，界面要如实分开。

### 3.1 探测落地时的一条硬教训（2026-09-21，①-b）

真机第一次跑工具探测就差点误伤：本机 `qwen3-vl:8b` **支持**工具，但面对"必须调用
probe_get_time 来回答"它**直接作答了** —— 按"没返回 tool_calls 就是不支持"的直白判据，
我们会写回 `supports_tools=false`，于是 `call_model` 从此不给这个健康模型绑工具。
症状是"它突然不会用工具了"，比不测更难查。

判据因此是三态（`core/model_probe.probe_tool_capability`），与 P1-2"只拦确定的否"同一条纪律：

| 附了工具的这一次调用回了什么 | 结论 | 为什么 |
|---|---|---|
| 带 `tool_calls` | `True` | 硬证据 |
| **既没内容也没 tool_calls**（空返回） | `False` | 这正是要探的那个真实故障（某些云端 VLM 一附工具就空返回） |
| 有内容但没调工具 | `None`（没测过） | 它完全可以只是选择直接回答 —— 不知道就说不知道 |
| HTTP 失败 / 超时 | `None` | 问不到不是"不能" |

同一纪律下的另外两条：`vision` 云端只在 `test_vision=true` 时才测（图片外发是红线），本地走
`/api/show` 元数据所以永远免费且不出机；`model_listed=false` **只是提示**（中转站的列表经常不
全），手填仍然可以加入 —— 列表不是白名单。

## 4. 不可用控件的通则（你说的"该变灰不让按"）

分三类处理，别再一刀切：

1. **在这个部署形态里永远不可能用** —— B/S 里起停本机进程、dev 下的开机自启。
   → **整条不出现**（现有口径）。给一个永远点不动的控件是噪音，也骗人去点。
2. **暂时不可用，但有明确恢复路径** —— 默认模型未驻留时的「释放显存」、没填 key 的行的「测连」、
   知识库还没索引时的「重建」。
   → **出现 + 禁用 + 一句话说明怎么恢复**。这才是该置灰的那一类，也是你现在觉得别扭的地方。
3. **不确定能不能用** —— 探针问不到、云端探不了。
   → **不拦、不禁，如实显示"未知"**（P1-2 的三态口径；"未知"当"不能用"会误杀能用的模型）。

### 4.1 全站盘查结果（2026-09-20 已做）

| 位置 | 原来 | 现在 |
|---|---|---|
| `ui/Button` | ghost/danger **没有禁用样式**，也没有能显示原因的出口（`title` 在禁用按钮上 Chromium 不弹） | 补齐禁用态 + 新增 `disabledHint`（只在禁用时渲染，说明落在 DOM 里）—— 全站这条规则的唯一实现 |
| `LocalServiceCard`「释放显存」 | 显存里没模型时**整个不出现**（用户不知道有这能力） | 出现 + 禁用 + 「显存里现在没有模型 —— 预热或发一条消息之后这里就能用」 |
| `LocalServiceCard`「预热/常驻」 | 服务没在跑时**照样可点**，点了必吃 502 | 禁用 + 「本机推理服务没在跑 —— 先把它起起来才能预热」 |
| `ApprovalPanel` 批准/拒绝 | 令牌已用掉或列表是旧的时照样可点，点完才 403 | 禁用 + 「决定令牌已用掉或过期 —— 关掉重开待批列表再批」 |
| `ServicesPanel` ↑/↓ | 停用的行禁用了但只有 `title="上调优先级"`（说不清为什么不能点） | 保留 title，另加一行「该行已停用 —— 先「启用」才能排优先级」 |

**盘过之后刻意不改的三处**（写清楚，免得下一轮又被"顺手修好"）：
- `ShellReleaseCard` 配置了目录但还没有产物 → **仍然整卡不出现**。受众是终端用户，
  他修不了"部署的人没拷产物"，给一句报错只是噪音；这条属于第 1 档而不是第 2 档。
- `ChatPage` 的发图按钮 → **仍然不禁用**。云端探不了视觉 = 第 3 档"不确定"，
  按"未知当不能用"会误杀能看的模型；后端已有调用前拦截（P1-2）。
- `DataPage`/`Records` 在插件关掉时**不灰**：写库本身是合法的用户动作（模型看不见工具而已），
  灰掉等于替用户决定"你关了插件就不许管自己的数据"。

> **非反应式检测**这个已知限制留着：`shellBridge()` 在渲染期求值，桥若晚到会不刷新 ——
> 桌面壳里桥总在首帧前就位，所以现在不出问题；真出问题再做 hook，不提前造。

## 5. 施工顺序与不做

1. **§4 的全站控件盘查 + 收口**（小、立刻改善手感，且不改数据结构）。
2. **§2 的凭据/模型拆分 + usage 派生**（一次迁移 + 模型页与服务页两轮界面改动）→ 这一步跑全量门禁。
3. **§1 的"拉模型列表来选" + 测连门禁**（新增 `GET /api/settings/models/catalog?provider=` 之类的端点）。
4. **「探测能力」按钮**（含云端外发测试图的显式确认）。

**不做**：多租户的模型权限（还没有第二个用户）；自动选路/智能路由（回退链 ≤2 已经够用）；
"模型能力自动学习"（探测不到的东西宁可信人手勾，别让它悄悄改变行为）。
