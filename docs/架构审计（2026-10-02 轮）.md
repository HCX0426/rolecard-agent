## H1 · 执行摘要

**整体健康度：结构是真的，暗面也是真的。** 承重结构经两波独立取证站住了：内核不认识 HTTP
（`core/`→`api` 0 条依赖边）、装配单链、域间零互 import、47 条一致性断言真在咬人（本轮门禁唯一红
正是它在干活）、开轮批 8 条红当场收口且每条有变异证据。但复审批在同一骨架上照出开轮批没碰的两块暗面：
**一是来源信任边界**（P0：网页可全量接管后端并替用户批准命令，主控已复跑全链），
**二是复合写的原子性与终态**（整份替换先清后导可以"清了不导"；审批执行无兜底可以永久卡死）。
共同根因一句话：**本仓的信任模型与事务模型都建立在"单机、单用户、无并发"的假设上，
而同步、审批、后台执行三个功能早已打破这个假设**。

**最大架构风险：`R102-45`（P0）。** AUTH_MODE=off（默认）下，后端把「TCP 对端是 127.0.0.1」
等价于「用户本人」，而浏览器发起的 DNS rebinding 请求与跨源盲 POST 的对端同样是 127.0.0.1。
主控实测四步全通：伪造 Host 读端点 → 从审批列表原文拿 `decide_token` → 替用户批准 →
命令真实执行（`result_json` 里就是探针命令的输出）。

**核心建议（按杠杆排序）**：
1. **立一层「本机来源标识」中间件**（`R102-45`/`46` 一次收两个洞）——把信任模型从
   "对端=本人"升级为"对端+来源标识=本人"，覆盖全部端点，不是逐端点打补丁。
2. **给三条复合写路径补终态与原子性语义**（`R102-47`/`48`/`52`）——审批状态机要自足
   （任何路径都达终态）、整份替换要单事务、幂等要下沉到库层。
3. **迁移链事务化 + `user_version`**（`R102-53`/`54`，与老项 `R102-27`/`11` 同批）——
   消灭"库再也打不开"的第三种死法与降级无护栏。
4. **前端契约立第三把尺子**（`R102-50`）——九条用户可见红全部住在"后端↔前端↔产物"的接缝上，
   而契约测试只看守 `api.ts`/`stream.ts` 两份文件，组件侧 payload 全靠各测试自编自测。

## H4 · 架构级修复方案汇总（按模块与边界）

1. **api/ 来源信任边界（新增一层，而非逐端点补）**：`R102-45`/`46` 共用一把刀——
   「本机来源标识中间件」放在认证之前：Host 必须命中 `{127.0.0.1[:port], localhost[:port], [::1]}`，
   带浏览器来源头且 Host 非白名单 → 403；`decide_token` 从"读侧明文下发"改为"读侧 `has_token`
   布尔 + 批准时由界面换发"。独立开关 `LOCAL_ORIGIN_ENFORCE=0` 保回滚。
2. **core/approvals 审批状态机自足（把"执行一次"的契约从路由层收回状态机）**：
   `R102-47`（终态兜底：失败本身作为 result 回填 done）+ `R102-52`（幂等下沉：pending 部分唯一索引 +
   撞索引回读既有行）。后台任务的监督收口与 `_CHAT_POOL` 同等待遇（Future 统一 `add_done_callback`）。
3. **storage 层"按 thread_id 级联删"唯一入口 + 替换单事务（删除路径的 repository）**：
   `R102-48`/`26` 同批——`_clear_for_replace` 与单删路径都改走一个级联删入口；replace 的
   清空+导入收进同一显式事务（per-item 容错保留为 SAVEPOINT）；import 入口先按 `SYNC_KINDS`

### 安全（R102-45/46/56/57/58）

**R102-45｜P0｜伪造 Host 可全量接管后端并替用户批准命令（含跨源盲 POST）**
- 位置：`api/main.py:270-336`（认证中间件全链无 Host/Origin 校验）；`api/auth.py:274`（`auto` 档回环放行）；`api/access.py:124-132`（off 档 `enforce=False` 一律放行）；bind 护栏 `main.py:171-180` 只挡非回环绑定，恰好放行本条。AUTH_MODE 默认 off（`config.py:393`）。
- 问题：信任模型把「TCP 对端是 127.0.0.1」当用户本人；浏览器发起的 rebinding 请求与跨源盲 POST 的对端同样是 127.0.0.1。审批 token（挡盲 POST 的设计，`api/routers/approvals.py:8-10` 自述）与 `require_loopback` 都建立在这层缺失上。
- 证据（**复核=复跑**，主控 HEAD `6a4fd8e`、临时库、127.0.0.1:58431）：① `curl -H "Host: attacker.example" /api/health` → 200；② 临时库插一条 pending → `GET /api/approvals?status=pending` 原样回 `"decide_token":"tok_audit_reverify_1"`；③ `POST /api/approvals/1/decide`（`{"decision":"approve","token":"tok_audit_reverify_1"}`，伪造 Host）→ 200；④ 2 秒后该行 `status=done`、`result_json={"exit_code":0,"output":"pwned_probe\n"}`——命令真执行。盲 POST 半区（该路实测）：`POST /api/uploads/cleanup` 带 `Origin: evil`（无预检）→ 200 `{"deleted":0,...}`；`/api/session/{tid}/stop` 同 200。
