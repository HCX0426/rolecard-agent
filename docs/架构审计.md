## 0. 总体判定

- **后端 shell-agnostic：合格。** `core/` 对 FastAPI/starlette/SSE **零 import**，LangGraph 内核与 HTTP 彻底解耦，C/S 桌面壳原则上可直接复用 core。✅
- **唯一实质复用障碍**：`api/chat.py` 把"一轮对话编排"和"SSE 帧化"缠在一起（~250 行），且装配根 `build_kernel` 只在 `api/main.py`。→ **两条都已落地**：`core/bootstrap.py`（装配根）+ `core/turn.py`（轮次编排发结构化事件、HTTP 只帧化），见 §10 与 §7。
- **架构设计 B+**：核心机制（guard 嵌 call_model、bind 阶段裁剪、prompt 现拼、ContextVar 注入、能力位）都是"通用机制、放对层"，无厂商/角色特判；但有一批**反应式补丁与假接缝**（§4）。
- **发现 3 个 P0 级 bug**（其中 2 个是用户现在就会踩的活 bug）+ 一批 P1 正确性/泄漏 + P2 设计/UX/性能。

## 4. 界面分组合理性（前端信息架构）

**核心问题：一个配置项有多个家 + "通用"成杂物抽屉。**

- **默认后端/回退链双入口**：模型页「默认」radio（`SettingsPage.tsx:954`）vs 服务页排序（`ServicesPanel.tsx:273`），写同一份（`services.py:546`）；后端已声明"编辑入口统一到服务页"（`settings.py:139`）→ 模型页那个 radio + fb1/fb2 该删（顺带修 P0-2）。

- **主动开口总闸两入口**：通用「主动开口」卡 vs 运行环境 reachout 组。
- **嵌入/重排/OCR 三入口**：模型页 usage 标签 / 服务页引用 / 运行环境 RAG_*、OCR_*。
  → **P1-5 已收口**：第三个入口（运行环境的选型行）连同那 6 个字段一起删除，
  选型只剩「服务」页一处，凭据只剩模型页一处。

## 6. 测试性能（实测）

- 全套 641 collected，墙钟 **199s**（Ollama 在跑）。**最慢 `test_records_api::test_extract_rejects_a_second_call_while_one_is_running` 独占 46~66%**（实测 130/93/92s）——其 `client` fixture 未注入 model → 走**真实 qwen3-vl:8b**，断言接受 200/502 故恒绿。
- **隐蔽外呼**：`main.py:308/337 _auto_pin_default_model` 每次 lifespan 真 POST `/api/generate`（timeout 120）；测试补的是 `routers.settings.ollama_keep`，**没补 main** → 20 处 `TestClient` + 冒烟都把 8B 钉进显存争 GPU。
- **冒烟**：13 项离线 ~98s（其中 `_settings` 仍打真 Ollama，与"离线"自述不符）+ 1 项真机 UI ~630s（真 Chrome + 真对话，固定 sleep + 90/180s 等待）。**缺陷**：`console_ui_smoke` 的 `@check` 在模块顶层 → 装饰即执行，实际**最先**跑（与"放最后"相反）。✅（顺序反常已实测）
- 金字塔：unit 475(74%) / API 166(26%) / 冒烟 14 / 前端 vitest 72 —— 比例健康，问题是**顶层冒烟含真模型，比底层贵两个数量级**。

**提速方案**：① 该 fixture 注入 `ScriptedChat`/`model_factory` → 全套降到 ~35-45s（快 4-5×）；真模型路径另立 `@pytest.mark.live`。② lifespan 预热加开关 `create_app(pin_on_startup=False)`。③ 注册 markers，`--fast` 用 `-m "not live"`。④ ui_smoke 用 `waitForSelector` 换掉固定 sleep、超时下调。⑤ 校正 `gate.py`/`开发流程.md` 的计时口径（现称 fast≈51.7s，失真）。

> **2026-09-19 落地情况**：①~⑤ 全部完成，实测 pytest **199s → 73.7s**、离线冒烟 **98s → 10s**。
> 两处与方案预设不同，按"确定的前提"取向做了调整：
> ① 抽取端点**没有** `model=` 注入口（它按 `MODEL_BACKENDS` 自建调用器），所以把该文件的
> fixture 指向**必然拒绝连接**的端口（`127.0.0.1:9`）而不是塞假模型 —— 顺带把原来
> `in (200, 502)` 的**恒绿断言**收紧成确定的 502；真模型路径立成了 `test_extract_with_a_real_model_...`
> （`@pytest.mark.live`，`pytest -m live` 才跑）。② 用 `Settings.model_pin_on_startup`
> （env `MODEL_PIN_ON_STARTUP`）而不是 `create_app` 的关键字参数：`with TestClient` 的站点有
> 23 处，逐个加参数会把离线纪律散落到每个文件，配置契约里加一项 + conftest 会话级 autouse
> 一处封死才是同一个机制。剩余 73.7s 的大头是 ~640 个用例各自的建库/装配开销（并行反而更慢，
> 见 `gate.py` 的实测记录），两条死端口用例各 ~7s 来自 langchain 客户端的连接重试。

## 11. 规划增补（2026-09-19 审计轮之后新增，未开工）

### 11.1 模型页「本地推理服务」启停卡（用户 2026-09-19 提出，设计已拍定）

动机是真实痛点：8 GB 显存上默认模型 `qwen3-vl:8b` 被启动预热以 `keep_alive=-1` 钉死
（实测 `expires_at` 是 2318 年），**它自己永远不会让出显存**；要玩游戏/跑别的模型就得手动卸。
今天这一幕（"Ollama 停一下，我要玩游戏"）就是要做成界面的那个动作。

设计（**三档齐全**，用户已确认）：

| 档 | 语义 | 实现 | 风险与防护 |
|---|---|---|---|
| 卸载模型 | 释放显存，服务进程留着（回来第一条消息自动重载） | `POST /api/generate {"model":…,"keep_alive":0}`，原语已在 `core/probes.ollama_keep` | 无。这是默认按钮 |
| 停止服务 | 杀掉 `ollama serve` 进程 | 只允许停**由本应用启动**的进程（记录 spawn 的 PID + 校验端口归属）；别人手动起的实例只显示不操作 | 误杀是主要风险；停止后正在跑的对话/抽取要收到可读失败而不是挂住 |
| 启动服务 | 拉起本地服务 | 需要可执行文件路径 → 新配置项 `OLLAMA_BIN`（**必须走 `Settings` + `from_env` + `.env.example` 契约**，不许在代码里 `os.environ` 直读，见 P1-4 的教训）。本机 Ollama 是便携安装、不在 PATH，自动发现要有失败兜底 | 起进程 = 本机执行，见下面的安全边界 |

状态行要显示：在跑/没跑、哪个模型驻留、占用/总量、是谁起的（本应用 / 外部）。
UI 位置：设置 → 模型页顶部一行卡片（不新开页签）；`前端设计.md` 能力矩阵加一行"可见/可控"。

⚠️ **安全边界（写死，不留配置）**：这是一组"能起停本机进程"的端点，而 §1 的 P0-3 尚未闭环
（`AUTH_MODE` 默认 off + 审批可自批 = 公网即自批 RCE 链）。所以这些端点从第一天起
**只接受回环来源调用**（不看 `X-Forwarded-For`，复用 `api/auth.client_ip` 的 TCP 对端口径），
且不随 `AUTH_MODE` 放开。等 P0-3 的 operator 鉴权建起来，再把它纳入同一套角色判定。

依赖顺序：与 `core/turn.py`（§7 D 的最后一条返工点）**无冲突** —— 那是在动对话链路的编排，
这是新增一组管理端点。先做哪个都不挡另一个。

**落地（2026-09-19，第一档 + 状态）**：`api/routers/local_service.py` 三个端点
`GET /api/local-service`、`POST /api/local-service/pin`、`POST /api/local-service/unload`，
界面在设置 → 模型顶部一张卡（`components/LocalServiceCard.tsx`）。三处值得记的偏离与收获：

- **原来那半张卡被合并了**：「预热/常驻」原先是 `routers/settings.py` 的
  `GET /api/settings/models/resident` + `POST /api/settings/models/keepalive`，与新的卸载端点
  分家 = 两处各写一遍"什么在显存里"（P1-5 收口的正是这类"两处各自实现且不同步"）。
  合并到一处后旧的两个端点**删除**，
  `num_ctx` 透传的断言搬到 `test_local_service_api.py`，`PATCH .../context` 的读回另补一条。
- **合并顺带补了一个洞**：`keepalive` 原先挂在设置路由上、**没有回环门禁**，而它会驱动进程去
  加载 5.8 GB —— 公网部署时等于任何人可远程撑满显存。现在 `pin` 与 `unload` 吃同一道门禁。
- **状态行没有"占用/总量"**：总量要读 `nvidia-smi`，本机（WDDM/混合显卡）那个数不可信，
  而且多一个进程外呼就是多一种失败模式。卡片只显示 Ollama 自己报的驻留字节数，够用。

`停止服务 / 启动服务` 两档**仍未做**，等 D② 的桌面壳：`OLLAMA_BIN` 与 PID 归属校验都属于壳侧
的进程管理，先在 HTTP 层做一遍到壳里还要挪一次。

### 11.2 运行形态与分发（2026-09-20 定，含一处自我更正与一次壳选型翻转）

用户问的两件事把形态问题逼了出来："总不能后端还放我这吧"、"别人填其他厂的 API key 能不能用"。

**先说承诺并钉住的那条**：**不装 Ollama 也必须是完整可用的一等形态**。核实结果是对话/抽取
（模型页任意 OpenAI 兼容行 + key）、检索嵌入（服务页端点序，`hash` 兜底）、OCR（云端行需
操作员显式建凭据行）都不依赖本地推理；受影响的只有三处，且都不影响可用性：视觉能力探针
（`vision_model_ready` 问的是 Ollama，云端只信声明的能力位）、模型页那张本地服务卡（会老实
显示"未运行"）、以及隐私边界从"全本地"变成"文本走第三方"。这条整体成立由
`tests/integration/test_cloud_only_shape.py` 负责（跨装配根/预热/地址解析/主动投递四个模块，
拆进各模块单测就没人对"这一形态"负责）。

**两个运行形态，按"这台机器是不是别人也会连"分，不按有没有网分**：

| 形态 | 后端在哪 | 绑定 | 安全前提 |
|---|---|---|---|
| **A 单机自用**（桌宠/桌面 App，**当前目标**） | 用户自己机器（sidecar 随包） | 127.0.0.1 | 回环即边界，`AUTH_MODE=off` 可用；主机影响类端点的回环限制天然满足 |
| **B 共享服务**（v2.4 那条线，暂不做） | 某台服务器 | 0.0.0.0 / 反代 | **必须** `AUTH_MODE=on` + 多用户身份 + 速率限制 + 审批鉴权（P0-3 未闭环前不能开） |

"模型走本地还是走云端 API"是**另一根独立的轴**，四种组合都合法 —— 之前把两根轴混在
"离线/在线"这一个词里，会生出"给离线模式做一套代码"这类伪需求。

**自我更正（记下来是因为它差点误导了选型）**：我拿"安装包 6 MB vs 100 MB"比较壳时，比的
是**只装壳**。一旦按形态 A 把 Python 后端打进包（PyInstaller/Nuitka → 200–500 MB），
两边总包体积基本相同，Tauri 的体积杀手锏在自包含分发里不成立。

**于是壳选型翻转：Tauri → Electron**（用户 2026-09-20 拍定"换吧，早换早好"）。理由按分量排：

1. **D② 剩下的活全是原生能力胶水**（托盘/自启/全局热键/系统通知/单实例/窗口位置记忆）。
   Electron 里每一项都是同一份 TS；Tauri 里每一项都是 Rust 侧改动 + 一个插件 + capability
   配置 + 一次 cargo 编译。
2. **与本项目门禁贴合**：Electron 跑在现成的 npm + tsc + vitest 上，壳代码能进同一套门禁；
   `cargo build` 几分钟，gate.py 覆盖不到，只能靠手工验（这一轮就是这么过的）。
3. **体积优势被后端抹平**（见上），而"你这台机器"的装机成本从 1.5 GB 工具链 + 两颗坑
   变成零编译器、`npm i` 即可。
4. 保留的优势承认更小：Tauri 省 100–200 MB 常驻内存（只在本地模型场景有意义）、更新包小
   （但整包大头是后端，本来就得重发）。

**反过来该选 Tauri 的唯一情形**：如果最终不做自包含包，而是"壳只 6–10 MB、用户连你部署的
服务"（形态 B），小体积/小更新/系统 WebView 又都回来了。所以这个选择的真正前提是分发形态，
而形态已定为 A。

**从 Tauri 实测里带走的三条结论**（换壳不改变它们，是桌宠这类窗口的通用事实）：

1. **透明窗必须截屏幕区域验**，按窗口截图（WGC/类似机制）不合成下层窗口，永远看不出来 ——
   这条验证死胡同走过一次。WebView2 与 Chromium 的 per-pixel alpha 都能真透明。
2. **不能让窗口直接指向后端地址**：后端没起来时内核浏览器会显示它自己的错误页（实测
   "嗯…无法访问此页面"），那块白底 + 浏览器文案比桌宠还显眼，我们写的可读提示根本没机会
   渲染。正确做法是每扇窗先落**壳自带的本地着陆页**，探活成功再跳。
3. **进程归属不能只挂在"正常退出"上**：硬杀/崩溃时后端会变孤儿，占着端口（本地模型场景还占
   着 6 GB 显存）。Tauri 版用 Win32 作业对象（`KILL_ON_JOB_CLOSE`）实测有效；换 Electron 后
   等价做法是**后端自己盯着父进程**（`ROLECARD_PARENT_PID` + 看门狗线程，父没了就自杀），
   这样这条保证与壳无关，两种壳都受益 —— 该做在后端，不该做在壳里。

**待办**：sidecar 自包含打包（PyInstaller onedir + 随包 `dist/`，安装包 200–500 MB）排在 D
的收尾，不打断桌宠主线；B/S 的"下载壳安装包"入口按已定方案由后端托管、**有产物才显示**。
