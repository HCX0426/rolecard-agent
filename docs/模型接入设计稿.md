## 0. 现在为什么别扭（对着代码说的）

| 症状 | 根因 |
|---|---|
| `siliconflow` 和 `siliconflow-vl` 两行，看起来重复 | 一行 `model_backend` 把**凭据 + 模型名 + 用途 + 能力位 + num_ctx** 焊在一起。同一个 key 要用两个模型，就只能把凭据复制一份 —— 改 key 得改两处 |
| "这行是干什么的"有两处答案 | `model_backend.usage` 要手填，而服务页的端点行**又**引用了一次（`core/services.py:484` 还拿 usage 过滤候选）→ P1-5 那一族没收干净的尾巴 |
| 添加模型时不知道能不能用 | 保存即入库 + 热重建；校验只看"这个 provider 要不要 key"，**没有测连这步**。反而是 MCP 那边做了"添加即自动测、连不上标红" |
| 模型名要手抄 | 供应商目录已经有了（`GET /api/settings/model-providers` → `provider_catalog()`），但没做"从这个供应商拉一份模型列表来选" |

## 1. 目标流程（就是你描述的那个）

新增模型 = **选供应商 → 选模型名（拉它的列表；拉不到就手填，中转站经常给不全）→ 填 key（同供应商填过就复用，不再问）→ 自动测连 → 通过才入库**。
用途不在这里选（见 §2），能力位默认人勾、可选探测（见 §3）。

## 2. 结构决策：把"供应商"和"模型"拆成两层

- **provider 行（凭据面）**：显示名、`base_url`、`api_key`、是否中转站。**一个供应商一份凭据**。
- **model 行（模型面）**：属于哪个 provider + 模型名 + 能力位 + `num_ctx`。**同 key 下 N 个模型就是 N 行，凭据不再复制**。
- **用途（chat / embedding / rerank / ocr）不再是字段**：它由「服务页哪一类引用了这一行」**派生**。
  于是"用于对话还是语义"真的只需要在服务页配一次，模型页不再问第二遍。
- 迁移：`_migrate` 幂等建表 + 现有行按 `(provider, base_url, api_key)` 归并出 provider 行；
  `usage` 列**保留但停止手填**（改成派生值回显）—— 不改列名、不破坏公开签名是本项目纪律。

> 这一步顺带消灭的是"同一个事实两处各写一遍"，不是只为少点两下鼠标。

## 3. 测连时到底能测什么（这一节必须诚实）

| 探测项 | 怎么测 | 代价与边界 |
|---|---|---|
| 连通 + 凭据有效 | OpenAI 兼容 `GET /v1/models`；Ollama `GET /api/tags` | 一次 HTTP，免费 |
| 模型存在 | 命中上面那个列表 | 0 |
| 真能出字 | 一次最小 completion（`max_tokens=1`） | **1 次调用**，云端扣配额 → 默认不做，勾上才做 |
| 工具能力 | 带一个 no-op 工具的最小请求，看是否返回 `tool_calls`（有些云端 VLM 附工具就空返回） | **1 次调用**，同上 |
| 视觉能力 | 只能真发一张图 | **不能静默做** —— 图片外发是红线（与云端 OCR、SauceNAO 反向图搜同一条义务） |

**结论**：「测试连接」默认只做上面前两项（免费、不外发内容）；能力位仍然人勾，但加一个
**「探测能力」** 按钮，点它之前把代价写在按钮边上（两次模型调用；测视觉会向你选的供应商
发一张测试图），确认后才执行。本地 Ollama 的视觉可以白嫖（`/api/show` 的 `capabilities`，
P1-2 已经做了那个探针），所以**云端和本地的探测能力天生不对称**，界面要如实分开。

## 4. 不可用控件的通则（你说的"该变灰不让按"）

分三类处理，别再一刀切：

1. **在这个部署形态里永远不可能用** —— B/S 里起停本机进程、dev 下的开机自启。
   → **整条不出现**（现有口径）。给一个永远点不动的控件是噪音，也骗人去点。
2. **暂时不可用，但有明确恢复路径** —— 默认模型未驻留时的「释放显存」、没填 key 的行的「测连」、
   知识库还没索引时的「重建」。
   → **出现 + 禁用 + 一句话说明怎么恢复**。这才是该置灰的那一类，也是你现在觉得别扭的地方。
3. **不确定能不能用** —— 探针问不到、云端探不了。
   → **不拦、不禁，如实显示"未知"**（P1-2 的三态口径；"未知"当"不能用"会误杀能用的模型）。

需要**盘一遍全站**把现在归错类的控件列出来（ExtensionPanel 的按钮、数据页的清理、知识页的索引
重建、模型页的常驻/卸载…），一次专门的 UI 提交收口，顺带更新 `docs/前端设计.md` 的组件约定。

## 5. 施工顺序与不做

1. **§4 的全站控件盘查 + 收口**（小、立刻改善手感，且不改数据结构）。
2. **§2 的凭据/模型拆分 + usage 派生**（一次迁移 + 模型页与服务页两轮界面改动）→ 这一步跑全量门禁。
3. **§1 的"拉模型列表来选" + 测连门禁**（新增 `GET /api/settings/models/catalog?provider=` 之类的端点）。
4. **「探测能力」按钮**（含云端外发测试图的显式确认）。

**不做**：多租户的模型权限（还没有第二个用户）；自动选路/智能路由（回退链 ≤2 已经够用）；
"模型能力自动学习"（探测不到的东西宁可信人手勾，别让它悄悄改变行为）。
