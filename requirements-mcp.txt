# MCP 扩展通道依赖（架构计划 C·§6.1，core/tools/mcp.py）
# **它是运行树的一族，不是可选 extra**（2026-10-01 改的分类，理由在 check_consistency 的
# `installer scope parity` 那段）：随包后端自 09-29 起带它（R28-34），镜像自 10-01 起带它
# （R28-53），源装形态（install.bat / README / CI）同一批跟上 —— 四条路径装的是同一套。
# 装载仍然**不是"非有不可"**：未装时 loader 打 warning 并跳过 MCP 工具，核心对话照跑
# （fail-open 只影响扩展能力）。但"界面照常摆着、工具永远加载不出来"这个形状已经红过三次，
# 所以不再让每条安装路径自己决定装不装。
langchain-mcp-adapters>=0.0.9
# **`mcp` 也要点名**（10-01，与 `R28-11` 那个"httpx 靠传递依赖兜住"同族）：它从前只作为
# adapters 的依赖被带进来，而 `core/tools/mcp.py` 与 spec 的 `RUNTIME_PACKAGES` 都**直接**用它。
# 上游哪天把它改成 optional extra，我们的装法会照旧"成功"，包内模块数却掉到零 ——
# 症状是设置页那格照常摆着、一个工具都加载不出来。新那条门禁断言（spec 要收的每一族都得
# 在这五份里有声明出处）也靠这一行才绿。
mcp>=1.30
# **`pywin32` 也要点名，并且带标记**（2026-10-08 CI 实撞立案）：它是 `mcp` 的传递依赖，而
# `pip-compile` 把传递依赖写进锁时**丢掉上游的环境标记** —— 于是 Windows 上解析出的锁躺着
# 一条裸的 `pywin32==312`，Linux 用同一把锁装（CI 门禁臂、镜像、发布链）第一步就崩：
# `No matching distribution found for pywin32==312 (from versions: none)`。
# 为什么必须住在**这一侧**而不是手改锁：实测过两条相反的路 —— 输入里带标记的行，标记**会活进
# 锁**（`pywin32==312 ; sys_platform == "win32"`）；而手工把标记加到锁里、再跑一轮 compile，
# 标记被**重新剥掉**（周更锁 `lock-refresh.yml` 会静默 revert 那种改法）。判据 `lock platform
# markers` 盯着这件事：镜像带标记而锁里裸着 ⇒ 红。
# 与上面 `mcp` 那条同一条纪律：靠传递依赖带进来的东西，装法由别人的一句话决定。
pywin32>=310 ; sys_platform == "win32"
